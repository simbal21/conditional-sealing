# Fresh adversarial audit — net-new findings (HEAD e87c108, 2026-06-02)

Scope: all Solidity in contracts/src/. Read-only. Verdicts grep/read-confirmed at HEAD.

## F-1 (CRITICAL) — Mode F FSM conditions are not enforced; engine fabricates a trivially-terminal transition
- ConditionEngine `_evaluateAxis` (src/engine/ConditionEngine.sol:468-483) builds its OWN TransitionProof for Mode F: fromState=0, toState=1, terminalState=1, maxTransitions=1, deadline=0, fsmHash=config.conditionSpecHash. Calls `_fsmInterpreter.advanceFSM` once and treats `result.terminal` as the condition.
- FSMInterpreter.advanceFSM (src/fsm/FSMInterpreter.sol:124-167) NEVER validates that the transition (fromState→toState) is a legal edge in the committed FSM. It only checks `proof.fsmHash == state.fsmHash` (opaque equality of a public value) and `proof.fromState == state.currentState`. `transitionId` is only checked non-zero (L134) and folded into cursorData (L160) — never matched against any transition table. The doc comment claims "(c) transitionId is a legal outgoing transition" and "(d) transitionProof verifies against the configured FSM bytecode" — the code does neither.
- Result: terminal = (currentState==toState==1) == (terminalState==1) = true on the FIRST call. Confirmed by test ConditionEngine.t.sol:341-346 (configureFSM with initialState=0,terminalState=1 → single authorizeReveal succeeds).
- `authorizeReveal`/`authorizeShred` are PERMISSIONLESS (ConditionEngine.sol:208,242). So any Mode F reveal/shred PDA whose FSM sits at state 0 with matching fsmHash fires on the first anonymous call, regardless of the multi-step real-world sequence the FSM was meant to enforce (KYC sequence, M&A deal-stage, multi-phase regulatory). This DEFEATS the Universal Tripwire for every Mode F PDA: RevealAuthorized/ShredAuthorized emits without the real condition holding.
- Fix: FSMInterpreter must validate transitionId/(fromState,toState) against the on-chain-committed transition set bound by fsmHash (e.g., merkle membership of the edge under fsmHash, or an on-chain transition table). The engine must NOT fabricate the proof; the real submitter-supplied proof (advanceFSM path) must drive evaluation, and `_evaluateAxis` Mode F should read the FSM's actual terminal state, not assert a hardcoded 0→1.

## F-2 (HIGH) — markChallengeResolved bypasses the ChallengeRegistry and the challenge window
- ConditionEngine.markChallengeResolved (src/engine/ConditionEngine.sol:296-311), OPERATOR_ROLE. For Reveal axis it only checks `lifecycle == RevealChallengeOpen`, then forces `postChallengeReveal = true` and transitions to PostChallengeRevealInProgress.
- NO check that `block.timestamp >= challengeWindow end`. NO read of the ChallengeRegistry to see whether a challenge is Open/Halted. The engine stores `_challengeRegistry` (L102,133) but NEVER reads it anywhere (grep-confirmed: only assignment, no usage).
- `canGatesSign` (L333-338) returns true for PostChallengeRevealInProgress → off-chain gates sign → DEK reconstructed → reveal delivered.
- Exploit: a subject/data-subject opens a legitimate challenge in ChallengeRegistry (e.g., DataSubjectErasureInvoked / Art22InterventionRequested). The OPERATOR can immediately call markChallengeResolved while that challenge is still Open and unresolved, stomping the dispute window and forcing the reveal. The ChallengeRegistry resolver (CHALLENGE_RESOLVER_ROLE, per-PDA) never gets a say. This is a single-OPERATOR override of the challenge mechanism — contradicts the "system-locked / halt-capable" posture.
- Fix: markChallengeResolved (Reveal) must require either (a) `block.timestamp > recorded challenge deadline` with no open challenge, or (b) a positive ConfirmedNoIntervention status from ChallengeRegistry for (authorizationId, axis). Bind the engine to the ChallengeRegistry it stores.

## F-3 (HIGH) — PasskeyRotationLog.appendRotation performs no signature authentication; any account's active passkey chain is hijackable
- src/passkey/PasskeyRotationLog.sol:79-118. Permissionless. The only "auth" checks are `webauthnAssertion.length != 0` and `rotationAuthorizationDigest != bytes32(0)` (L110). NO P-256/WebAuthn signature verification anywhere on-chain (grep: zero p256/secp256r1/RIP-7212/precompile usage in src/). `rotationAuthorizationDigest` is never checked against entry contents or any signature.
- Chain continuity requires `prevPubkey == prior.newPubkey` (L104) — but the prior newPubkey is PUBLIC via getEntry. An attacker who reads the current head can append index N+1 setting `newPubkey` to a key they control, `prevPubkey` = current head's newPubkey, any non-empty `webauthnAssertion`, any non-zero digest.
- Docstring (L13-19) states combiners + G4 verifier use this log "to prove a subject's currently-active passkey at commit_block." A hijacked head redirects which key is treated as active. Append-only means the legitimate subject cannot reclaim the chain (index is consumed; attacker is now the chain owner).
- Mitigation only if off-chain consumers independently verify WebAuthn — but the contract is presented as the on-chain proof and provides no authentication. Fix: verify the WebAuthn/P-256 assertion (RIP-7212 P-256 precompile on Base) over the rotationAuthorizationDigest against the PREVIOUS active pubkey before accepting the rotation.

## F-4 (MEDIUM) — Mode-P condition modules' state-mutating paths are unreachable through the engine (dead reveal path / liveness)
- ConditionEngine never calls `module.advance()` nor any typed submit/observe fn (grep-confirmed: only `IConditionModule(module).evaluate(...)` view at L487 and `_fsmInterpreter.advanceFSM`). Module write fns (markDefaultObserved, markPaymentObserved, submitOracleAttestation, submitSubjectInitiated, submitConsent, setChildResult, recordHeartbeat...) are all `onlyConditionEngine` (msg.sender == engine), and modules are init'd with the real engine address (Deploy.s.sol:243-279 predictedConditionEngine).
- So for Mode P, `evaluate()` reflects state that can only be set true by functions the engine never invokes → predicate can never become true on-chain → Mode P reveals are dead unless state was pre-seeded at config time. (PaymentObligation defaults can't be observed; Oracle attestations can't be submitted; etc.)
- Not directly exploitable, but a correctness/availability hole: either the engine is missing forwarding entrypoints, or the modules' `onlyConditionEngine` gate is on the wrong principal (should be ORCHESTRATOR). Worth flagging because the fix direction (loosening the gate or adding engine forwarders) is security-sensitive and must not open an unauthenticated default-injection path.

## F-5 (LOW/MEDIUM) — Subject/Consent/Oracle modules treat signatureEnvelopeRef as a mere non-empty bytes ref; no on-chain signer authentication
- SubjectInitiatedModule._submitSubjectInitiated (src/modules/SubjectInitiatedModule.sol:105) only checks `signatureEnvelopeRef.length == 0`. ConsentGateModule._submitConsent (src/modules/ConsentGateModule.sol:137) same. No signature is verified; the "signature" is an off-chain reference. Currently shielded by F-4 (these paths are engine-gated and the engine doesn't call them), so impact is latent — but IF F-4 is fixed by adding orchestrator-reachable forwarders without also adding real signature verification, these become unauthenticated reveal triggers. Recommend binding actual EIP-712 / WebAuthn verification at these submit points before the F-4 forwarding gap is closed.

## F-6 (LOW) — GateRecipientPubkeyRegistry: caller-supplied effectiveBlock can be backdated for an existing commit (privileged)
- src/gate-recipient/GateRecipientPubkeyRegistry.sol:79-99. `entry.effectiveBlock` is caller-supplied and only defaulted-to-now when 0 (L91-93). A holder of GATE_PUBKEY_PUBLISHER_ROLE (Lit/G4/Conditional) or REGISTRY_ADMIN_ROLE (Drand) can publish a new pubkey with `effectiveBlock` set to a PAST block. getPubkeyAt(commitBlock) reverse-scans for `effectiveBlock <= blockNumber` (L116-118) and returns the most-recent matching entry — a backdated entry can shadow the legitimate as-of-commit key for an already-committed authorization, undermining the "at-commit-block reading discipline" that is supposed to prevent mid-commit key replacement. Privileged-role only (trust scope), so LOW, but the registry should reject `effectiveBlock < block.number` (or < the authorization's commit block) on publish.
