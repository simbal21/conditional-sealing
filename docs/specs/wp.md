## §A — System at a glance

Cealis is a data escrow system. Data goes in, gets encrypted into an age envelope, and sits off-chain in a vault — the chain holds only a commitment hash, not the data itself. Data-agnostic by construction: partners configure schemas per deployment, with no enumerated catalog of supported data types. Identity, source code, financial records, evidence, M&A documents, testamentary instructions, medical records — all instances of the same mechanism, distinguished by PDA configuration rather than by separate protocol paths (§F, §J item 12). Art. 9 GDPR special-category data (health, biometric, genetic, etc.) carries an additional PDA+ marker with explicit basis declaration per §F so the data-agnostic property doesn't elide regulatory awareness. At commit, the TEE generates a random DEK, encrypts the payload once, Shamir-splits the DEK into shares, and wraps each share to the relevant gate recipient. Release needs signatures from four gates working together: the chain itself (Base L1 with a configurable condition on-chain), Lit, either dcipher or drand, and a Cealis verification component. The chain's condition is whatever the partner configured for that deployment — a time window elapsing, a subject pressing the button, an oracle attesting to an external event — and only when that condition evaluates true on-chain do the gates produce signatures that authorize share release. The combiner reconstructs the DEK only after enough verified shares are recovered, so a missing fixed gate share means the threshold is not met and the plaintext stays sealed. Release needs all four fixed gates and those only appear after the chain-verified condition fires, so there is no path to plaintext that goes around the chain.

Launch custody posture is four gates from commit-zero: Chain + Lit V3 + G3 + G4. G3 is not a later add-on; each PDA chooses dcipher or drand and freezes that choice in h_commit. G4 Phase 1 vs Phase 2 is operational phasing for the Cealis verification component, not reduced launch scope — partner-facing commitments are Phase 2 per §N. The `age-plugin-cealis-v3` Shamir policy stays commit-versioned only so historical/dev-scaffold 3-gate profiles and partner-ready 4-gate profiles verify under their original commit metadata without ambiguity.

Cealis is a commercial protocol and Cealis charges for it. "Platform" here means one system serves many use cases through configuration — each partner's deployment is a set of parameters (PDA) sitting on top of platform-level choices Cealis sets (PDA+). This is a configurability claim, not an open-source claim and not a decentralization claim. If Cealis-the-company disappears the protocol still composes — rented commodity networks, Base L1, the age envelope format, the plugin — so data already committed can still be operated, and worst-case the protocol is open-sourceable.

The protocol is built open. Every surface has a defined forward-compat extension path — new use cases by schema configuration, new conditions through template composition or oracle onboarding or DSL extension, new gate policies through versioned Shamir share profiles, new ingestion modes through Mode A/B architecture preserved at design-time, new plugin and authority and oracle and DSL versions through on-chain registries with timelock governance and per-entry deprecation. Each commit pins its version surface via h_commit and commit_AAD, so old commits verify under their original references no matter how the platform evolves. Future features land by additive extension within governance, not by fork or migration. P25 carries this commitment.

Naming: V2 is the system version, V3 is the custody subsystem within V2, as of 2026-04-22. The *operation* Cealis performs has one canonical name across every use case — **conditional sealing** — meaning data sealed under a chain-verified condition with no party able to release outside it. The TPM-cryptography lineage of the term is intentional; Cealis extends sealing-under-policy from local platform state to chain-verified state, with no custodian. The *category* readers slot Cealis into stays plural by design (different audiences and use cases evoke different category descriptors); meta is fixed, category is selected per audience. As of 2026-04-30.

Configuration profiles compose on top of the V2 substrate without modifying it. Controlled-use access sessions ship as the first configuration profile under `commit_version = 0x0303` (S2-8 spec). Monetary value escrow ships as the second under `commit_version = 0x0304` (S2-9 spec pending authoring at post-data-pilot trigger), introducing the seed-payload class — a raw 32-byte ECDSA secret born inside a TEE-genesis ceremony, never existing as extractable plaintext outside the TEE, sealed under the same 4-gate AND substrate as data payloads, delivered to a PDA-pre-committed recipient at reveal time. The destination is a vanilla EOA; Cealis never appears in the wallet's on-chain signer set. Monetary A25.1 launch scope is DELIVER-only at fixed-destination on EVM; expansion to SWEEP / multi-chain / destination-resolution-at-reveal is deferred to A25.2 post-data-pilot per the spec's ship-deferred strategic posture. Both profiles are PDA+ governance sub-classifications applied through the same Cealis-internal configurator over the same primitives — they extend the surface, they do not modify the substrate.

This document is a snapshot. The longer you think about Cealis the more views surface — the primitives compose in ways that aren't all enumerated here and use cases keep growing without protocol change, so this is a current articulation and not an exhaustive one.

## §B — Primitives

The primitives are the system's commitments. The things the system promises to do. Composed together they produce the behavior Part 1 describes. V2-WP has 22 live primitives numbered P0 through P24. P12 is deleted, P16 is parked, P17 is not carried forward under V3 custody. P18 through P22 are V3-custody additions from the 2026-04-21 integration pass. P23 and P24 are condition-orchestration additions from the 2026-04-22 FSM pass. Numbered after the original V2 set rather than folded in, so the numbering carries the history.

### P0. Chain as orchestrator.

The system IS on-chain, calling off-chain components. Every primitive below is coordinated, gated, or verified through the chain. Remove the chain and nothing functions.

### P1. TEE-bounded commit with subject-assent.

Under the shipping ingestion mode, plaintext enters the Cealis TEE boundary via authenticated upload. Inside the boundary it gets encrypted into a DEK-sealed age envelope with gate-recipient stanzas. The plaintext is destroyed after processing. The subject signs σ_subject (WebAuthn passkey or EIP-712 wallet) over the digest of `h_commit_preimage + PDA_terms_digest`. σ_subject itself is stored off-chain in the vault; `keccak256(σ_subject)` is included in commit_AAD and therefore AEAD-bound into every decryption check — so drift at σ_subject is detectable at reveal even though the signature itself never anchors on-chain. Cross-partner-unlinkable by construction. When the alternative ingestion mode is enabled via PDA+ (P20), the subject's client constructs the envelope locally and Cealis never sees plaintext. Subject-assent applies identically in that path.

### P2. Off-chain sealed vault.

Ciphertext is stored off-chain after it leaves the TEE. Or after it leaves the subject's device under the alternative ingestion mode. Off-chain because on-chain permanence combined with future-crypto-break risk makes public-by-default storage strictly worse for long-retention data. The vault operator runs hardened infrastructure with access control. Vault code is closed-source by explicit commit — not a transparency reflex but a threat-model decision. §M has the reasoning.

### P3. Chain-gated custody — crypto-enforced via 4-gate AND-composition.

The DEK is generated randomly at commit and split into Shamir shares wrapped to four disjoint-operator gates. Chain (Cealis ConditionEngine smart contract on Base L1, event-visible). Lit V3 Chipotle (rented commodity TEE, σ_Lit). dcipher or drand per PDA (rented commodity threshold network, σ_G3). And the Cealis verification component (σ_G4, Phase 1 server signature or Phase 2 rented TEE attestation). Each signature is authorization evidence for that gate's share release. No 3-of-4 subset of fixed gates reconstructs the key in a 4-gate commit. Crypto-enforced, not procedural. Missing any fixed gate share means the Shamir threshold is not met and no decryption is possible. Full bypass requires compromising Lit + G3 + G4 operators at the same time.

### P4. Parameterizable gate condition via ConditionEngine.

> **See S2-8 (controlled-use spec) §6 for the tenth condition module (PresentedTokenCondition) and the composition-compatibility matrix with the nine existing modules.**

The on-chain condition that authorizes a ceremony — reveal or shred — is a single primitive: `AttestationGate`. It verifies that a signed attestation from a PDA-designated oracle passes a frozen Claim expression — a small DSL of comparison, boolean, path-access, and time-window operators. Each PDA declares condition logic per ceremony axis in one of two authoring modes. **Mode F** is a finite state machine orchestrating which AttestationGate the PDA is waiting on next; when the FSM reaches a terminal firing state, ConditionEngine emits `RevealAuthorized` (reveal axis) or `ShredAuthorized` (shred axis). Mode F is the reveal-side default because reveal conditions genuinely traverse stages. **Mode P** is a stateless Claim expression evaluated at ceremony attempt time; if the predicate evaluates true, the ceremony event emits directly. Mode P is the shred-side default because shred conditions reduce to a predicate over on-chain state for most PDA archetypes. Both modes share infrastructure — AttestationGate, OracleRegistry, Claim DSL, trust tiers, verification gate, 7-day timelock governance. Evaluation is permissionless-push in Mode F — authorized submitters advance the FSM by submitting attestations on-chain. Mode P evaluates in the ceremony transaction itself — no attestation push required for pure chain-state predicates. New condition domains extend the palette by onboarding new oracles to `OracleRegistry`, not by forking the system. Three trust tiers — chain-native, commodity-oracle, bespoke-oracle — are declared per PDA and carried in the artifact bundle. Full architecture in §F.

A tenth condition module, `PresentedTokenCondition`, ships as the controlled-use configuration profile under `commit_version = 0x0303` (S2-8). It is the chain-verifiable predicate "valid policy-scoped access token presented by a holder," consuming on-chain credential anchor state plus revocation state, and emitting `RevealAuthorized` for reads or `WriteAuthorized` for writes on PASS. The module composes with the existing nine modules under a normative composition-compatibility matrix (S2-8 §6.3); one composition is FORBIDDEN — `PresentedTokenCondition ∧ DeadManSwitch`, logically self-canceling because the first requires σ_holder proof-of-life and the second fires on holder absence. PresentedTokenCondition rides the same 4-gate AND substrate as the other nine modules; it is an additional gate condition, not a substitute for any gate. Controlled-use PDAs declare the module in their composition; non-controlled-use PDAs do not include it.

### P5. Optional independent side-channel disclosure.

At commit-time, inside the TEE, specific fields or proven predicates get emitted as cleartext or zero-knowledge proofs. The pipeline that does this runs independently from the sealed-core escrow pipeline. Off by default per partner, opt-in via PDA. Shares the DEK only for salt-derivation, never for decryption. Compatible with the shipping ingestion mode. Incompatible with the alternative device-encrypt ingestion mode when that mode is enabled. Plaintext never enters the Cealis TEE in that path, so TEE-side SD cannot run. Client-side SD with on-device ZK-proof generation is a future extension, out of current scope.

### P6. Two-level platform configurability.

Cealis configures the platform. Schema library, condition module set, retention policies, side-channel defaults, shred guardrails, ingestion-mode availability. That is the PDA+ level. Partners configure their deployment inside what the platform offers. Schema, G3 choice, phase, recipients, shred authority, challenge window, condition module selection. That is the PDA level. No enumerated catalog of use cases. New configurations happen by config, not by registry.

### P7. Schema-polymorphic payload.

The system makes zero assumptions about what data is being committed. Each PDA declares its own schema, AAD construction, and attestation requirements. No registry of "supported schemas." Data-agnostic by construction.

### P8. Multi-recipient delivery.

When a gate fires, the reconstructed payload is delivered to N recipients via N re-encryptions under N distinct recipient keys. The recipients list is Merkle-rooted in commit_AAD and is first-class in the artifact bundle. Per-recipient schema selectors support partial delivery. Single-recipient is length-1.

### P9. On-chain chain-of-custody (inherent).

Because the chain orchestrates the lifecycle, every event is inherently on-chain. Commit, disclose, gate-fire, challenge-open, challenge-resolve, release, deliver, shred. Not logged to chain. Happens on chain. The reveal artifact composes from on-chain events plus the decrypted payload. Nothing needs to be added after the fact for chain-of-custody to hold.

### P10. Tier-conditional challenge window.

Between the gate firing and the release executing, a configurable window may let an authorized party dispute. Availability is structural, not arbitrary: PDAs whose condition modules are all Tier A (chain-native — the chain itself is the oracle) default to zero-window because there is nothing to dispute with chain-native facts. PDAs with any Tier B/C condition module (third-party oracle attestations) require a non-zero window at or above the PDA+ archetype floor — Tier B/C is where oracle-honesty is the trust point and dispute is operationally meaningful. Resolution, where windows are non-zero, is on-chain and mechanically gated; timeouts and dismissals are deterministic and not operator-overrideable. The §F "PDA+ challenge-window guardrail" makes this configurator-enforced. Per-PDA defaults: KYC-lending and M&A on Tier A condition modules ship zero-window; the same archetypes on Tier B/C oracles ship 14-day with bond. Testament, archival, journalism, consumer ship zero-window across both tiers because their condition shape doesn't admit dispute. Resolution mechanics live in §F "Challenge window resolution"; that subsection applies only when the window is non-zero.

### P11. On-chain shred event with PDA-configured authority AND condition.

Shred is a contract state change on ShredRegistry that permanently blocks decryption-key issuance for a commitment. Triple block. ConditionEngine refuses to return `isConditionMet = true` post-shred, so no future reveal events. G4 reads ShredRegistry pre-attestation and refuses to sign σ_G4, which also halts in-flight reveals that have not yet completed σ assembly. The vault physically deletes the ciphertext after on-chain confirmation. Shred is gated on two axes: the PDA's shred **authority** (who can trigger — Subject by default, or Joint / Operator / Timelock / Disabled) AND the PDA's shred **condition** (under what on-chain state the attempt is valid). The condition uses the same ConditionEngine primitive as reveal (§B P4) in its Mode P authoring by default. Every PDA's shred condition includes a mandatory `NOT post_challenge_reveal_in_progress` clause at PDA+ layer — shred cannot fire once a reveal ceremony has passed its challenge window and gates have begun signing. This closes the destruction-axis tripwire mirror: no shred path bypasses the on-chain-verified predefined shred condition. Privacy-first framing survives — the subject retains shred right for PDAs whose conditions permit it — but the right is bounded by the condition layer so that a subject cannot unilaterally break enforcement mid-ceremony.

### P12 — DELETED under V3 (2026-04-21).

Original primitive: custodian-topology independence. V3 has no Cealis-operated committee, so the target this primitive addressed no longer exists. Substrate-independence is now carried by P19 (disjoint-operator composition). Full disposition in `_archive/wp-working-files/p16-p17-v3-alignment.md`.

### P13. No operator discretion over reveal content or outcome.

All administrative work (configure PDAs, manage onboarding, monitor) is dashboard + API-key. Normal SaaS admin. Reveal-content operations are cryptographically determined by chain events, gate signatures, and the subject's commitment data. The operator powers that do exist are bounded to halt-or-allow. G4 refusal is a crypto-enforced halt on legal, GDPR, or integrity grounds. Vault availability is Cealis running the vault and potentially going down or being legally compelled to stop serving. Neither alters what a valid reveal contains. Both only stop or allow the reveal from completing. No human decides whether a default is real. No human overrides a gate to grant or deny a specific party. No human redacts reveal output. Availability is a separate axis from correctness.

Tier-conditional resolution surface. Tier A PDAs realize this halt-or-allow bound without a post-commit human resolution surface — chain-native conditions are not disputable, and the system-locked claim holds at its strongest. Tier B/C PDAs route their dispute path through the ceremony resolver's halt-or-confirm-or-extend powers, which are bounded (cannot grant, cannot deny content, cannot override outcomes — only halt via G4 refusal or extend within PDA+ caps). The resolver does not introduce content-determining discretion; it introduces an Art. 22(3)(a) human-intervention endpoint where Tier B/C oracle-correctness is the trust boundary that legal frameworks ask for.

### P14. Optional Issuer role.

Three modes. Mode A is external issuer, flagship for KYC — an external issuer signs an attestation, and personKey derives from provider ID plus a per-subject nonce. Mode B is subject-self-sovereign — the subject is the issuer, and personKey derives from wallet plus a registration nonce. Mode C is asset, not person — depositor role, with the key deriving from content hash plus a depositor nonce.

### P15. Attestation-as-input.

Data going into a commit can be self-declared (trust reduces to the subject only) or externally attested (trust extends to the signer's audit trail). The attestation travels as part of the AAD. Per-PDA configuration decides which fields require which attestations. Extends chain-of-custody backwards to data provenance.

### P16 — PARKED FOR REDESIGN under V3 (2026-04-21).

Original primitive: auditable committee. Not a V2-WP primitive. The V3 custody architecture eliminated the committee this primitive described. A proposed G4-liveness-beacon redesign was dropped because client-side fail-closed on stale attestation already absorbs the threat without needing a separate primitive. Kept for potential future redesign. Full disposition in `_archive/wp-working-files/p16-p17-v3-alignment.md`.

### P17 — NOT CARRIED FORWARD under V3 (2026-04-21).

Original primitive: tamper-responsive custody. Not a V2-WP primitive. This was V2's Cealis-committee-defense descriptive package. V3 eliminated the target. The defense-in-depth it described is carried natively by P3 (4-gate AND-composition), P11 (shred cascade), and P19 (disjoint-operator composition). Full disposition in `_archive/wp-working-files/p16-p17-v3-alignment.md`.

### P18. Zero Cealis-operated custody.

For fixed-gate custody, Cealis holds no decryption-capable gate key material at any point in the commit, reveal, or storage lifecycle. No Cealis-operated staked custody network. No Cealis-held master key for fixed gates. No long-lived decryption key. PASSKEY_ACCOUNT rotation-log nuance is handled in §K item 9. The only Cealis-controlled signing capability is the G4 authority key, which signs σ_G4 and authorizes G4 share release. σ_G4 alone does not yield the DEK, and the G4 share alone is below threshold. Reveal also requires σ_Lit from Lit operators (disjoint from Cealis) and σ_G3 from dcipher or drand operators (disjoint from Cealis). Cealis cannot unilaterally decrypt any commitment.

### P19. Disjoint-operator composition.

The gate operators are selected so the cost of compromising the substrate scales multiplicatively, not additively. Three dimensions of disjointness. Organizationally disjoint: Lit Protocol operators, Randamu Threshold Association or League of Entropy, and Cealis are separate legal entities. Jurisdictionally disjoint: permissionless global pool for Lit, Swiss association or international public good for G3, Cealis entity for G4. TEE-vendor disjoint: spec-mandated cross-vendor between G2 Lit's serving TEE and G4 Phase 2 TEE. Compromise of any single organization yields no decryption capability. Compromise across organizations requires visible multi-party coordination, cross-jurisdictional legal processes, and multi-vendor hardware attacks at the same time.

### P20. Ingestion mode as platform-configuration (PDA+).

The platform is architected for two ingestion modes. Mode A (TEE-ingest) is the shipping default. Plaintext enters the Cealis TEE boundary, gets encrypted there, and the plaintext is destroyed after processing. Supports P5 SD. Simpler client. Mode B (device-encrypt) is architected as a PDA+ capability for later enable. When turned on, the subject's client generates the DEK locally and constructs the full age envelope with all gate-recipient stanzas on the device. Cealis never sees plaintext. Incompatible with P5 SD and with any TEE-plaintext-dependent feature. Requires a crypto-capable client SDK. Current deployment ships Mode A only. Mode B's architecture is preserved so it can be enabled through a PDA+ decision later without protocol rework. When enabled, partner or subject picks the mode via PDA or a user UI.

### P21. Crypto-aging operational discipline.

Cryptographic primitives age. Long-retention ciphertext has to outlive any single primitive. Three-part commitment. Hybrid post-quantum wrapping at commit (ML-KEM-768 plus X25519) — the attacker needs both to fall. Periodic stanza-addition re-key ceremony: as primitives weaken, gate operators participate in a ceremony that adds a new stanza to existing commitments under fresh primitives. The payload bytes are never touched. Only the key-wrapping gets re-done. And shred-first lifecycle bias: for PDAs where early shredding is compatible with the use case, shred as soon as possible to minimize the window during which ciphertext exists. Operational commitment, not a silver-bullet claim.

### P22. σ-as-authorization and share secrecy.

Under V3 custody's A1+Shamir construction, the gate signatures σ_Lit, σ_G3, and σ_G4 are authorization evidence, not DEK material. They verify that the relevant gate may release or decap its wrapped Shamir share for `(authorizationId, h_commit, block_hash)`. The secrecy boundary moves to the recovered shares, DEK, and plaintext. σ values are still delivered through authenticated channels before reveal completion to prevent replay and operational leakage, but observing σ values alone is insufficient to reconstruct the DEK. The recipient's combiner runs in a hardened execution context appropriate to the use case, recovers shares in memory, runs Shamir.combine at the configured threshold, decrypts once, and zeroizes shares and DEK after delivery.

### P23. Finite state machine as condition-orchestration primitive.

A PDA's condition is a finite state machine. States, transitions (each gated by a specific AttestationGate call), and terminal firing states. The FSM spec is public-by-design and lives on IPFS with multi-pin redundancy — Cealis primary pin, partner mirror, and an optional Filecoin deal funded from the PDA's retainer. The FSM spec hash is bound into `pda_root` and therefore into `h_commit`. Any post-commit swap of the FSM fails both the advance-time hash check at the FSMInterpreter and the reveal-time AEAD. Per-transition submitter authorization is declared at commit — default oracle-self-only, optionally widened to a PDA-declared relayer set — so permissionless-push triggering is bounded. Multi-stage conditions (dispute windows, cures, grace periods, M&A milestones) are native to the FSM. Boolean trees collapse into degenerate single-state FSMs. Reachability + gas-budget + schema-compatibility analysis at configurator-emission time, with dry-run simulation, before deploy.

### P24. Per-PDA pause as bounded bug-response primitive.

Distinct from shred. A PDA declares `pause_authority` — partner, joint subject-and-partner, or none. The authorized party calls `pausePDA(authId, reason, duration_max_90d)` to block FSM advancement without altering reveal content. On-chain visible. Auto-lifts after the duration or after an explicit unpause. Purpose: respond to discovered vulnerabilities in AttestationGate code, OracleRegistry entries, or oracle operator compromises before full shred becomes warranted. Does not alter reveal correctness — only halts, per P13's halt-or-allow bound on operator powers.

### P25. Open-architecture as protocol commitment.

Every protocol surface has a defined forward-compat extension path. New use cases land by configuration without protocol change (P7). New conditions land via three extensibility vectors — template composition, oracle onboarding, DSL extension — none of which fork the system (§F). Versioned Shamir share profiles support historical/dev-scaffold 3-gate profiles and partner-ready 4-gate commitments without silent reinterpretation (§B P3, §N). Mode A and Mode B ingestion are wired through plugin, stanza, and commit structure at architecture-time so Mode B can later enable through a PDA+ decision without protocol rework (§G). New plugin, authority, oracle, DSL, and QTSP versions land via on-chain registries (`PluginHashRegistry`, `G4AuthorityRegistry`, `OracleRegistry`, `DSLVersionRegistry`, `QTSPRegistry`) with timelock governance plus per-entry DeprecationFlag (§F, §M, §N). Backward compatibility is enforced cryptographically — each commit binds `plugin_version_digest`, `g4_authority_ref`, `dsl_version_ref`, `oracle_references_root`, `qtsp_provider_ref` (when `qes_subject_required = true`), `commit_version`, and the rest of the versioning surface via h_commit and commit_AAD, so old commits verify under their original references regardless of registry rotation. The `conditional_recipient` stanza format reserves variant tags for future delivery modes (`0x03 WALLET_EIP1271` today, additional modes later) without breaking variants 0x01 and 0x02. The `subject_authenticator_class` flag extends to support new authentication paths (e.g., a future Cealis-issued QTSP) by additive registry entry, not protocol rework. New PDA+ guardrails extend the configurator surface without breaking existing PDAs, because PDAs freeze their guardrail set at commit. The discipline this primitive commits to: future change lands by additive extension within governance, not by fork or migration. Surfaces without a defined extension path are not added — that is the discipline that makes this primitive load-bearing rather than promissory.

These are the commitments. §O names what the system cannot do, §P names what this document doesn't enumerate.

## §C — Commit ceremony

The commit ceremony starts with a subject or a partner initiating an upload to the G4 ingestion endpoint. The plaintext enters the Cealis TEE boundary, gets encrypted inside the boundary into an age envelope with gate-recipient stanzas, and the plaintext is destroyed after processing. The subject signs σ_subject over a digest of the commit preimage and the PDA terms. The envelope and σ_subject land in the off-chain vault. A commitment hash anchors the envelope on Base L1. That is the ceremony end-to-end. The rest of §C fills in the mechanics.

### Ingestion

Under the shipping ingestion mode, the subject's client (or the partner's backend in B2B deployments) uploads plaintext to the G4 ingestion endpoint. Before transmitting, the client fetches the endpoint attestation and verifies it. Phase 1 G4 attestation is an Ed25519 signature from a server running sealed code whose binary hash is registered on-chain under timelocked updates. Phase 2 G4 attestation is a DCAP quote from a rented TEE, verified on-chain. Once attestation verifies, plaintext transits to the endpoint over an authenticated channel and enters the TEE boundary. Inside the boundary the plaintext is encrypted and then destroyed.

The alternative ingestion mode (Mode B, device-encrypt) is architected as a PDA+ capability and not currently enabled (see §G). When enabled, the subject's client constructs the full envelope locally on the device and uploads ciphertext only; Cealis never sees plaintext in that path. §C describes the shipping mode.

### Endpoint attestation verified before transmit

Before plaintext leaves the client's authenticated channel, the client must fetch and verify the attestations that bind the commit to specific gate operators. This is not a best-effort pre-flight — it is the defense against adversary-chosen-TEE substitution and quote-replay attacks, and it happens client-side, not server-side. Four checks.

1. **Lit V3 assignment record** for this `authorizationId`. The assignment is published on-chain, block-scoped, so the client queries the assignment contract with `authorizationId` and reads back the identity of the specific TEE Lit governance assigned to serve this op. Reject if no assignment is posted.
2. **Per-op DCAP quote** from the assigned TEE. The quote's `user_data` field MUST bind `(authorizationId ‖ h_commit ‖ block_hash)` — any divergence means the quote is a replay from a different op and the commit is rejected.
3. **G3 committee pubkey** (dcipher registry or drand beacon chain) for the chosen G3. Cached per-epoch but verified fresh at commit.
4. **G4 authority attestation.** Phase 1: Ed25519 signature over `(binary_hash ‖ block_hash ‖ authorizationId ‖ h_commit ‖ timestamp)`, verified against `G4AuthorityRegistry` state at the commit's block. Phase 2: DCAP quote with the same binding in `user_data`, verified on-chain via Automata zkDCAP.

Any check fail aborts the commit before plaintext transits to the endpoint. The checks defend against (a) an adversary serving from a TEE not assigned by Lit governance, (b) a replayed quote from a different op, (c) G4 registry-race attacks where a key rotation lands mid-commit. Identical checks run at reveal (§D) against the commit's block, so tamper anywhere between commit and reveal is detectable. G4AuthorityRegistry governance and the zkDCAP verification chain are detailed in §N and §M; the client-side check runs against registry state at the transaction's block, not current state, which is how the system survives key rotations without breaking historical commits.

### Envelope construction

The age envelope is a header plus a payload. The header carries stanzas produced by the custom plugin `age-plugin-cealis-v3`. Three mandatory gate stanzas — Lit ACC, G3, G4 — plus zero or more `CONDITIONAL_RECIPIENT_*` stanzas (§F `conditional_recipients_policy`). A conditional_recipient is any non-partner party whose σ authorizes a Shamir share AND who receives plaintext at reveal. The testament heir is one instance of this primitive; the same shape covers DeadManSwitch-beneficiary, M&A-acquirer-counsel, medical-proxy, journalism-alternate-recipient, subject-alternate, subject-self. Pure delivery-only recipients (partners routing to institutional staff, audit inspectors) stay non-gating in `recipients[]` (§B P8), not as conditional_recipient stanzas.

```
stanza[0]: age-plugin-cealis-v3, recipient = LIT_ACC(id=authorizationId, chain_condition=..., block_hash_bound=true)
stanza[1]: age-plugin-cealis-v3, recipient = G3_ID(type=g3_choice, id=authorizationId OR drand_round)
stanza[2]: age-plugin-cealis-v3, recipient = G4_ATTESTATION_AUTHORITY(authority_pubkey_ref=CealisRootKey OR G4RegistryContract)
stanza[3..3+n-1] (optional, k-of-n policy): age-plugin-cealis-v3, recipient = CONDITIONAL_RECIPIENT_*(...)
```

Conditional_recipient stanzas are polymorphic by delivery mode. Variant tags `0x01` PASSKEY_ACCOUNT and `0x02` WALLET_EOA ship at V2 launch. Variant tag `0x03` WALLET_EIP1271 is reserved (architected, configurator rejects at V2; ships post-V2 with explicit §K carve-out that EIP-1271 is contract-trust consent rather than cryptographic consent).

```
CONDITIONAL_RECIPIENT_PASSKEY_ACCOUNT(
  variant_tag = 0x01,
  account_id,                   // Cealis-issued opaque identifier, bytes32
  initial_passkey_pubkey,       // P-256 uncompressed, bytes65, at commit time
  rotation_log_anchor,          // keccak snapshot of PasskeyRotationLog head at commit
  role_tag,                     // HEIR / BENEFICIARY / ACQUIRER_COUNSEL / MEDICAL_PROXY
                                // SUBJECT_ALTERNATE / JOURNALISM_RECIPIENT / SUBJECT_SELF
  delivery_hint                 // enum: IN_APP_NOTIFICATION / PASSIVE / EMAIL_NOTIFICATION_NO_CONTENT
)

CONDITIONAL_RECIPIENT_WALLET_EOA(
  variant_tag = 0x02,
  wallet_address,               // bytes20
  delivery_x25519_pubkey,       // recipient-provided X25519 pubkey for post-DEK delivery wrap
  delivery_url,                 // recipient's preferred delivery endpoint (HTTPS or IPFS gateway)
  role_tag
)
```

Every gate stanza carries a MAC under `TAG_STANZA_MAC_V3` over `(stanza_index, binding_tag, plugin_version_digest)`. Every conditional_recipient stanza carries an additional MAC under `TAG_CONDITIONAL_RECIPIENT_BINDING_V3` over `variant_tag ‖ stanza_index ‖ plugin_version_digest ‖ SCALE-length-prefixed(payload)`. Verifiers MUST validate the MAC before parsing payload fields — this closes cross-variant substitution (e.g., WALLET_EOA payload reinterpreted as PASSKEY_ACCOUNT via byte reinterpretation). The plugin MUST abort if any stanza MAC fails.

**PasskeyRotationLog — supporting sub-primitive for Mode 1 (PASSKEY_ACCOUNT).** Cealis accounts rotate passkeys over time (new device, authenticator replacement). The stanza commits `initial_passkey_pubkey` + `rotation_log_anchor`, not the current passkey — rotations authenticate themselves via the PRIOR passkey's WebAuthn assertion and land on the `PasskeyRotationLog` contract. The contract is an ABI standard, not a singleton; Cealis deploys a canonical instance on Base L1, recipients MAY use any ABI-compatible contract. At reveal, the verifier walks the rotation log from anchor forward, verifying each `entry[i].webauthn_assertion` under `entry[i-1].new_pubkey`, and verifies σ_conditional under the current head's `new_pubkey`. Cealis runs the infrastructure but cannot forge rotations — rotation forgery requires the prior passkey, which Cealis does not custody. Cealis can censor publication; recipients then self-publish via the permissionless contract. §K carries the resulting framing honestly: Cealis as rotation-log INFRASTRUCTURE, not rotation AUTHORITY.

The payload is ChaCha20-Poly1305 over the plaintext, with AAD set to the commit_AAD and a nonce derived from the DEK and h_commit:

```
payload = ChaCha20-Poly1305(
  key   = DEK,
  nonce = HKDF(DEK, TAG_AEAD_V3 ‖ h_commit)[:12],
  aad   = commit_AAD,
  pt    = plaintext
)
```

The DEK is generated fresh at commit inside the Cealis TEE boundary under the shipping ingestion mode. The payload is encrypted once under that DEK. The DEK is then split into `n = 3 + n_conditional` Shamir shares with threshold `k = 3 + k_conditional`; each share is wrapped into a stanza under the relevant gate-recipient pubkey. The reveal does not re-run a DEK derivation formula from signatures. It verifies signatures as authorizations, decaps the corresponding stanzas, and reconstructs the DEK from shares:

```
n = 3 + conditional_recipients_policy.n
k = 3 + conditional_recipients_policy.k
shares = Shamir.split(DEK_commit, n, k)

file_key = Shamir.combine({
  share_i recovered from a stanza whose σ_i verifies
}, threshold = k)
```

The ordered share policy is frozen in `conditional_recipients_policy_digest` and commit_AAD. Missing any fixed gate share, or fewer than k conditional-recipient shares where conditional recipients are configured, leaves `Shamir.combine` below threshold. No DEK is reconstructed and the reveal halts crypto-enforced. §D walks the reveal-side composition in full.

### Subject commitment

```
subject_commitment_v3 = keccak256(
  TAG_SUBJECT_V3
  ‖ person_key
  ‖ partner_namespace = keccak256(partner_id ‖ pda_id)
  ‖ registration_nonce
)
```

`person_key` comes from the PDA's Issuer mode (P14): provider ID plus a per-subject nonce for external issuance (Mode A), wallet plus a registration nonce for self-sovereign (Mode B), content hash plus a depositor nonce for asset-not-person (Mode C). `partner_namespace` is keyed to both the partner and the PDA, so the same subject across two partners or two PDAs produces different commitments — cross-partner linkability on the commitment layer is prevented by construction. `registration_nonce` is stored in vault metadata and destroyed on shred; without it, subjects whose `person_key` candidates are enumerable (for example, known national-ID ranges) could be matched to on-chain commitments by brute force.

### authorizationId

```
authorizationId = keccak256(
```

`epoch` is an onboarding timestamp bucket. `nonce` is client-generated random bytes, fresh per commit, which prevents deterministic-collision attacks where an attacker could force two commits to share an authorizationId.

V3 custody and the condition sub-platform (§F) require its internal structure to be enumerated, because tamper-detection on the condition logic extends beyond the commit envelope into the FSM spec, the DSL version, and the oracle references bound at commit-time.

```
pda_root = keccak256(

  ‖ shred_condition_spec_hash
```

**Field count:** 29 fields after the `TAG_PDA_ROOT_V3` domain-separator (16 original + 13 added 2026-04-25). Conditional-binding rule: every field MUST appear in the canonical preimage form (fixed-width byte concatenation per §1.3.1 of the S2-1 cryptography-spec) regardless of value; "not applicable" semantics use the zero-value of each field's type (e.g., `qtsp_provider_ref = 0x00…00` when `qes_subject_required = false` per §F). The 13 fields below the original 16 (`subject_authenticator_class` onward) were back-propagated 2026-04-25 from the §F legal-conform pass + the conditional-recipient.md / emergency-response.md committed designs — Rule 33 propagation pass triggered by S2-1 cryptography-spec drafting (worker-4 delta-audit Δ3 + worker-2 Q-W2-17 jointly surfaced the gap; Simon greenlit the structural enumeration patch 2026-04-25). Field-count correction (15→16 original / 28→29 total) + encoding clarification (SCALE → fixed-width byte concatenation, matching the §3 family in the S2-1 cryptography-spec) applied 2026-04-26 per worker-4 §3 cycle-1 review finding-1 + finding-3, BP-9 in the S2-1 back-propagation record.

`reveal_condition_mode` and `shred_condition_mode` are enum tags selecting Mode F (FSM) or Mode P (predicate) per §B P4. `reveal_condition_spec_hash` is the keccak of the canonicalized reveal-side spec stored publicly on IPFS (FSM JSON under Mode F, Claim expression AST under Mode P). `shred_condition_spec_hash` is the same for the shred-side spec; every PDA ships a shred condition because every PDA must commit to when destruction is valid. `oracle_references_root` is a Merkle root over the union of oracle IDs referenced by BOTH specs, each bound to its `OracleRegistry` entry at commit-time (so later rotation of an oracle pubkey in the registry does not retroactively alter what this PDA's conditions evaluate against). `dsl_version` identifies the Claim DSL interpreter contract version — the one deployed at commit-time, verified against `DSLVersionRegistry` at reveal-time the same way `PluginHashRegistry` gets verified. `wasm_predicate_hashes_root` is the Merkle root of any WASM predicate binaries embedded via the DSL's `custom_predicate` meta-operator across both specs (if unused, zeroed). `submitter_sets_root` is a Merkle root of the per-transition authorized-submitter lists for Mode F specs (Mode P has no submitter layer). `pause_authority_id` binds the P24 pause-authority mode. `ceremony_resolver_id` binds the on-chain address with halt-capability during challenge windows on both axes (§F Challenge window resolution). `eligible_challengers_reveal_root` and `eligible_challengers_shred_root` are Merkle roots over the per-axis declared challenger sets. `template_id` references the template selected from the PDA+ library.

Tamper-detection extends through two layers. At advance-time, the FSMInterpreter re-hashes the loaded FSM spec fetched from its multi-pin location and verifies the hash matches `fsm_hash` extracted from `pda_root` on-chain — any swap fails at the transition before any gate considers signing. At reveal-time, the age-plugin-cealis-v3 combiner verifies the AEAD bind of `commit_AAD` (which carries `pda_root` via `pda_root_digest`), so a tampered configuration path is caught redundantly.

### h_commit

```
h_commit = keccak256(
  TAG_COMMIT_V3
  ‖ authorizationId
  ‖ pda_root
  ‖ schema_digest
  ‖ ciphertext_digest
  ‖ aad_digest
  ‖ composite_identity_digest
  ‖ endpoint_attestation_digest
  ‖ retention_window
  ‖ shred_authority_id
  ‖ recipients_root
  ‖ reveal_challenge_window
  ‖ shred_challenge_window
  ‖ g3_choice
  ‖ phase
  ‖ commit_version
)
```

`h_commit` anchors the authorization ID, the PDA configuration root, the schema, the ciphertext, the AAD, the composite-identity specification, the endpoint attestation that was valid at commit, the retention window, the shred authority, the recipients root, the reveal challenge window, the shred challenge window, the G3 choice, the G4 phase, and the commit version. The PDA configuration root (`pda_root`) itself anchors the reveal-side and shred-side condition specs plus the ceremony resolver and eligible-challenger sets. Any change to any of those inputs produces a different `h_commit`, so a tamper anywhere in the envelope or the configuration is detectable against the chain-anchored hash.

Each input pins a specific surface. `authorizationId` binds to the derivation above. `pda_root` binds to the PDA configuration root (whose own internal structure is enumerated below). `schema_digest` pins the keccak of the PDA's declared schema. **`ciphertext_digest = keccak256(age_envelope)`** pins the exact bytes of the age envelope — at reveal, the recipient's combiner recomputes the keccak of the loaded envelope and rejects if it drifts from `ciphertext_digest` (§D). `aad_digest` pins commit_AAD. `composite_identity_digest` pins the keccak of `(Lit ACC spec ‖ G3 identity spec ‖ conditional_recipients_root)`, where `conditional_recipients_root` is the Merkle root over the ordered conditional_recipient stanza set (zero-valued when `n = 0`). `endpoint_attestation_digest` pins the attestation valid at the commit's block — recipients verify against registry state at this block, not current state. `retention_window`, `shred_authority_id`, `recipients_root`, `reveal_challenge_window`, `shred_challenge_window`, `g3_choice`, `phase`, and `commit_version` are PDA configuration values frozen at commit. Fifteen inputs, each load-bearing; the ciphertext_digest binding in particular closes the "was this the envelope the chain saw" question that otherwise weakens the tamper-detection story, and the split of `reveal_challenge_window` / `shred_challenge_window` lets the two ceremony axes carry independent windows while sharing the resolution protocol (§F).

### σ_subject and commit_AAD

The subject signs σ_subject via WebAuthn passkey (P-256) or EIP-712 wallet over the digest of `h_commit_preimage + PDA_terms_digest`. σ_subject is stored in the vault only. Its keccak digest goes into commit_AAD (and therefore into the AEAD check on every decryption), but σ_subject itself is never anchored on-chain. This keeps the subject's passkey public key off-chain — passkey pubkeys are identity-bearing, and on-chain anchoring would create cross-partner linkability on the subject layer.

`commit_AAD` is a SCALE-encoded structure carrying the fields the AEAD binding needs at reveal. Authorization and PDA references: authorizationId, pda_root, schema_digest, partner_id, commit_version. Binding digests: subject_commitment_v3, sigma_subject_digest, recipients_root, p15_attestations_root, endpoint_attestation_digest, conditional_recipients_policy_digest. Configuration choices and version references: g3_choice, phase, composite_identity_type, conditional_recipients_stanza_count, plugin_version_digest, g4_authority_ref, dsl_version_ref, oracle_references_root. Three fields worth naming specifically. `plugin_version_digest` binds the commit to the specific `age-plugin-cealis-v3` build registered on-chain at commit time — the recipient MUST match this at reveal. `g4_authority_ref` binds the commit to a specific G4 authority key registration, which supports key rotation without breaking old commits — recipients verify σ_G4 against the registry state at the commit's block, not against current state. `conditional_recipients_policy_digest = keccak256(SCALE(conditional_recipients_policy))` binds the full conditional_recipients policy — n, k, the ordered recipient stanza set, their delivery modes and bindings — into the AEAD check. The subject-side verifier (next subsection) independently verifies this digest against the σ_subject'd payload so a server-side post-display tampering with the stanza set is detectable before σ_subject is produced. `heir_wrap_present` from the earlier testament-specific wording is retired; its role is subsumed by `conditional_recipients_stanza_count > 0`.

### Subject-side verifier

Before σ_subject is produced, the `age-plugin-cealis-v3` client runs a mandatory pre-σ verification sub-flow on the subject's device. The plugin loads the SCALE-encoded PDA payload, parses it, and displays in human-readable form: every conditional_recipient (role_tag, delivery_mode, binding summary with sensitive fields masked where appropriate, delivery hint), the condition module's reveal and shred logic, the PDA+ policy surface visible to the subject, and the derivation of `h_commit` from the displayed inputs. The plugin requires per-recipient explicit confirmation from the subject (one checkbox per conditional_recipient) and an overall confirmation on the condition spec digest. The plugin refuses to invoke WebAuthn/EIP-712 signing for σ_subject without all confirmations.

This is a sub-flow of the existing plugin, not a separate binary — the plugin's reproducible-build hash is already registered in `PluginHashRegistry` per this section's `plugin_version_digest` check. A compromised configurator server that shows the subject one policy in the UI while serializing a different policy into the SCALE payload is detected at the plugin's parse-and-display step: the subject sees the parsed payload, not the UI the server rendered. G4 reproduces the same check at reveal time — G4 parses `commit_AAD.conditional_recipients_policy_digest` and verifies it matches `keccak256(SCALE(conditional_recipients_policy))` of the stanza set in the envelope; any mismatch → σ_G4 refused. The cryptographic binding between subject inspection and reveal-time verification survives server compromise.

## §D — Reveal ceremony

The reveal starts when the PDA's ConditionEngine module evaluates true on-chain. G1 emits `RevealAuthorized(authorizationId, h_commit, block#, ts)`. Base L1 finality lands after ~13 minutes. If the PDA configured a challenge window, that window runs next. Once finality and the challenge window have both cleared, the three signing gates produce their signatures — G2 (Lit V3 serving TEE), G3 (dcipher or drand per PDA), G4 (the Cealis verification component). The recipient, or a recipient-operated combiner they delegate to, gathers the σ values, verifies them as authorizations against the commit's registry state, decaps the corresponding wrapped Shamir shares, reconstructs the DEK with Shamir.combine at threshold `3 + k_conditional`, decrypts the age envelope under the commit_AAD, and delivers the payload to the recipients listed in the commit. The rest of §D fills in the mechanics.

### Condition fires, gates respond

**G1 Chain.** The PDA's condition module evaluates `isConditionMet(authorizationId)` true on-chain. G1 emits `RevealAuthorized(authorizationId, h_commit, block#, ts)`. Downstream gates wait for Base L1 finality (~13 min) before acting. Reorg tolerance is zero — the reveal is a one-way gate.

**G2 Lit V3.** A single serving TEE, randomly assigned per-request from Lit's ~30-operator pool, reads chain state and verifies the ACC (access control condition) against the event. The TEE signs σ_Lit as a BLS signature over `authorizationId ‖ h_commit ‖ block_hash`. It returns σ_Lit together with a per-op DCAP quote from the specific TEE that served the request. The assignment record — which TEE was selected for which authorizationId — is published on-chain block-scoped, so recipients can verify later that the serving TEE was the one Lit's governance assigned.

**G3 dcipher or drand.** Per PDA. dcipher: the Randamu Threshold Association committee reads chain state and produces a threshold BLS signature σ_G3 over `authorizationId ‖ h_commit ‖ block_hash`. drand: at the target round specified in the commit, the League of Entropy publishes the round signature, which serves as σ_G3. Both paths yield a single σ_G3 verifiable against public registry pubkeys.

**G4 Cealis verification component.** G4 reads chain state via its own independent RPC. It checks ConditionEngine state AND ShredRegistry state for the h_commit. If both check out — condition met, not shredded — G4 signs σ_G4. Phase 1: an Ed25519 signature over `authorizationId ‖ h_commit ‖ block_hash ‖ binary_hash ‖ timestamp`. Phase 2: a DCAP quote whose user_data binds the same fields. If either check fails — chain state mismatched, commit shredded, legal compulsion standing, Art. 17 erasure received, integrity failure detected — G4 does not sign σ_G4. It emits `G4RefusalRegistry.refuse(authorizationId, reason_code, proof)` on-chain instead.

The three signing gates (G2, G3, G4) fire independently. The recipient's combiner can gather their signatures in any order.

Under the controlled-use configuration profile (S2-8, `commit_version = 0x0303`), G4 Phase 2 extends its TEE scope to cover three additional ceremonies beyond reveal attestation: a write-validation gate that runs five normative checks on every controlled-use write (schema conformance, scope conformance, history immutability, policy-allow, token-authorizes-this-exact-write) and produces a `write_attest` signature; a Stream 2 audit-event signing path that signs metadata-only events under a separate key `K_G4_audit_stream2`; and a read-event ingest path that counter-signs client-produced σ_holder event tuples without ever decrypting plaintext content for read operations. Both new G4 keys (`K_G4_write_attest`, `K_G4_audit_stream2`) anchor in the existing `G4AuthorityRegistry`. Cross-vendor disjoint discipline extends to Stream 2 — every audit event is co-signed by one of G2 Lit V3, G3 dcipher, or G3 drand per PDA selection, so a single G4 TEE-key compromise cannot retroactively forge audit history. The asymmetric ingest scope is normative: writes must pass through the TEE for schema and history enforcement, but reads decrypt client-side and G4's role at read time is audit signing only, never content mediation.

### Shamir composition at reveal

The DEK is reconstructed from Shamir shares. The three fixed gates each authorize one share. A variable-length vector of σ_conditional values authorizes the conditional-recipient shares required by the k-of-n policy frozen at commit:

```
file_key = Shamir.combine({
  share_Lit,
  share_G3,
  share_G4,
  share_conditional[0..k_conditional-1]
}, threshold = 3 + k_conditional)
```

The commit wraps each Shamir share under the gate or conditional-recipient stanza. The reveal verifies each σ as authorization for that stanza before admitting the recovered share. Missing any fixed gate share, or missing enough σ_conditional/share pairs to satisfy the configured conditional threshold, leaves Shamir.combine below threshold. No DEK is reconstructed; AEAD decryption never starts.

### Per-mode σ_conditional signing and delivery

At reveal, each conditional_recipient produces σ_conditional per their stanza's delivery mode. Verifiers MUST validate stanza MACs before parsing payloads and MUST enforce the minimum σ_conditional length per mode listed below.

**Mode 1 — PASSKEY_ACCOUNT (variant 0x01).** Recipient signs into Cealis and produces a WebAuthn assertion over:
```
keccak256(TAG_REVEAL_CHALLENGE_V3 ‖ authorizationId ‖ h_commit
         ‖ account_id ‖ role_tag ‖ stanza_index ‖ reveal_block_hash)
```
σ_conditional = the WebAuthn assertion bytes (P-256; minimum 64 bytes). Verifier resolves `account_id` → `current_passkey_pubkey` by walking the `PasskeyRotationLog` from `rotation_log_anchor` forward, verifying each entry's `webauthn_assertion` under the previous entry's `new_pubkey`; the head entry's `new_pubkey` verifies σ_conditional. Plaintext delivery lands in the recipient's Cealis dashboard.

**Mode 2 — WALLET_EOA (variant 0x02).** Recipient signs EIP-712 (secp256k1, exactly 65 bytes) over:
```
keccak256(TAG_REVEAL_CHALLENGE_V3 ‖ authorizationId ‖ h_commit
         ‖ wallet_address ‖ role_tag ‖ stanza_index ‖ reveal_block_hash)
```
Verifier recovers the signer from (digest, σ); must equal `wallet_address` in stanza. Plaintext delivery: per-recipient payload wrapped to `delivery_x25519_pubkey` via age X25519 recipient stanza, POSTed to `delivery_url` or pulled via IPFS per recipient's URL convention.

**Mode 3 — WALLET_EIP1271 (variant 0x03).** Reserved at V2 launch; configurator rejects selection. When enabled post-V2: σ_conditional = opaque bytes (contract-defined). Verifier computes current `extcodehash(contract_address)`, compares against `contract_bytecode_hash_at_commit` in stanza, and issues `eth_call` to `contract_address.isValidSignature(digest, σ)` expecting the EIP-1271 magic value. Minimum σ length: 1 byte (empty σ explicitly rejected). If `reject_on_bytecode_change = true` AND the extcodehash has changed since commit → σ rejected; otherwise, STALE_BYTECODE warning emitted, verifier continues.

Before reconstructing file_key the combiner runs a set of verification checks. The stored ciphertext's keccak must match `ciphertext_digest` from h_commit. The `age-plugin-cealis-v3` binary loaded into the combiner must match `plugin_version_digest` from commit_AAD, verified against the PluginHashRegistry state at the commit's block. The Lit per-op DCAP quote must bind `(authorizationId, h_commit, block_hash)`, and the serving TEE's identity must match the on-chain Lit assignment record. σ_G4 must verify against G4AuthorityRegistry state at the commit's block, not current state. Current ShredRegistry state for h_commit must be unshredded. Every gate-stanza MAC must verify under `TAG_STANZA_MAC_V3`; every conditional_recipient stanza MAC must verify under `TAG_CONDITIONAL_RECIPIENT_BINDING_V3` BEFORE the stanza payload is parsed (cross-variant substitution defense — see §C stanza format). `commit_AAD.conditional_recipients_policy_digest` must match `keccak256(SCALE(parsed_conditional_recipients_policy))` of the stanza set in the loaded envelope. For each required σ_conditional/share pair, the per-mode verification in the preceding subsection applies. Any check fail and the plugin aborts before reconstructing file_key.

**Registry deprecation state at the authorization block, not current.** The five Cealis-governed V3 registries (PluginHashRegistry, G4AuthorityRegistry, DSLVersionRegistry, OracleRegistry, QTSPRegistry) carry DeprecationFlags on individual entries (§F, §N). At reveal, the combiner reads deprecation state AT THE `RevealAuthorized` block — the block when G1 emitted the authorization for this ceremony — not at current state, for any entry pinned in the commit's AAD or referenced by the commit's condition evaluation. A deprecation set AFTER `RevealAuthorized` does not halt the in-flight reveal: the gate-signing window is an architectural halt-impossibility window (same discipline as shred — §B P11, §E). A deprecation set BEFORE `RevealAuthorized` blocks the authorization path and the reveal never enters the combiner check list. G4 performs the same deprecation check pre-σ-sign and refuses σ_G4 with the matching reason code (`0x06` plugin_deprecated / `0x07` authority_deprecated / `0x08` dsl_deprecated / `0x09` oracle_deprecated, §N; QTSPRegistry deprecation fails the QES signature-chain path as `0x04` integrity_fail unless a dedicated QTSP code is later added) for pending commits pinned to deprecated entries.

Once file_key is derived, the combiner runs ChaCha20-Poly1305 decrypt over the payload with AAD = commit_AAD. If the AEAD tag verifies, the plaintext is produced. If any field bound in commit_AAD has drifted, the AEAD check fails and no plaintext is produced.

### σ_G4 — crypto-enforced halt

σ_G4 is authorization for the G4 Shamir share. Its absence does not merely flag an issue for the combiner to check — it prevents release of a fixed-gate share, and the Shamir threshold cannot be met.

G4 can refuse to sign σ_G4. The reasons are bounded by a closed on-chain reason-code enum: legal compulsion (`0x01`), GDPR Art. 17 erasure received mid-flight (`0x02`), Art. 18 freeze (`0x03`), integrity failure detected in G4's own state (`0x04`), chain-state mismatch (`0x05`), plugin deprecated (`0x06`), authority deprecated (`0x07`), DSL deprecated (`0x08`), oracle deprecated (`0x09`). Codes `0x06`-`0x09` carry class-wide deprecation semantics for pending commits pinned to deprecated registry entries (§N class-wide deprecation), distinct from per-commit `0x04 integrity_fail`. Refusal emits an on-chain signal. The reveal halts before Shamir reconstruction because the G4 share is absent. No combiner honesty or source-review discipline is load-bearing — the key cannot be computed.

Halt, not alter. σ_G4 is either produced or it is not. Its contents are a pure function of chain state and commit data — no operator chooses what σ_G4 contains, only whether to produce it. The same applies to σ_Lit and σ_G3. Each is either signed or not, and its signed content is determined by the event and the commit, not by the operator. Reveal output is a function of chain events and commit data, not a decision.

Mid-reveal shred follows from the same structure. If a shred fires after σ_Lit and σ_G3 have been gathered but before σ_G4, G4 reads the ShredRegistry pre-attestation, refuses, and the in-flight reveal cannot complete. §E covers the shred trigger and ShredRegistry state machine.

### σ authorization and share secrecy at reveal

The three signatures σ_Lit, σ_G3, σ_G4 are authorization evidence under the Shamir construction. Observing all three σ values is not enough to derive the DEK; the combiner also needs the wrapped shares to decap successfully and meet threshold.

This determines how reveal material is handled. σ values, recovered shares, and DEK are delivered or held only inside authenticated in-memory paths. Shares and DEK are never published on-chain, never logged, and never cached in intermediate systems. The combiner runs in a hardened execution context appropriate to the use case. The reveal is a one-shot exposure inside that context — once the plaintext is produced and delivered to the recipient, the shares and DEK do not persist.

### Combiner location

The combiner runs on the recipient side or at a combiner service the recipient delegates to that does not retain σ values, recovered Shamir shares, the reconstructed DEK, or plaintext beyond the in-process reveal window. It is not a Cealis-operated component. A Cealis-operated combiner would sit at the convergence point where verified σ values authorize per-stanza share admission, recovered shares reconstruct file_key, the DEK decrypts the payload, and plaintext crosses to the recipient delivery layer — collapsing the disjoint-operator composition at the last step. The danger is that convergence, not σ receipt by itself: σ values are authorization evidence and MAY appear in the post-reveal `RevealArtifactBundle` per S2-1 §14.3 + §6.6, but recovered shares, decap material, the DEK, and plaintext are the actual secrets and MUST NOT cross the combiner's process boundary. Cealis operating the combiner would put a single party at that convergence point even though σ publication on its own is benign.

### Challenge window

Per-PDA configurable. When configured, the challenge window opens after G1 emits `RevealAuthorized` and L1 finality has landed; G2, G3, and G4 do not fire until the window closes. The window is mechanically gated. The deadline is a block number or timestamp on-chain, dismissals are deterministic, the window is not operator-overrideable. Resolution during the window is on-chain: if a dispute resolves the condition invalid, the authorization is marked resolved-invalid and the gates do not sign. If the window expires without a valid challenge, the gates proceed. Per-PDA duration defaults are in §F "PDA template defaults." The full resolution protocol — eligible challengers, evidence format, ceremony resolver role, bond mechanics, dismissal criteria, Art. 22(3) interlock — is specified in §F "Challenge window resolution."

### Delivery to recipients

The recipients list is committed at commit-time, Merkle-rooted in commit_AAD (§C). Each recipient is bound to a schema selector that determines which fields of the payload they receive. After deriving the DEK and decrypting the payload, the combiner filters the payload per recipient selector and produces one delivery per recipient.

The combiner produces one JCS-canonicalized RevealArtifactBundle (RFC 8785) per recipient — the multi-recipient delivery (§B P8) emits N bundles for N recipients rather than a single shared bundle. Each per-recipient bundle carries the authorization identifiers (authorizationId, h_commit), that recipient's plaintext filtered per schema selector, σ_subject from the vault, the three gate signatures (σ_Lit with its per-op Lit DCAP quote, σ_G3 with its g3_choice marker, σ_G4 with its phase marker), the chain proofs (commit transaction hash, the RevealAuthorized event, the block number, the finalized-at timestamp, the challenge-window-expired-at timestamp, the ShredRegistry state at reveal), the registry-deprecation snapshots at the RevealAuthorized block for all five V3 registries (PluginHashRegistry, G4AuthorityRegistry, DSLVersionRegistry, OracleRegistry, QTSPRegistry), and a canonical-form marker. Every signature in the bundle is verifiable against the public operator registries — the Lit assignment registry, the dcipher or drand pubkeys, the G4AuthorityRegistry, the QTSPRegistry when σ_subject is QES — so any third party with access to those registries can independently verify that the reveal was produced by the operators registered for this commit under the chain conditions that actually held. The `p16_audit_refs` field present in earlier drafts is dropped (P16 PARKED disposition per §B). Per-recipient bundle issuance preserves the per-recipient schema-selector privacy boundary already established at commit-time.

## §E — Shred ceremony

Shred is a gated transaction with multi-layer consequences. Before the ShredRegistry state change can execute, the shred attempt passes two independent gates: the PDA's declared shred **authority** (who can trigger — Subject by default, or Joint / Operator / Timelock / Disabled per PDA configuration) AND the PDA's declared shred **condition** (under what on-chain state the attempt is valid — a Mode P predicate or Mode F FSM per §B P4 / §F). When both gates clear, ConditionEngine emits `ShredAuthorized(authorizationId, h_commit, block#, ts)` and the authorized party submits the shred transaction. The state change activates a triple block. G1 stops returning true on future reveal checks. G4 stops signing σ_G4 for future reveals. The vault physically deletes the ciphertext. After these three blocks land the commitment is forward-unrevealable and past-ciphertext-free. ShredRegistry state is binary per authorizationId — shredded or unshredded — and the transition from unshredded to shredded is permanent.

The destruction-axis mirror of the universal tripwire: no shred path bypasses the on-chain-verified predefined shred condition. What made the reveal side system-locked (predefined condition + no operator override) now also holds on the destruction side.

### Triple block

**G1 block.** ConditionEngine reads ShredRegistry state on every `isConditionMet(authorizationId)` call. If the commitment is shredded, `isConditionMet` returns false regardless of whether the underlying condition would otherwise evaluate true. No future `RevealAuthorized` event gets emitted for this commitment.

**G4 block.** G4 reads ShredRegistry state before signing σ_G4. If the commitment is shredded, G4 refuses and does not sign. Because σ_G4 authorizes the G4 Shamir share (see §D), missing σ_G4 means the DEK threshold cannot be reached. In-flight reveals that already gathered σ_Lit and σ_G3 still halt before Shamir reconstruction — the share set is incomplete, the key is not computable, and the plaintext stays sealed. The recipient's pre-decrypt verification (§D) also checks ShredRegistry state at reveal, so a shred firing after σ_G4 is signed but before decryption completes terminates the reveal on the recipient side — defense-in-depth on top of the crypto-halt.

**Vault block.** The vault listens for on-chain shred confirmation. On confirmation, it physically removes the ciphertext bytes from storage — not a soft-delete, not a tombstone, actual byte removal. §M covers the storage-layer discipline that makes this deletion meaningful, including what gets preserved for chain-of-custody and why physical deletion is load-bearing for forward-secrecy.

### Mandatory shred-condition guardrail — no shred mid-reveal

Every PDA's shred condition includes a mandatory `NOT post_challenge_reveal_in_progress` clause enforced at PDA+ layer. The configurator rejects any shred condition spec whose evaluation could return true while a reveal has passed its challenge window and gates have begun signing. Operationally, this means shred can fire in exactly two windows:

- **Before `RevealAuthorized` emits, or during the reveal challenge window.** Subject, Joint, Operator, or Timelock authority-holder signs shred; condition evaluates true because no gates have signed yet; shred cascades. Subject retains full shred capability up through the challenge window. For use cases that want subject-halt capability on reveals (e.g., journalism-style source protection — subject detects adversarial reveal during the challenge window and shreds), this window is where it happens.
- **After reveal has finalized.** Plaintext has been delivered; the reveal is closed. Shred cleans up ciphertext going forward. The ceremony can't be reversed, but exposure on future-crypto-break is reduced.

Between these windows — specifically, from the moment challenge-window-expired-without-resolver-halt triggers gate signing until the combiner has assembled the required σ authorizations and Shamir shares — shred is condition-blocked at the protocol layer. No PDA can configure its way around this; the guardrail is PDA+, not PDA-configurable. The race between shred and share assembly that would otherwise let a malicious combiner reconstruct DEK post-shred-authorized cannot occur because the shred transaction itself cannot land in that window. The tripwire is crypto-enforced at the condition layer, not dependent on cooperative combiner behavior.

This reframes what "σ_G4 refuses on shredded h_commit" defends against. The G4-share authorization property remains load-bearing for `RevealAuthorized` events whose conditions subsequently become invalid — shred is one such cause, but so are Art. 17 propagation, integrity-failure detection, and legal retention orders (§N G4 refusal scope). The ceremony-guardrail is what prevents shred from racing gate-signing; σ_G4 refusal is what enforces G4-side halt for all other refusal causes.

### PDA-parametric shred authority and shred condition

Shred is configured on two PDA axes. The **authority** axis fixes who can submit the shred transaction; the **condition** axis fixes under what on-chain state the submission is valid. Both are frozen at commit time — authority via `shred_authority_id`, condition via `shred_condition_mode` + `shred_condition_spec_hash` in `pda_root` (§C). A PDA cannot change either retroactively. §F handles the configurability discipline for both axes.

**Authority modes** (five, from PDA+ allowed set):

- **Subject.** Default for most PDAs. The subject signs and submits the shred transaction. Shred is the subject's right unless the PDA's authority mode or condition blocks it.
- **Joint.** Subject and partner both required to sign. Use cases: M&A escrow where neither party should be able to unilaterally destroy the committed data.
- **Operator.** Cealis submits. Legal basis is PDA-defined and narrow. §F handles the legal-basis criteria and which use cases admit Operator-mode shred.
- **Timelock.** Scheduled automatic shred at a specific block number or timestamp. Fires without a signer — the contract executes shred when the timelock elapses AND the shred condition evaluates true. Use cases: retention windows that must close at a known time, evidence with a mandated destruction date.
- **Disabled.** No shred path for this PDA. Used when shred would compromise the use case, e.g., long-retention evidence archival where evidentiary value depends on non-erasure. Implemented as `shred_condition = false` plus authority set to a sentinel no-signer value.

**Condition defaults** (per PDA archetype — expressed as Mode P Claim predicates; full table in §F "PDA template defaults"):

- **KYC-lending / Enforcement.** Tiered retention logic: `NOT obligation_active OR past_active_exposure_window OR past_statutory_evidence_window` AND mandatory guardrail.
- **M&A escrow.** `(deal_closed_attestation OR deal_terminated_attestation OR post_retention_window_elapsed) AND NOT active_litigation_attested` AND mandatory guardrail.
- **Evidence.** `custodian_consent_attested OR post_custody_release_window_elapsed` AND mandatory guardrail.
- **Archival.** `retention_window_elapsed OR subject_and_operator_joint_attest` (or authority=Disabled for permanent-archive PDAs) AND mandatory guardrail.
- **Testament.** `NOT trigger_attestation_received AND NOT reveal_in_progress` — Mode P by default, Mode F opt-in for heartbeat-grace state semantics. AND mandatory guardrail.
- **Journalism / source protection.** `NOT post_challenge_reveal_in_progress` — relies on challenge window for subject halt capability, not on unconditional shred. AND mandatory guardrail.
- **Medical.** `NOT active_treatment_claim AND NOT reveal_in_progress` AND mandatory guardrail.
- **Consumer.** `NOT post_challenge_reveal_in_progress` — subject-initiated any time outside the narrow gate-signing window. AND mandatory guardrail.

Every condition carries the mandatory `NOT post_challenge_reveal_in_progress` clause as a PDA+ guardrail the configurator enforces. Partners compose additional PDA-level predicates on top within PDA+ allowed ranges but cannot remove the guardrail.

### proof_shred — public verification token

When both gates clear and ShredRegistry state-changes, ConditionEngine produces `proof_shred` — a public verification signature over `(authorizationId, h_commit, block#, ts, shred_reason_code)` that third parties use to verify the shred event without chain queries. `proof_shred` is not a reveal authorization and does not derive a key. The shred-side token uses proof_-naming to avoid overloading σ, which this WP reserves for reveal-side authorization signatures.

### Shred-first lifecycle bias

For PDAs where early shred is compatible with the use case, shred happens as soon as the PDA-defined retention window closes — not later. Enforcement-completed KYC commitments are a typical case: once the enforcement event has resolved and the retention window has elapsed, there is no further system use for the ciphertext. Shredding at that point minimizes the window during which ciphertext exists, which reduces exposure to future crypto-breaks (§M). This is a policy bias the mechanism supports, not a mechanism of §E. §M has the full crypto-aging treatment.



## §F — Configurability (PDA+ and PDA)

Two levels of configurability sit on top of the primitives. Cealis configures the platform — the set of configuration surfaces, the allowed values on each surface, the governance around changes to those surfaces. That is PDA+. Partners configure their deployment by picking values from those surfaces within the allowed ranges. That is PDA. The configurator that produces a PDA is Cealis-internal, not partner self-serve. The system is data-agnostic by construction: no enumerated catalog of supported schemas, no pre-approved list of use cases. The platform provides surfaces; partners pick values. Configuration profiles extend the PDA+ surface for specific operational shapes — `ControlledUseAccessPolicy` (S2-8, `commit_version = 0x0303`) and `MonetaryEscrowPolicy` (S2-9 pending authoring, `commit_version = 0x0304`) are the first two, each adding governance sub-classifications and per-profile field families within the same Cealis-internal configurator discipline.

### PDA+ — what Cealis sets platform-wide

- **Schema library.** The set of template schemas partners can start from. Convenience templates, not a closed catalog of what can be committed.
- **Condition primitive set.** ConditionEngine ships one on-chain primitive — `AttestationGate` — plus an FSM interpreter (§B P23), an OracleRegistry, an OracleSchemaRegistry, and a DSL interpreter. PDA+ controls which oracles are registered, which FSM templates are whitelisted, which DSL version is current, and which WASM predicate binaries are permissible. A PDA picks from the whitelisted set; PDA+ controls the set. Expanded in "Condition detection" below.
- **Retention policies.** Platform-wide minimum and maximum retention windows. Per-PDA retention must sit inside these bounds.
- **Side-channel (SD) defaults.** Whether SD is available at all for a given schema, and what the default is when available. SD is off by default per PDA; PDA+ decides which schemas can turn it on (§H).
- **Shred guardrails.** Two dimensions at PDA+ layer. (1) Which of the five shred-authority modes (Subject, Joint, Operator, Timelock, Disabled — §E) are allowed for each PDA type; partner picks from the allowed set. (2) Which shred-condition templates are allowed for each PDA type; partner picks from the allowed set of Mode P predicates and Mode F specs. **Mandatory guardrail:** every shred condition (regardless of mode or template) must AND-compose with `NOT post_challenge_reveal_in_progress`. The configurator rejects any shred spec that could evaluate true once a reveal has passed its challenge window and gates have begun signing. This PDA+ invariant closes the destruction-axis tripwire mirror (§B P11, §E).
- **Challenge-window guardrail (Tier-A-zero / Tier-B-C-required).** Mandatory PDA+ rule binding `reveal_challenge_window` and `shred_challenge_window` to the trust tier of the PDA's condition modules (§F "Trust tiers"). When all of the PDA's reveal-side condition modules are Tier A (chain-native), `reveal_challenge_window` MUST be zero — there is nothing to dispute with chain-native facts, and the zero-window is structural, not optional. When any reveal-side condition module is Tier B/C, `reveal_challenge_window` MUST be ≥ the PDA+ archetype floor (14 days for KYC-lending / M&A / enforcement; 7 days for evidence; archetype-specific elsewhere). Same rule applies independently to `shred_challenge_window` against the shred-side condition tier. The configurator rejects mismatched configurations (Tier A with non-zero window, or Tier B/C with sub-floor window). Tier mix at the PDA — different reveal vs shred tiers, or composed multi-tier conditions — resolves to "any-Tier-B/C in the relevant axis triggers required-window." Closes the operational gap where Tier A PDAs were inheriting non-zero windows from archetype defaults that don't apply to chain-native facts, and ensures Tier B/C PDAs cannot silently configure zero-window where dispute is the legal-effect intervention path.
- **Ingestion-mode availability.** Mode A (TEE-ingest) is the shipping default. Mode B (device-encrypt) is architected as a PDA+ capability for later enable (§G). Current PDA+ state: Mode A only.
- **G4AuthorityRegistry governance.** 7-day timelock on G4 authority key updates. Updates propagate through the timelock before taking effect.
- **G4 phase guardrail.** Legal-effect PDA types — KYC-lending, M&A, evidence, medical — cannot be committed under Phase 1 G4. The configurator rejects any such PDA whose `g4_phase` is set to Phase 1. This is defense-in-depth against dev-environment leakage and emergency-fallback misuse of the Phase 1 scaffold. Consumer / archival / testament / journalism PDA types may technically commit under Phase 1 if ever used as dev-scaffold data, but partner-facing PDAs of any type commit under Phase 2 per the pilot anchor (§N). Phase choice is frozen at commit via `g4_phase` in `h_commit` (§C).
- **σ_subject authenticator class guardrail.** Mandatory PDA+ rule binding σ_subject's authenticator class to the PDA's `legal_effect_expected` flag. For PDAs with `legal_effect_expected = true` (KYC-lending, M&A, evidence, medical), σ_subject MUST be either (a) a WebAuthn assertion produced by a **platform authenticator** — not a synced passkey — accompanied by a WebAuthn attestation statement that the configurator validates at commit time and the combiner re-validates at reveal, OR (b) a QES from a registered QTSP per the QTSP integration capability below (`qes_subject_required = true` plus `qtsp_provider_id`). Synced-passkey σ_subject is rejected for legal-effect PDAs because synced credentials cross device boundaries opaquely — they do not meet the §371a-evidentiary or eIDAS AES standards that the legal-effect framing depends on (eIDAS Art. 26 AES requires the signature to be "uniquely linked" and "under the sole control" of the signatory; synced passkeys multi-device blur both). For non-legal-effect PDAs (consumer / journalism / archival / testament), synced passkey is permitted because the evidentiary bar is lower and consumer ergonomics dominate. Frozen at commit via `subject_authenticator_class` in `pda_root`. The configurator surfaces the choice at PDA configuration time; defaults follow archetype.
- **Art. 9 special-category guardrail.** Mandatory PDA+ rule for PDAs handling Art. 9(1) GDPR special-category data — health, biometric (when used for unique identification), genetic, racial / ethnic origin, religious / philosophical beliefs, political opinions, trade-union membership, sex life or sexual orientation. The PDA must declare `art_9_scoped = true` (default false) AND reference an `art_9_basis_id` from the closed enum: `(2)(a) explicit_consent` · `(2)(b) employment_law` · `(2)(c) vital_interests` · `(2)(d) legitimate_activities` · `(2)(e) public_data` · `(2)(f) legal_claims` · `(2)(g) substantial_public_interest` · `(2)(h) preventive_or_occupational_medicine` · `(2)(i) public_health` · `(2)(j) archiving_research_statistics`. The configurator rejects Art. 9-scoped PDAs without a declared basis. When `art_9_basis_id = (2)(a) explicit_consent`, the configurator additionally enforces that the σ_subject ceremony presents an Art. 9-grade explicit-consent flow distinct from the standard PDA terms — separate plain-language explanation of the special-category data class, separate consent confirmation in the §C subject-side verifier, and explicit acknowledgment that this consent is freely given, specific, informed, and unambiguous (Art. 7 + Art. 9(2)(a) standard). Schema-polymorphic property is preserved — `art_9_scoped` is metadata about the PDA's processing posture, not a registry of which schemas qualify. Frozen at commit in `pda_root` via `art_9_scoped` and `art_9_basis_id`.
- **Refusal-reason encryption guardrail.** Mandatory PDA+ default `refusal_reason_encrypted_default = {0x02, 0x03}` for all PDAs — G4RefusalRegistry emissions for reason `0x02` (Art. 17 erasure received) and `0x03` (Art. 18 restriction) default to encrypted-reason mode (see §N "Privacy mode"). The on-chain event emits only `RefusalSignal(authorizationId, "refused")` plus an `encrypted_reason_blob` decryptable to the partner's resolver flow + regulators with subpoena authority. PDA+ allows per-PDA opt-out (public-reason mode for these codes) only with explicit subject acknowledgment recorded at σ_subject signing AND partner attestation that public-reason mode does not adversely affect the subject's rights — both surfaced at configurator time. The default rests on Art. 5(1)(a) transparency and Art. 5(1)(c) data minimization: codes that record subject-exercise of fundamental rights are themselves personal data and should not be public-by-default. Other reason codes default to public-reason mode unchanged.
- **Art. 22 safeguard guardrail.** Legal-effect PDA types (KYC-lending, M&A, evidence, medical — same set as G4 phase guardrail) must carry `legal_effect_expected = true` in the PDA+ template. The configurator enforces a tier-conditional rule, because the legal posture differs by where the trust boundary sits.
    - **Tier A condition modules (chain-native).** Art. 22(3) safeguards are satisfied via pre-commit informed consent (σ_subject over PDA_terms_digest naming the predefined trigger; the subject-side verifier in §C presents the full PDA before signing) AND oracle-correctness held by the chain itself (no off-chain oracle to dispute) AND PDA-permitted crypto-shred (§E, where the PDA's shred authority allows). Ceremony resolver halt-capability remains AVAILABLE on Tier A PDAs but is NOT load-bearing for Art. 22(3)(a) — Recital 71 + EDPB Guidelines 05/2020 §IV.B do not require post-commit human intervention when pre-commit consent is genuinely informed and the trigger is mathematically deterministic on chain-native state. `reveal_challenge_window` is forced zero by the §F "Challenge-window guardrail" above.
    - **Tier B/C condition modules (third-party oracle attestation).** The configurator enforces all of (1) non-zero `reveal_challenge_window` ≥ PDA+ archetype floor (forced by the challenge-window guardrail), (2) `ceremony_resolver` of type `human_endpoint` or `judicial_address` (bot-only and multisig-with-single-human-signer are rejected — they don't meet EDPB §IV.B "active not token gesture" standard), (3) subject included in `eligible_challengers_reveal`, (4) `minimum_shred_latency` above the archetype floor below, AND (5) `cealis_class_wide_halt_opt_out = false` (forced; the configurator rejects opt-out on legal-effect PDAs because the same halt is the Art. 22(3)(a) endpoint — see Change 2). Legal basis for automation across both tiers is Art. 22(2)(a) contract-performance; for Tier B/C specifically, (3)(c) contest is the challenge window, (3)(b) express view is `counter_attestation_ref`, (3)(a) meaningful-safeguard surface is G4 refusal via `0x03` Art. 18 plus ceremony resolver halt-capability (§N G4 refusal scope).
    - **`conditional_recipient_present = true` (any tier).** When set, the beneficiary's σ_conditional additionally serves as cryptographic human-consent — Art. 22(3)(a) is satisfied at the crypto layer because decryption mathematically requires the beneficiary's signature. This is independent of and additional to the tier-specific safeguards above.
- **`minimum_shred_latency` per archetype.** Floor on the elapsed time between `ShredAuthorized` emission and shred cascade. Enforces a window in which G4 refusal, ceremony resolver halt, and Art. 17 timing can operate. KYC-lending / M&A / evidence / medical — 14 days (matches §F enforcement shred-challenge default). Testament — zero permitted (shred fires post-conditional-recipient ceremony + grace window). Archival — zero permitted (σ_non_recoverable subject consent). Consumer / journalism — subject choice at onboarding, default zero. Frozen at commit via `minimum_shred_latency` in `pda_root`.
- **`applicable_jurisdiction` semantics.** Scalar by default — each commit tagged with one jurisdiction, retention-order and legal-compel refusals scope to that jurisdiction. Joint-escrow archetypes (M&A multi-jurisdiction, joint-custody) opt in to set-valued `applicable_jurisdiction` with k-of-n court-attestation composition on the shred condition — any cooperating jurisdiction's attestation satisfies the predicate. PDA+ hardcodes scalar for single-subject archetypes; set-valued requires explicit archetype opt-in and partner acknowledgment of the cross-jurisdictional DoS surface (any one court can freeze shred on the whole commit). Frozen at commit.
- **PluginHashRegistry.** Canonical `age-plugin-cealis-v3` binary hash registry. 7-day TimelockController on ADDITIONS; `DeprecationFlag` on individual entries (see `CealisSecurityMultisig` below). Recipients verify plugin_version_digest (§C) against registry state at the commit's block, not current state.
- **DSLVersionRegistry.** Claim DSL interpreter contract version registry. Same governance shape as PluginHashRegistry: 7-day on additions, DeprecationFlag on individual entries. Bound into commit via `dsl_version` in `pda_root` (§C).
- **OracleRegistry.** Oracle source pubkey registry. Same governance shape. Bound into commit via `oracle_references_root` in `pda_root` (§C).
- **QTSPRegistry.** Optional capability registry of approved EU Qualified Trust Service Providers whose Qualified Electronic Signatures are accepted as σ_subject when a PDA elects `qes_subject_required = true` (per the PDA-side surface below). Same governance shape as OracleRegistry — 7-day TimelockController on additions, per-entry DeprecationFlag governed by CealisSecurityMultisig with 24h expedited delay for canonical-in-use entries, 72h auto-clear absent on-chain disclosure. Each entry is `(qtsp_provider_id → {qtsp_root_pubkey, qtsp_jurisdiction, qtsp_eIDAS_status_url, metadata})`. Cealis bootstraps the registry with at least one EU QTSP at V2 launch (D-Trust or Bundesdruckerei as initial candidates), pending counsel + commercial evaluation; partners can request additional QTSPs through the standard PDA+ governance process. A Cealis-issued QTSP option may be added in the future as a separate registry entry. Bound into commits that elect QES via `qtsp_provider_ref` in `pda_root` (§C); recipients verify σ_subject's QTSP signature chain against `QTSPRegistry` state at the commit's block, not current state, per the standard backward-compat pattern.
- **`qes_subject_required` capability.** PDA+ surface controlling whether a PDA may elect QES-grade σ_subject. When the PDA's `qes_subject_required = true` (PDA-side surface), the configurator validates the QTSP signature chain at commit time against `QTSPRegistry` state, and the combiner re-validates at reveal. When false, σ_subject follows the standard WebAuthn / EIP-712 path subject to the §F "σ_subject authenticator class guardrail." Switching `qes_subject_required` on a PDA after commit is impossible — the choice is frozen via `subject_authenticator_class` in `pda_root`.
- **CealisSecurityMultisig (emergency-response governance).** A 2-of-3 on-chain contract that can set `DeprecationFlag` on individual entries across the five Cealis-governed V3 registries (PluginHashRegistry, G4AuthorityRegistry, DSLVersionRegistry, OracleRegistry, QTSPRegistry). Non-canonical entries deprecate instantly (0h); the current canonical-in-use entry in each registry adds a 24h expedited TimelockController delay (partner/recipient observation window). Flag clearing requires 7-day TimelockController. Re-deprecation of the same entry within 30 days of an auto-clear requires TimelockController. Every deprecation binds `(reason_code, disclosure_cid, disclosure_commit_hash)`; absent on-chain `publishDisclosure(bytes)` with `keccak256(bytes) == disclosure_commit_hash` within 72h, the flag auto-clears. Member rotation runs through TimelockController (7-day). Composed with `EmergencyGovernance` (3-of-3 circuit breaker, distinct from Security Multisig) that can suspend the Security Multisig's deprecation authority for up to 7 days if compromise is suspected. Full threat-model treatment in §M; on-chain reason codes 0x06-0x09 that G4 emits on deprecated-entry refusal in §N, with QTSPRegistry deprecation currently failing the QES signature-chain path as `0x04` integrity_fail. Used as the backstop for PDA-level `cealis_class_wide_halt_opt_out` opt-outs (see PDA surface below).
- **Governance Phase 1 / Phase 2 distinction.** At V2 launch the `CealisSecurityMultisig` and `EmergencyGovernance` contracts exist but all seats are Cealis-held pending external-advisor seating — this is Governance Phase 1. §K discipline requires both the launch form and the target form to be surfaced in public framing, not just the target. Phase 2 transition (external advisor seated, distinct security domain) completes before first paying partner OR within 90 days of V2 launch, whichever is sooner; if neither trigger fires, new partner onboarding halts until Phase 2 is achieved. The two-phase shape mirrors the existing G4 Phase 1 → Phase 2 discipline in §N and rides the same business event (partner signing ≈ funding arriving). §M threat model names the Phase 1 compromise surface explicitly.
- **conditional_recipients_policy — PDA+ bounds.** Cealis platform-wide bounds on `n` (total), `k` (threshold), and per-role-tag delivery-mode availability. V2 launch surface: role_tag ∈ {HEIR, BENEFICIARY, ACQUIRER_COUNSEL, MEDICAL_PROXY, SUBJECT_ALTERNATE, JOURNALISM_RECIPIENT, SUBJECT_SELF}; delivery_mode ∈ {PASSKEY_ACCOUNT, WALLET_EOA} (shipping) + WALLET_EIP1271 variant tag `0x03` reserved (configurator rejects selection at V2; enables post-V2 via PDA+ update). PDA+ enforces: role_tag = SUBJECT_SELF requires delivery_mode = PASSKEY_ACCOUNT AND condition_module.subject_liveness_required_at_fire = true.
- **2-phase ingestion.** G4 ingestion endpoint runs a 2-phase intake. Phase 1: client POSTs `(plugin_hash, authority_key, dsl_version, oracle_refs, metadata)`; G4 checks deprecation state across referenced entries, returns a 5-minute `ingestion_token` or a refusal. Phase 2: client uploads plaintext keyed to the token; G4 re-verifies before accepting plaintext; any deprecation landed between phases → plaintext discarded without processing. Closes the narrow window where plaintext could transit into TEE before the deprecation check runs.

### PDA — what the partner configures per deployment

- **Schema.** Selected from the PDA+ schema library or derived from a platform-provided template.
- **Condition.** An FSM composed by the Cealis-internal configurator from a template in the PDA+ whitelisted library, parameterized with PDA-specific values: which oracle(s) the transitions reference, timing windows, recipient-specific thresholds, trust tier. Partner does not author raw FSM JSON (v1). The FSM reaches a terminal firing state to emit `RevealAuthorized`. Full detail under "Condition detection" below.

- **Pause authority.** Per P24, selected from `{partner, joint, none}`. Bounded bug-response halt mechanism, distinct from shred.
- **G3 choice.** dcipher or drand for the G3 gate (§C, §D).
- **Recipients.** List of allowed recipient pubkeys, Merkle-rooted in commit_AAD at commit time (§C). Per-recipient schema selectors for partial delivery (§D).
- **Shred authority mode.** Selected from the PDA+ allowed set for this PDA type. Frozen at commit via `shred_authority_id` in h_commit (§C, §E).
- **Shred condition.** Mode P (predicate) or Mode F (FSM) per §B P4. Selected from the PDA+ allowed set of shred-condition templates for this PDA type, parameterized with PDA-specific values (retention windows, oracle references, archetype-specific operands). Mandatory `NOT post_challenge_reveal_in_progress` guardrail AND-composed by the configurator — partner cannot remove it. Frozen at commit via `shred_condition_mode` + `shred_condition_spec_hash` in `pda_root` (§C, §E).
- **Shred challenge window.** Duration of an optional challenge window between `ShredAuthorized` emission and the shred cascade executing, or zero for no window. Parallel to the reveal challenge window (§D). Uses the same ceremony resolver and the same resolution protocol (§F "Challenge window resolution").
- **Challenge window.** Duration per PDA, or zero for no window. Placement and mechanical gating are in §D (reveal-side). Resolution mechanics — eligible challengers, evidence format, bond mechanics, dismissal criteria — live under "Challenge window resolution" below.
- **Ceremony resolver.** On-chain address (EOA, multi-sig, or contract) with halt-capability during challenge windows for both reveal and shred axes. Default at pilot: Cealis-internal operator. Frozen at commit via `pda_root`; rotation applies only to future PDAs. Full powers under "Challenge window resolution" below.
- **Eligible challengers per axis.** Per-PDA declaration of which parties may open a challenge, separately for reveal-axis and shred-axis. Selected from `{subject, partner, named_observers[], recipients}`. Must contain at least one challenger role if the corresponding window duration is non-zero. Full detail under "Challenge window resolution" below.
- **Retention window.** Within PDA+ min/max.
- **Issuer mode.** A (external issuer — KYC-flagship), B (subject-self-sovereign), C (asset-not-person). Per §B P14.
- **`subject_authenticator_class`.** One of `{platform_authenticator, qtsp_qes, synced_passkey}`. Selected per the PDA+ "σ_subject authenticator class guardrail" — synced passkey is rejected for `legal_effect_expected = true` PDAs; platform authenticator is the standard for legal-effect PDAs without QTSP integration; `qtsp_qes` is selected when `qes_subject_required = true` and the partner has elected QTSP-issued σ_subject for §371a-class admissibility. Frozen at commit in `pda_root`.
- **`qes_subject_required` and `qtsp_provider_ref`.** Partner-electable capability for PDAs requiring §371a-class admissibility. When `qes_subject_required = true`, the partner additionally selects `qtsp_provider_ref` from the PDA+ `QTSPRegistry` (D-Trust, Bundesdruckerei, any registered EU QTSP, future Cealis-issued QTSP). σ_subject must then be a Qualified Electronic Signature issued under that QTSP's signature chain — the configurator validates this at commit time and the combiner re-validates at reveal against `QTSPRegistry` state at the commit's block. Partners not electing this capability default to platform-authenticator WebAuthn σ_subject (legal-effect PDAs) or synced passkey (non-legal-effect PDAs) per the §F "σ_subject authenticator class guardrail," and admissibility scopes to §286 ZPO free-evaluation rather than §371a Anscheinsbeweis.
- **`art_9_scoped` and `art_9_basis_id`.** Required on PDAs whose data class falls under Art. 9(1) GDPR (health, biometric used for unique identification, genetic, etc.). `art_9_scoped` is a bool default false; when true, `art_9_basis_id` must reference one of the ten Art. 9(2) bases per the PDA+ "Art. 9 special-category guardrail." Configurator rejects Art. 9-scoped PDAs without a declared basis. When `art_9_basis_id = (2)(a) explicit_consent`, the σ_subject ceremony additionally surfaces an Art. 9-grade plain-language consent flow in the §C subject-side verifier, separate from the standard PDA-terms confirmation. Frozen at commit in `pda_root`. Defaults follow archetype: medical = true with `(2)(h) preventive_or_occupational_medicine` as default basis (partner can override with another (2) basis); biometric-KYC = true with `(2)(g) substantial_public_interest` or `(2)(a) explicit_consent` per partner choice; testament-with-health-data = true with `(2)(a) explicit_consent`.
- **Attestation requirements.** Per field: self-declared or externally attested. Per §B P15.
- **`conditional_recipients_policy`.** `{n, k, recipients: [{delivery_mode, binding, role_tag, delivery_hint?}, …], recipient_stanza_merkle_root}`. When `n = 0`, no conditional_recipient stanzas are included and the Shamir threshold is the fixed-gate threshold. When `n ≥ 1`, `1 ≤ k ≤ n` is the conditional-recipient threshold and every recipient composes a CONDITIONAL_RECIPIENT_* stanza in §C. Configurator validation: every recipient's delivery_mode must be in the PDA+ shipping set (Mode 1 / Mode 2 at V2). For `role_tag = SUBJECT_SELF`, `delivery_mode = PASSKEY_ACCOUNT` is required AND the condition module's `subject_liveness_required_at_fire` flag must be true. For `role_tag = HEIR` under a testament condition module, `subject_liveness_required_at_fire = false` is expected (subject is not alive at fire), which forecloses SUBJECT_SELF on the same PDA.
- **`conditional_recipients_updatable`.** Bool. When true, the subject (while alive) can issue a PDA update signed by a fresh σ_subject over a new `conditional_recipients_policy`; updates land on-chain with their own block anchor and the stanza set at reveal is the CURRENT version at fire time. When false, the PDA is immutable after commit on this axis — recipients removed by an update cannot produce valid σ_conditional. Configurator rule: condition modules with `fire_time_ttl_estimate > 5 years` default this to true AND additionally require the subject's `emergency_response_bricking_acknowledgment` if the subject elects immutability for a long-TTL PDA.
- **`emergency_response_bricking_acknowledgment`.** Bool. Required on long-TTL PDAs (`fire_time_ttl_estimate > 5 years`) with `conditional_recipients_updatable = false` OR `pda_updatable = false`. Names the trade-off at config time: if a registry entry referenced by this PDA is later deprecated as a security response and the subject cannot migrate, the commit becomes unrevealable until the deprecation clears or the registry entry is replaced through TimelockController. Acknowledged deliberately by the subject, not defaulted.
- **`time_critical_pda_flag`.** Bool. When true, the configurator forces `pda_updatable = true` and surfaces the affirmative-harm trade-off at config time: "Cealis's emergency-response halt capability can halt this reveal during a deprecation window even if your specific PDA's condition is unaffected by the vulnerability." Meant for testament-with-legal-deadline, oracle-triggered-with-short-expiry, and similar PDAs where a halt that coincides with a hard external deadline causes real harm independent of the vulnerability.
- **`cealis_class_wide_halt_opt_out`.** Bool. When true, this PDA's commits are exempt from Cealis class-wide deprecation halts — the plugin/G4 verify the commit's opt-out status and continue under the original registry entries even if deprecated. Partners electing opt-out accept vulnerability-window risk in exchange for uninterrupted enforcement. AAD-bound and visible to recipients at reveal. Meant for institutional-partner contracts where the commercial model requires no-halt guarantees (commercial-lending without Art. 22 footprint, regulated-finance enforcement-timing contracts). G4 emits reason code `0x0A opt_out_active` on any would-be deprecation refusal. **Configurator forbids `true` on legal-effect PDAs** (`legal_effect_expected = true` — KYC-lending, M&A, evidence, medical) because the same class-wide halt is the Art. 22(3)(a) human-intervention surface for Tier B/C legal-effect PDAs, and erodes pre-commit-consent + chain-trigger determinism backstop for Tier A legal-effect PDAs. Available exclusively on non-legal-effect PDAs (commercial-lending without Art. 22 footprint, time-locked archival, journalism, consumer) where no Art. 22 surface needs preservation.

### Condition detection

ConditionEngine is one on-chain primitive plus an orchestration layer. The primitive is `AttestationGate` — it verifies a signed attestation from a PDA-designated oracle passes a frozen Claim expression. The orchestration layer is a per-PDA finite state machine (§B P23) that determines which AttestationGate call the PDA is currently waiting on. All condition detection reduces to this: an oracle signs an attestation, a submitter pushes it on-chain, AttestationGate verifies signature plus Claim, the FSM advances, and at a terminal firing state `RevealAuthorized` emits.

**AttestationGate.** Single on-chain contract. Verifies `(oracle_signer_pubkey, attestation_payload, signature, claim_expr) → bool`. Never reverts on evaluation failure — failed signature, failed Claim, wrong oracle for current transition all resolve to `false` without advancing the FSM. The oracle's signer pubkey is bound into the PDA's `oracle_references_root` at commit-time via `pda_root` (§C), so later rotation of a pubkey in OracleRegistry does not retroactively change what this PDA evaluates against.

**Claim DSL v1.** Twelve operators — `==`, `!=`, `<`, `<=`, `>`, `>=`, `AND`, `OR`, `NOT`, `IN`, `path_access` (JSON field extraction against attestation payload), `within_time_window`. AST-based, deterministic, bounded evaluation gas per invocation. Each Claim expression in an FSM transition (Mode F) or as a standalone predicate (Mode P, shred-side default) is a single parseable expression; the DSL is compiled at configurator-emission time and verified at deploy-time against the referenced oracle's published schema (§F oracle discipline). A thirteenth meta-operator — `custom_predicate(wasm_hash, input_binding)` — is reserved for v2 and embeds a deterministic WASM predicate for conditions the twelve operators cannot express; binary stored alongside spec, hash bound in `pda_root`.

**State-read operands (shred-condition support).** Mode P predicates on the shred side frequently need to read cross-primitive chain state. Six dedicated state-read operands extend DSL v1 for shred-condition authoring: `obligation_state(partner_contract, authId)` → enum `{None, Active, Repaid, Defaulted, Resolved}`; `reveal_progress_state(authId)` → enum `{None, Authorized, ChallengeOpen, GatesSigning, Finalized, Timeout}`; `challenge_state(authId, axis)` → enum `{None, Open, Resolved, Expired}`; `dispute_state(authId)` → enum `{None, Open, ResolvedInvalid, ResolvedConfirmed}`; `retention_window_elapsed(authId)` → bool (reads `retention_window` frozen in h_commit + current timestamp); `g4_refusal_standing(authId)` → bool (reads G4RefusalRegistry). The composite `post_challenge_reveal_in_progress(authId)` is a derived predicate — `reveal_progress_state(authId) IN {GatesSigning, Finalized}` — used as the mandatory shred guardrail. These operands evaluate deterministically against chain state at the ceremony-transaction block; gas is bounded by the cross-contract read count.

**FSMInterpreter.** Per-PDA FSM advancement. On each `advanceFSM(authId, attestation)` call: load the referenced FSM spec from its multi-pin location, verify the spec's hash matches `fsm_hash` in `pda_root`, look up the current transition for `(authId, current_state)`, verify the attestation's oracle matches the transition's oracle reference, verify the submitter is authorized for this transition (per the declared submitter set), verify the Claim passes, and advance `current_state` to the transition's target. On-chain state per active PDA is minimal — `(current_state, fsm_hash, cursor_data)` at ~64 bytes. When the transition target is a terminal firing state, emit `RevealAuthorized(authorizationId, h_commit, block#, ts)` — identical event signature to pre-V3, so §D's gate flow is unchanged.

**Triggering.** Permissionless-push, bounded by submitter-set. Each transition's `submitter_set` is declared at commit-time and bound into `pda_root` via `submitter_sets_root`. Default is oracle-self-only — only the registered oracle's pubkey may submit its own attestation. Partners may widen to a declared relayer set (e.g., "partner's own keeper plus this third-party indexer"), trading some DoS surface for keeper flexibility. The effect at scale: Cealis operates zero watcher infrastructure. Oracles push attestations when events occur; time-triggers route through TimeOracle services (Chainlink Automation as default, with per-PDA override). Firing is autonomous — from the perspective of any partner, subject, or recipient, nothing manual happens.

**FSM spec storage.** Public-by-design. JSON canonicalized, stored on IPFS with Cealis primary pinning plus partner mirror plus optional Filecoin deal funded from the PDA's retainer. Hash in `h_commit` provides tamper detection; multi-pin provides availability. Metadata leakage is accepted as a bounded trade-off — the on-chain `advanceFSM` event sequence already publicly reveals a PDA's state graph structure, so publishing the spec itself is information-theoretically equivalent. Recipients receive a copy at commit-time alongside the standard PDA onboarding materials.

**Three extensibility vectors.** New condition types extend the palette through one of three paths, in priority order. First, template composition — the configurator composes existing internally reviewed primitives (oracle references + Claim expressions + FSM patterns) into a new template; days of work, Cealis-internal operations, no engineering. Second, oracle onboarding — an operator sets up signing infrastructure plus an attestation schema plus canonical example sets, Cealis onboards via OracleRegistry; days of work, zero Cealis engineering. Third, DSL extension — a new DSL operator or new WASM predicate support; rare, requires a DSL interpreter contract deployment under 7-day timelock, engineering-bounded. In practice the first two absorb more than 95% of novel condition requests.

**Trust tiers.** Three tiers are declared per PDA and carried in the RevealArtifactBundle. Tier A — chain-native. TimeLock, SubjectInitiated, OnchainState reads against audited partner contracts on Base. The oracle in these cases is the chain itself; the attestation is a transaction signature verified against contract address. No off-chain trust. Tier B — commodity oracle. Established data aggregators with audit history and reputation — Chainlink feeds, production vital-records APIs, court-docket aggregators. Chain verifies the oracle's assertion; oracle operator is the trust point. Tier C — bespoke oracle. Partner-operated or single-purpose oracle for a narrow domain. Same verification as Tier B but with a narrower trust basis. High-stakes PDAs default to Tier A where possible, Tier B where unavailable, Tier C only with explicit partner acknowledgment plus k-of-n disjoint-oracle attestation mandated.

### Oracle discipline

Oracles are the boundary through which off-chain facts enter the system. Everything on-chain is a signature verification against a frozen oracle pubkey plus a Claim evaluation against the attestation payload. Oracle discipline determines how much of the tripwire claim holds in Tier B/C conditions.

**OracleRegistry.** On-chain contract `(oracle_id → {pubkey, schema_hash, canonical_examples_hash, metadata, reputation_proxy})`. Cealis-curated at launch. Oracle onboarding is explicit: the operator publishes a signing pubkey, an attestation schema, and canonical `valid-attestation` plus `invalid-attestation` example sets (used for Claim verification). Cealis vets the operator (identity, operational history, legal basis), validates the schema, and registers the entry under a 7-day TimelockController. Rotations follow the same timelock with tombstone semantics — old pubkeys remain valid for verifying attestations tied to prior commitments; new pubkeys apply to new commitments only.

**OracleSchemaRegistry.** Companion contract holding each oracle's published schema plus the canonical example set. Every Claim written in a PDA's FSM is replay-tested at configurator-emission time against both example sets: the Claim must pass on the valid examples and fail on the invalid examples. This catches case-sensitivity bugs, field-path mismatches, and type errors before deploy. LLM-generated Claims (v2) run through the same gate.

**Liveness.** Oracle silence does not fire conditions. This is by design — missing attestations mean the FSM never reaches a firing state. Partners wanting fallback behavior compose it explicitly: `OracleAttestation(primary) OR TimeOracle(fallback_timestamp) OR SubjectInitiated` is a standard pattern. TimeOracle services (Chainlink Automation default, Gelato/Pyth/Cealis-beacon alternatives) are registered oracles themselves, bound per-PDA at commit. High-stakes time-critical PDAs default to 2-oracle redundancy on the time axis.

**Tier C and k-of-n.** For irreversible use cases (testament, evidence, archival), single-oracle attestation is opt-out. The default is `MultiPartySignal` k-of-n across disjoint oracle operators — e.g., a death-cert attestation requires two independent vital-records oracles to agree. This bounds the blast radius of a single operator compromise to "one PDA stuck, not every testament fires."

**Governance.** OracleRegistry admin sits with Cealis at launch, guarded by TimelockController (7 days). Year-2 target: migrate governance to a foundation or partner-committee multi-sig while preserving vetting discipline — standards do not relax with the governance move. All admin actions are on-chain-visible events; external watchdog services can subscribe to timelock queues.

### Challenge window resolution

This subsection applies only to PDAs with non-zero challenge windows. Under the §F "Challenge-window guardrail," windows are non-zero only when at least one relevant-axis condition module is Tier B/C. PDAs with all-Tier-A condition modules have zero-window on the corresponding axis and the resolution protocol below does not apply to them — there is nothing to dispute with chain-native facts.

§D places the (Tier-B/C) challenge window between `RevealAuthorized` emission plus L1 finality and the gate signatures firing. A symmetric window optionally sits between `ShredAuthorized` emission and the shred cascade executing (§E). The two windows share a single resolution protocol — one primitive, one resolver role, one set of mechanics. This subsection fills the gap §D forward-references ("per-PDA defaults and dispute resolution mechanics are in §F") for both reveal-side and shred-side, scoped to the Tier B/C cases where windows exist.

**Ceremony resolver — the unified role.** Each PDA declares a `ceremony_resolver` per its configuration. The resolver is an on-chain address (EOA, multi-sig, or contract) whose scope covers challenge windows on BOTH reveal and shred ceremonies for the PDA. Single role, two ceremony axes, one audit surface. Default resolver at pilot is Cealis-internal operator; year-2 target is partner-designated or ombudsman per PDA. The resolver identity is bound into `h_commit` via `pda_root`, so rotation post-commit is not possible — rotation only applies to future PDAs.

**Eligible challengers — PDA-configurable per axis.** The PDA declares, per ceremony axis (reveal-challenge, shred-challenge), which parties may open a challenge within the window. The options are `{subject, partner, named_observers[], recipients}`. At least one challenger role must be eligible for any non-zero challenge window — a non-zero window with no eligible challenger is a configurator-rejected misconfiguration. Template defaults: enforcement / KYC-lending / M&A use `{subject, partner}` for reveal-challenges and `{partner}` for shred-challenges; evidence uses `{subject, partner, custodian_observer}`; consumer / journalism / testament / archival typically have zero-duration windows and thus no challenger set.

**Evidence format — signed challenge statement + counter-attestation.** Opening a challenge calls `ChallengeRegistry.openChallenge(authorizationId, axis, reason_code, counter_attestation_ref, bond)`. The `reason_code` is enum-constrained: `{oracle_attestation_disputed, condition_misapplied, legal_hold_asserted, art_22_intervention_requested, data_subject_erasure_invoked, integrity_claim}`. `counter_attestation_ref` is a hash pointer to a signed counter-attestation — signed by the challenger's authenticated key (σ_subject for subject-opened, partner HMAC-equivalent for partner-opened, named-observer pubkey for third-party-opened) and bound to `authorizationId ‖ h_commit ‖ axis ‖ reason_code`. Counter-attestation content depends on reason_code; structure is enum-defined, not free-form. A challenge with a malformed or missing counter-attestation is dismissed at submission time.

**Bond mechanics.** Bond denomination is ETH or a PDA+-approved stablecoin on Base. Per-PDA minimum declared at configuration; PDA+ sets a platform-wide floor. Bond escrowed in `ChallengeRegistry` at challenge-open. Slash criteria: challenge determined frivolous — counter-attestation invalidates against the oracle schema it disputes, or challenger fails to substantiate within the window. Slashed bonds accrue to a `slashedBalance` withdrawable only by TimelockController (7-day governance). Refund criteria: challenge substantiates (counter-attestation validates + oracle contradicts original), shred intervenes (makes the challenge moot), or challenger withdraws explicitly before window expiry. Template defaults: enforcement / KYC-lending / M&A require bond (discourages nuisance challenges at scale); evidence is bond-optional (third-party observers may legitimately challenge without capital stake); testament / archival / journalism / medical default to zero-duration window and thus no bond.

**Resolver powers during the window.** Within an open challenge window, the ceremony resolver can: (a) invoke G4 refusal on the authorization — σ_G4 (for reveal) or `proof_shred`-refusal (for shred) — which crypto-halts the ceremony via the same G4 refusal path used elsewhere in §D / §E; (b) confirm no intervention needed, which lets the window timeout normally and the ceremony proceed on expiry; (c) extend the window, up to a PDA+-capped number of extensions of fixed duration. For legal-effect PDAs (KYC-lending, M&A, evidence, medical) the resolver is the Art. 22(3)(a) human-intervention endpoint — the challenge statement itself satisfies Art. 22(3)(b) subject point-of-view expression, and the challenge primitive satisfies Art. 22(3)(c) contest. Non-legal-effect PDAs may configure extensions to zero, giving the resolver only halt-or-confirm powers. The resolver cannot override a shred that has already cascaded, cannot un-shred, and cannot force gates to sign — resolver powers are halt-capable, not content-determining.

**Dismissal criteria beyond timeout.** A challenge is dismissed (with bond refunded unless frivolous) if: challenger withdraws explicitly, another challenge on the same authorizationId + axis is already active (one challenge per axis per window), challenger's signer is not in the PDA's declared eligible-challenger set for this axis, bond is under the PDA minimum, counter-attestation is malformed against the reason_code enum, or shred intervenes and moots the challenge. Frivolous dismissal (counter-attestation invalid against schema) slashes the bond; structural dismissal (missing eligibility, wrong bond, malformed payload) refunds.

**Mechanical gating, not operator override.** Every resolution path above is deterministic and on-chain. The resolver role is bounded — it can halt via G4 refusal and extend within PDA+ caps, but cannot unilaterally mark a challenge resolved in either direction, cannot change the outcome of a valid counter-attestation, and cannot reach into committed data. Challenge outcomes are pure functions of (counter-attestation validity against oracle schema) × (resolver halt/extend actions) × (window expiry). "Mechanically gated" in §J item 22 refers to this determinism.

**Interlock with Art. 22 automated-decision-making.** The ceremony resolver primitive is the WP's Art. 22(3) compliance surface for Tier B/C legal-effect PDAs. The resolver provides the halt-capability that makes Art. 22(3)(a) satisfiable when the dispute path is needed — i.e., when a third-party oracle is the trust point and oracle-correctness is what a subject might contest. For Tier A legal-effect PDAs, Art. 22(3) safeguards are satisfied differently — pre-commit informed consent + chain-native trigger determinism + PDA-permitted crypto-shred — and the resolver remains available but is not load-bearing (per the §F Art. 22 safeguard guardrail tier-conditioning). For non-legal-effect PDAs (consumer / journalism / archival / testament in their zero-window configurations), Art. 22(3) does not apply because the reveal does not produce "legal effects concerning" the subject under Art. 22(1) — the resolver primitive remains available but its Art. 22 framing is inactive.

### AI composition

The configurator takes partner intent and produces a PDA config. At V1 it operates from a pre-verified template library and parameter forms. At V2 a free-form LLM composition path is opened behind a verification gate. Either path converges on the same on-chain primitives — FSM over AttestationGate over OracleRegistry — and the same verification gate before deploy.

**V1 — template-library composition.** The PDA+ template library contains a curated set of internally reviewed FSM compositions — PaymentDefault, Testament, DeadManSwitch, EvidenceProvenance, MABoardClosing, and so on. Each template names its required oracles, its DSL Claims, its state transitions, its terminal firing states, and its parameter form. The Cealis-internal configurator takes a partner's intent, picks the closest template, fills the parameter form (specific oracle IDs, timing windows, recipient lists, threshold values), generates a plain-language summary for partner review, and runs the verification gate. No raw FSM authoring by partners. New templates are data-only additions, composed from existing internally reviewed primitives, added to the library via PDA+ update.

**V2 — LLM free-form composition.** Deferred to v2 by explicit scope decision. Shipping free-form LLM composition without a schema-bound verification gate invites silent mis-deploys — LLM hallucinations on oracle field paths or enum values pass shape-reachability analysis but produce FSMs that never fire. V2 adds a verification gate that replay-tests every LLM-generated Claim against the referenced oracle's canonical example sets (at OracleSchemaRegistry) before human review and deploy.

**Verification gate — constant across v1 and v2.** Reachability analysis (every state reachable from initial, every terminal reachable from somewhere), gas-budget analysis (worst-case `advanceFSM` below per-PDA budget), schema compatibility (every Claim type-checks against its referenced oracle's schema), acyclicity for cross-PDA references (when Cross-PDA composition lands as a v2 feature), dry-run simulation against canonical examples, and a human Cealis-operator review. Verification is the architectural seam where AI-generated output becomes deployed condition logic — the gate is not optional.

**Configurator discipline.** The configurator is Cealis-internal. Partners request configurations; Cealis operates the configurator, runs the verification gate, produces the PDA, deploys it on-chain, and provisions it in the partner's dashboard. This is a platform-security mechanism: the configurator is the single point at which PDA+ guardrails get enforced across all deployments, so no partner can produce a PDA that sits outside the PDA+ allowed ranges. The "no partner self-serve" discipline applies to authoring; partners participate through parameter forms and plain-language review, not through FSM authoring or on-chain deploy actions.

**Out-of-bounds handling.** When a partner's intent maps to parameters outside PDA+ allowed ranges, the configurator rejects the configuration at the parameter-form step and surfaces which surface is out of bounds — shred-authority mode disallowed for this PDA type, challenge-window shorter than PDA+ minimum, G3 choice unavailable for the selected condition category, schema incompatible with the requested oracle, or similar. Partners either adjust the intent to fit within the allowed set, or — for narrow extensions that a use case genuinely needs — request a PDA+-level expansion through Cealis's governance process (the same process that lands new templates, new oracles, or new DSL operators per the "Three extensibility vectors" above). Rejection is an operational step, not a protocol-level action; the partner-facing surface is the configurator's validation messages, and the audit trail is Cealis-internal.

Each archetype carries a default trust tier (§F "Trust tiers"); the challenge windows below assume the default. | Archival | A or B/C | Zero | Zero | `retention_window_elapsed OR subject_and_operator_joint_attest`. Authority=Disabled for permanent-archive PDAs (shred condition effectively `false`). Window-zero across tiers — archival has no dispute surface by design. |
| Journalism / source protection | A or B/C | Zero | Zero | `true` (after guardrail AND). Window-zero across tiers — subject-halt capability relies on subject-mode shred, not on a dispute window. |
| Medical | B/C (preventive/occupational health oracles) | 7 days | Zero | `NOT active_treatment_claim AND NOT reveal_in_progress`. Reveal-window covers Art. 22(3)(a); shred-window-zero is archetype-specific (treatment continuity overrides). |
| Consumer | A or B/C | Zero | Zero | Subject-initiated any time outside the gate-signing window. Window-zero across tiers — subject's own consent IS the authorization. |
| Medical | Zero | Zero | `NOT active_treatment_claim AND NOT reveal_in_progress` |
| Consumer | Zero | Zero | `true` (after guardrail AND). Subject-initiated any time outside the gate-signing window. |

Partners tune these within PDA+ min/max constraints. Challenge windows can be lengthened (up to PDA+ max) but cannot drop below PDA+ min per archetype. Shred conditions can be narrowed (adding AND clauses) but cannot be loosened beyond the PDA+ template.

Template defaults are a convenience starting point, not a lock on supported use cases. The data-agnostic property means new templates can land without protocol change — a new template is a set of default values on the existing configuration surfaces, not a new surface.

### Data-agnostic / schema polymorphism

The system makes zero assumptions about what data is being committed. Each PDA declares its own schema, its own AAD construction, and its own attestation requirements. The platform-level schema library is a convenience — a set of templates partners can start from — not a lock on what can be committed. There is no schema catalog, no registry of "supported schemas" the system will decrypt. New schemas land by configuration, not by registry update. The platform knows the shape of a PDA's schema because the PDA declares it; the platform does not have a list of which schemas exist.

## §G — Ingestion modes

The platform is architected for two ingestion modes. Mode A (TEE-ingest) is the shipping default. Mode B (device-encrypt) is architected as a PDA+ capability that is not currently enabled — the current PDA+ state supports Mode A only. Mode B's architecture is preserved in the plugin, the stanza format, and the commit structure so it can be turned on through a PDA+ decision later without protocol rework. Both modes produce the same age envelope format, anchor the same h_commit, reveal through the same 4-gate Shamir reconstruction — the ingestion mode determines where encryption happens, not what gets encrypted or how it's revealed.

### Mode A — TEE-ingest (shipping default)

Under Mode A, the subject's client or the partner's backend uploads plaintext to the G4 ingestion endpoint over an authenticated channel. Plaintext enters the Cealis TEE boundary, gets encrypted into the age envelope inside the boundary, and is destroyed after processing.

Phase 1 runs a server with sealed code whose binary hash is registered on-chain under a 7-day timelock on updates. σ_G4 at that phase is an Ed25519 signature, issued by the sealed-code server against the chain-registered binary hash. Phase 2 swaps the server for a rented TEE — AWS Nitro or equivalent — whose DCAP quote is verified on-chain. The two phases are API-compatible; commits made during Phase 1 keep verifying under Phase 1 attestation after the cutover. The swap discipline around that transition lives in §N.

Mode A supports P5 selective disclosure because plaintext is present inside the TEE boundary at commit-time. The SD pipeline runs alongside the escrow pipeline from within the same boundary and emits cleartext or proven-predicate outputs at commit. §H covers the SD pipeline.

The trust structure under Mode A is an institutional attestation chain — a sequence of published artifacts rather than a single mathematical step. Crypto-literate users can verify each link individually; consumer users rely on the chain collectively. §K treats this link-by-link.

### Mode B — Device-encrypt (architected, not currently enabled)

Under Mode B, the subject's client generates the DEK locally, runs `age-plugin-cealis-v3` on-device, and constructs the full age envelope — Lit ACC stanza, G3 stanza, G4 stanza, and zero or more `CONDITIONAL_RECIPIENT_*` stanzas per the PDA's `conditional_recipients_policy` (§C, §F) — locally on the device. The client uploads ciphertext only. Cealis never sees plaintext. Note: Mode B device clients must fetch deprecation state for the five Cealis-governed V3 registries (Plugin / G4Authority / DSL / Oracle / QTSP) at commit time alongside the existing Lit / G3 / G4 attestation fetches; deprecation precheck is part of the same pre-encryption attestation pipeline.

Mode B needs a crypto-capable client application. A webform cannot do it because the mode requires local plugin execution plus gate-attestation verification before encryption happens — the device has to fetch the Lit assignment record, the G3 committee pubkey, and the G4 authority attestation, verify each one, and only then construct the stanzas. That workflow fits an app, not a webform.

Mode B is structurally incompatible with P5 SD and with any other feature that depends on TEE-plaintext access at commit-time. Under Mode B the plaintext never enters the Cealis TEE, so anything that would run over plaintext inside the TEE cannot run.

The trust structure under Mode B is cryptographic non-custody at commit-time — the subject's device is the encryption boundary, and Cealis is mathematically outside it. Two trust links remain (the device SDK itself, and the gate attestations the device fetched pre-encryption), down from the seven-link chain Mode A carries. §K treats this.

Cryptographic non-custody applies at commit-time. Reveal-time custody composition is identical across modes — the same σ-authorized Shamir share recovery applies to Mode B commits the same way it applies to Mode A commits. §D covers the reveal. The ingestion mode determines where the plaintext is seen at commit. It does not alter the release path.

### Why Mode A defaults in the current deployment

The current deployment's workflow carries two shapes, neither of which admits Mode B. B2B partners POST raw data backend-to-backend through the API — no subject device is in the loop, so no client-side crypto step is available in that flow. Consumer-facing use runs through a webform, which also has no local plugin execution path. Mode A serves both shapes through one architectural path because the TEE-ingest endpoint accepts plaintext from either a browser webform or a partner backend and encrypts inside the boundary identically.

Mode B requires an app, and an app requires a distribution surface and a UX that neither the current B2B flow nor the current consumer webform has. Mode B's architecture is preserved so later expansions where cryptographic non-custody is structurally load-bearing — use cases whose threat model does not tolerate any Cealis-side plaintext exposure even briefly — can enable Mode B through a PDA+ decision without protocol rework. When enabled, the partner picks the mode at PDA configuration, or the subject picks it in the user UI when the PDA allows subject choice.

Enabling Mode B is a PDA+ configuration change — Cealis flips the platform-availability bit for a given PDA type, provisions the crypto-capable client SDK, and publishes the SDK's binary hash and attestation-flow specification. The first PDA to deploy under Mode B carries a new set of partner-facing expectations around client-side SDK requirements and attestation-flow UX; §N covers the operational-posture governance rhythm Cealis runs on for platform-level changes of this shape.

### No hybrid mode

One ingestion mode is active per PDA for that PDA's lifetime. The mode is frozen through the PDA/configurator ingestion-mode field; G4 `phase` remains the separate Phase 1 / Phase 2 attestation field (§N). Switching modes means a new PDA, not a reconfiguration of an existing one.

## §H — Selective disclosure (parallel pipeline)

At commit-time, inside the Cealis TEE boundary, a parallel pipeline can emit specific fields as cleartext or proven predicates as zero-knowledge proofs. This pipeline runs alongside the sealed-core escrow pipeline, not downstream of it. SD is off by default per PDA and opt-in via PDA configuration. When a partner opts in, the partner receives SD output at commit-time — before any reveal event, before any gate signatures, independent of whether the PDA's condition ever fires.

### Parallel, not extracting from escrow

Plaintext exists once inside the Cealis TEE at commit-time. During that TEE window the escrow pipeline encrypts the plaintext into the age envelope and the SD pipeline, if the PDA opted in, evaluates its configured predicates over the same plaintext. The plaintext is destroyed after processing regardless of which pipelines ran.

SD shares the commit-time DEK only for salt-derivation inside its own commitments, never for decryption. The escrow envelope is sealed once at commit and later reconstructed through 4-gate Shamir share recovery (§C, §D); SD outputs are separate artifacts produced at commit-time. Two products of the same TEE-boundary step; neither is a transformation of the other.

Release path unaffected — SD outputs are partner-consumable artifacts produced at commit-time, and the escrow sealed-core stays under 4-gate Shamir reconstruction regardless of whether SD ran. SD opt-in does not create a release-path side-channel.

### What SD outputs

Three artifact classes.

- **Cleartext fields.** Specific attributes pre-declared in the PDA's SD configuration, delivered to the partner in the clear at commit-time.
- **Zero-knowledge proofs.** Proven predicates over plaintext without revealing plaintext — the partner gets a proof that a predicate holds, not the value it holds over.
- **Commitments.** Plaintext-bound digests the partner uses to verify SD outputs against h_commit's ciphertext_digest (§C) and the escrow commitment, so the SD artifacts are cryptographically tied to the same commit the escrow envelope anchors.

Predicate types, commitment structure, proof system, and salt-derivation detail live in S2-7 (`docs/specs/sd-spec-v2.md`).

### Mode compatibility

SD is compatible with Mode A because plaintext is present inside the Cealis TEE boundary at commit-time, which is the SD evaluation window. SD is structurally incompatible with Mode B. Under Mode B the plaintext never enters Cealis infrastructure — the subject's client constructs the envelope locally — so TEE-side SD evaluation has no plaintext to evaluate over. Client-side SD with on-device zero-knowledge proof generation is a future extension, not in current scope.

SD is off by default per PDA even under Mode A. Mode A makes SD possible; the partner opts in per PDA to turn it on. A Mode A deployment without SD opt-in runs the escrow pipeline only.

### Technical specification reference

`docs/specs/sd-spec-v2.md` holds the active Stage-2 specification — predicate set, zero-knowledge proof system, commitment structure, salt-derivation detail, partner verification SDK, `sdMerkleRoot` binding, and SD/escrow isolation. The WP cites the concept; implementation detail tracks in S2-7.

## §I — Provenance + attestation

Chain-of-custody starts at commit-time and runs forward on-chain through reveal (§B P9). Provenance and attestation extend that chain backward from commit-time to the data's origin. Two mechanisms do the extending. P14 Issuer modes handle personKey derivation — the subject-identity axis of what enters the commit. P15 attestation-as-input handles field-level provenance — the data-origin axis for values inside the commit. Together: data enters the commit with its origin chain attached, the commit anchors the full chain, and the reveal artifact carries the attestations forward.

### Issuer modes (P14)

Three Issuer modes. The partner selects one per PDA at deployment. The mode determines how the subject's personKey is derived for the commit.

**Mode A — external Issuer.** An external Issuer signs an attestation binding personKey to the subject. personKey derives from provider ID plus a per-subject nonce. Used when the PDA requires trust in an external identity-verifier's audit trail rather than in the subject alone.

**Mode B — self-sovereign.** The subject IS the Issuer. personKey derives from the subject's wallet plus a registration_nonce. Used when the subject's own signature is the root of the identity claim.

**Mode C — asset, not person.** Depositor role. personKey derives from a content hash plus a depositor nonce. Used when the committed data is asset-centric rather than subject-centric — the identity anchor is the data's fingerprint, not a person.

All three modes compose identically into commit_AAD (§C). The mode determines how personKey is derived; it does not change commit, reveal, or shred ceremonies. A PDA's Issuer mode is a configuration choice at the personKey-derivation step, not a fork in the protocol.

### Attestation-as-input (P15)

Each field entering a commit is either self-declared or externally attested. Self-declared fields bind trust to the subject — σ_subject signs over the commit preimage, and the field's trust chain reduces to the subject's signature. Externally-attested fields bind trust to whoever signed the attestation — the attestor's audit trail carries the field's provenance.

Per-PDA configuration decides which fields require which treatment. A PDA can require external attestation on some fields and allow self-declaration on others.

Attestations travel as part of commit_AAD, Merkle-rooted under the `p15_attestations_root` field in the AAD structure (§C). They are bound into the AEAD check on reveal: if an attestation has drifted between commit and reveal, the AEAD tag fails to verify and no plaintext is produced. Drift produces cryptographic reveal failure, not procedural flagging.

Attestations contribute to h_commit via the AAD digest, so the chain-of-custody is not just "committed at time T" but "committed with these attestations from these attestors at time T." The reveal artifact (§D) carries the attestations forward — any recipient verifying a reveal can check attestation signatures against the attestor's published pubkey registry independently of Cealis.

### Chain-of-custody extension

P14 names the subject-identity provenance — who the subject is to this PDA and where that claim comes from. P15 names the field-level provenance — which data came from where, with what signer behind it. Both feed commit_AAD. commit_AAD's digest is bound into h_commit. h_commit is chain-anchored.

The chain-of-custody starts before commit-time at the attestors and the Issuer role, passes through commit as the anchoring step, and continues on-chain through reveal. A recipient of a reveal artifact can verify the attestations against the attestor's pubkey registry and the Issuer's attestation against the Issuer's published key — the same chain-of-custody property extends forward to any consumer of the reveal.

## §J — Features derivable from the system

The system described in Part 1 produces a set of derivable properties. Each one traces to a mechanism Part 1 already described — the property is not a separate claim, it is a consequence of the architecture. This section enumerates those consequences at three claim-depth altitudes: core system properties that fall directly out of Part 1's mechanisms, operational consequences that fall out of how the mechanisms compose into partner-facing behavior, and structural implicits that hold across the system without being named as features. Altitude names how directly a property traces to Part 1, not how important the property is — all items below are derivable, the altitudes describe derivation distance. Compositional possibilities that the primitives support but this WP doesn't enumerate are covered in §P, not §J.

### Core system properties

1. **Data doesn't exist to the partner until the predefined condition fires on-chain**, because the sealed ciphertext sits off-chain and the four gates do not produce signatures without the on-chain condition firing first (§C, §D). Universal tripwire — every other property here composes on top of this one.

2. **No single party can cause release — including Cealis**, because the DEK reconstructs only from the Shamir threshold of shares authorized by four disjoint-operator gates, and any missing fixed gate share makes the threshold unreachable (§B P3, §B P18, §D).

3. **On-chain conditions cannot be faked**, because the condition is evaluated by Base L1 consensus and G4 independently re-reads chain state before signing σ_G4 (§B P3, §D).

4. **Tamper-evident — any modification produces detectable mismatch**, because h_commit anchors the envelope and AAD on-chain, AEAD binds commit_AAD into every decryption, and stanza MACs reject bypass attempts at the plugin layer (§C, §B P9).

5. **Verifiable data deletion via on-chain shred, gated by predefined shred condition**, because shred fires only when both the PDA's declared shred authority signs AND the PDA's declared shred condition evaluates true on-chain — the same ConditionEngine primitive (§B P4) that gates reveal also gates destruction. A PDA+ mandatory guardrail (`NOT post_challenge_reveal_in_progress`) forecloses shred from racing gate-signing, so the shred-vs-reveal race that would otherwise let a combiner derive DEK post-shred cannot occur. The universal tripwire mirrors across destruction: no shred path bypasses the on-chain-verified predefined shred condition. Post-shred, the triple block lands — G1 refuses future authorization, G4 refuses σ_G4 for all remaining causes (Art. 17 propagation, integrity failure, legal retention orders), and the vault physically deletes ciphertext (§E, §B P11).

6. **Subject consent is cryptographic, not policy**, because σ_subject (WebAuthn P-256 or EIP-712 wallet signature) is AEAD-bound into commit_AAD, so any commit without valid subject signature fails the AEAD check at reveal (§C, §B P1).

7. **Cross-partner privacy — same subject, different partners, no correlation**, because subject_commitment_v3 uses per-partner namespace derived from partner_id and pda_id, and σ_subject stays off-chain so passkey pubkeys never anchor on-chain (§C).

8. **Chain-of-custody is inherent, not logged**, because every lifecycle event — commit, challenge, gate-fire, release, shred — happens *on* chain rather than being written *to* chain; the custody record IS the chain (§B P9).

9. **Release goes to named recipients, not broadcast**, because the age envelope carries per-recipient stanzas and recipients[] is Merkle-rooted in commit_AAD, so the set of addresses that can receive the reveal is frozen at commit time (§C, §D, §B P8).

10. **Halt-capable without release-capable**, because σ_G4 is either produced (with crypto-determined content) or not, and Cealis's only operator-capable action is whether to produce σ_G4, not what σ_G4 contains (§D, §B P13).

11. **Reveal content is cryptographically determined**, because reveal output is a pure function of chain events, gate signatures, and commit data — the plaintext that emerges from decryption is fixed at commit-time and no operator chooses what it contains (§D).

12. **Data-agnostic platform — any use case, any schema**, because each PDA declares its own schema, AAD construction, and attestation requirements, and the system holds no registry of "supported schemas" (§B P7, §F).

13. **Two ingestion modes with different trust structures**, because the platform architects both TEE-ingest (institutional attestation chain) and device-encrypt (cryptographic non-custody at commit-time) as first-class ingestion paths — shipping default is TEE-ingest, device-encrypt is PDA+-capability preserved for later enable (§G). Trust-structure detail per link is §K.

14. **Portable artifacts — protocol survives Cealis-the-company**, because the substrate composes rented commodity networks (Lit, dcipher/drand), Base L1, the age envelope format, and the `age-plugin-cealis-v3` plugin — so data already committed can still be operated if Cealis-the-company disappears, and worst-case the protocol is open-sourceable. Reveals do not require Cealis-the-company because the recipient combiner is recipient-operated (§D "Combiner location"); the protocol survives Cealis-the-company in full reveal capability, though vault availability is a separate operational axis (§L Non-defense 10, §N).

### Operational consequences

15. **Zero Cealis-operated fixed-gate custody at any point in the lifecycle**, because fixed-gate custody has no Cealis-held master key, no Cealis-held threshold set, and no long-lived decryption-capable gate key; PASSKEY_ACCOUNT rotation-log nuance lives in §K item 9. σ_G4 only authorizes the G4 share, and that share alone yields no DEK (§B P18).

16. **Disjoint-operator composition across three dimensions** (organizationally, jurisdictionally, and TEE-vendor-wise), because Lit Protocol operators, Randamu Threshold Association or League of Entropy, and Cealis are separate legal entities under separate jurisdictions running on cross-vendor TEEs (§B P19).

17. **Per-PDA G3 choice — dcipher or drand**, because the G3 gate accepts either Randamu's threshold BLS (dcipher) or League of Entropy's beacon signature (drand), selected per PDA at deployment and frozen in h_commit via the `g3_choice` field (§F, §C).

18. **Shred is PDA-parametric on two axes — authority and condition**, because `shred_authority_id` in h_commit fixes who can trigger shred (Subject, Joint, Operator, Timelock, Disabled) and `shred_condition_mode` + `shred_condition_spec_hash` in pda_root fix the on-chain state predicate under which shred is valid. Both axes pick from PDA+ allowed sets; the mandatory `NOT post_challenge_reveal_in_progress` guardrail AND-composes with every shred condition at the PDA+ layer (§E, §F).

19. **Configurable conditions via pluggable ConditionEngine modules**, because the on-chain condition authorizing reconstruction is a generic `isConditionMet(authorizationId)` call backed by a module selected per PDA from the PDA+ whitelisted set (§B P4, §F).

20. **Two-level platform configurability — PDA+ for the platform, PDA for the partner**, because Cealis configures the allowed surfaces and the partner picks values inside those surfaces, with the configurator itself Cealis-internal to enforce guardrails uniformly (§F).

21. **Multi-recipient delivery with per-recipient schema selectors**, because the age envelope carries N per-recipient stanzas and the commit_AAD binds per-recipient schema selectors that determine which fields of the payload each recipient gets (§C, §D, §B P8).

22. **Challenge and dispute windows are mechanically gated where they apply**, because availability is tier-conditional — Tier A (chain-native) PDAs default to zero-window on the relevant axis since chain-native facts are not disputable, while Tier B/C (third-party oracle) PDAs require non-zero windows at PDA+ archetype floor and share a single resolution protocol under a unified ceremony-resolver role: deterministic timeouts, structured counter-attestations, bond mechanics, PDA+-capped extensions, no operator override on outcome (§F "Challenge-window guardrail," §F "Challenge window resolution," §B P10).

23. **Provenance extends chain-of-custody backward to data origin**, because P14 Issuer modes fix personKey's derivation to either external attestor, subject, or asset-depositor, and P15 attestation-as-input binds per-field attestations into commit_AAD — so the chain-of-custody starts before commit-time at the attestors and Issuer role (§I).

24. **Hybrid post-quantum wrapping at commit**, because stanza encryption combines ML-KEM-768 with X25519 under the `age-plugin-cealis-v3` plugin, and an attacker needs both primitives to fall to extract the DEK from stanzas (§B P21).

25. **Stanza-addition re-key ceremony without payload re-encryption**, because the plugin's stanza architecture allows new stanzas under fresh primitives to be added to existing commitments while the payload stays encrypted under the original DEK and symmetric cipher (§B P21). Ceremony detail is §M.

26. **Phase-swappable G4 — Phase 1 sealed-code server to Phase 2 rented TEE**, because the G4 attestation contract binds the signature content (authorizationId, h_commit, block_hash, binary_hash or DCAP quote) identically across phases, and commits made in one phase keep verifying under that phase's attestation after cutover (§G, §N).

27. **Rental-commodity cost structure rather than bootstrapped staking**, because the 4-gate substrate is composed of rented commodity networks (Lit, dcipher or drand, G4 rented TEE) rather than a Cealis-operated staked custody network, and the customer-relationship structure preserves existing-commit reveal capability even if Cealis stops paying for new-commit capacity (§B P18, §N).

28. **Different on-chain trigger conditions produce different reveal events without protocol change**, because the ConditionEngine module set is pluggable and all modules flow through the same 4-gate reveal ceremony (§D, §B P4, §F).

29. **Structured artifact output — RevealArtifactBundle with third-party verifiability**, because the reveal produces a JCS-canonicalized bundle carrying authorization identifiers, per-recipient payloads, gate signatures with their attestations, chain proofs, and ShredRegistry state at reveal — every signature verifiable against public operator registries (§D).

30. **Parallel day-one disclosure pipeline (SD)**, because under Mode A the TEE boundary at commit-time can run a side-channel pipeline that emits cleartext fields or zero-knowledge proofs alongside the escrow envelope, opt-in per PDA (§H).

31. **Delegated identity verification**, because the PDA's Issuer mode A binds personKey to an external attestor's audit trail via provider ID plus per-subject nonce, and the attestation travels in commit_AAD so the chain-of-custody extends backward to the attestor (§B P14, §I).

### Structural implicits

32. **σ_G4 is a crypto-enforced halt, not a procedural one**, because σ_G4 authorizes a required fixed-gate share — a missing σ_G4 prevents G4 share admission, and even a malicious combiner with Lit and G3 shares cannot reach the Shamir threshold (§D).

33. **Gate signatures are authorization evidence, not DEK material**, because under the Shamir construction σ values verify gate consent and condition satisfaction while share secrecy carries the DEK boundary. Shares and DEK are never published on-chain, never logged, never cached (§B P22, §D).

34. **Architecturally distributed controller relationship**, because Cealis is a controller at G4 and vault operations and joint controller for PDA+ means; the reveal chain is layered because other operators also carry role-specific control points before plaintext availability (§B P19, §N).

35. **Vanish-path — data already committed remains operable without Cealis-the-company**, because the protocol composes rented commodity networks, Base L1, a standard envelope format, and an open-spec plugin, so the existing gate operators + chain + envelope can continue to produce reveals on existing commits without Cealis-the-company being present (§A, §B P18, §N).

36. **Reveal artifacts composable as input to other obligations**, because the RevealArtifactBundle is a canonical, independently-verifiable structure — which means one PDA's reveal output can feed another PDA's condition module as attested input (§D, §B P4).

37. **Future features land without breaking past commits**, because every protocol surface has a defined forward-compat extension path (P25) and each commit binds its full version surface — `plugin_version_digest`, `g4_authority_ref`, `dsl_version_ref`, `oracle_references_root`, `commit_version` — via h_commit and commit_AAD, so registry rotations, new templates, new oracles, new DSL operators, new ingestion modes, new gate counts, and new conditional_recipient variants all extend the system additively while old commits verify under their original references (§B P25, §C, §F, §M).

Compositional possibilities beyond these enumerated consequences are covered in §P.

## §K — Trust framing

> **See S2-8 (controlled-use spec) §10.7 for two banned-phrasing candidates the controlled-use profile adds to this list (no "secure container / sandbox / DRM" for the client SDK; no "Cealis prevents authorized recipients from extracting data once displayed").**

Trust has structure. The WP states the structure per link. Two ingestion modes (§G) produce two different trust structures — a seven-link institutional attestation chain under Mode A (TEE-ingest, shipping default), and a two-link cryptographic-non-custody chain under Mode B (device-encrypt, architected as PDA+ capability). The trust claim scales by user sophistication. A crypto-literate user who performs verification collapses each link to mathematical trust. A consumer user who cannot individually verify the links collapses the chain to institutional trust — Cealis plus the hardware vendors plus the external auditors are, collectively, competent and honest. The WP does not pretend trust is a single cryptographic statement. What the system defends against is §L territory; this section names only what the user is trusting.

### Mode A — TEE-ingest institutional attestation chain

Under Mode A, the subject's plaintext enters the Cealis TEE boundary, gets encrypted inside the boundary, and is destroyed after processing (§G). What the user is trusting is a chain of published artifacts, not a single mathematical step. Seven links, each named explicitly:

1. **Trust Cealis's claim** that the source code we publish is the code that compiles into the binary running G4. Verification path: read the published source.

2. **Trust the reproducible-build process** — that the source really does compile to the hash we've registered on-chain. Verification path: run the reproducible build locally and compare the output hash against the on-chain registry.

3. **Trust the on-chain binary-hash registry** — that the hash returned by a chain query is the one Cealis actually deployed. The 7-day timelock on updates makes silent swaps visible in advance of the swap happening. Verification path: monitor the registry's update events on-chain.

4. **Trust the runtime attestation** — that the enclave (Phase 2) or the sealed-code server (Phase 1) actually running is bound to the registered binary. Phase 2: DCAP quote from the serving TEE, verified on-chain via Automata zkDCAP. Phase 1: Ed25519 signature against the chain-registered binary hash, with the sealed-code pattern plus 7-day timelock carrying the binding.

5. **Trust the hardware vendor** (AWS Nitro, Intel SGX, or AMD SEV-SNP depending on the rented-TEE choice) that the TEE attestation chain is cryptographically sound and not backdoored. Verification path: vendor audits, industry analysis, vendor key transparency.

6. **Trust the compiler toolchain** that it didn't inject malicious code during build. Reproducible-build (link 2) helps but isn't absolute — the toolchain itself is part of the build dependency graph. Verification path: bootstrapped compilers, diverse-double-compiling.

7. **Trust any external audit** of the source plus the build pipeline plus the on-chain registry contracts, if and when one exists. Cealis has undergone internal adversarial review only and has never been externally audited; this link is anticipatory. Verification path: read the audit reports once any are published.

For a crypto-literate user, every link is verifiable. The chain collapses to mathematical trust if verification is performed at each link. For a consumer user who cannot perform the verifications, the chain collapses to institutional trust — Cealis plus the hardware vendors plus the external auditors are, collectively, competent and honest. The chain's strength equals its weakest link; stating otherwise in the WP would be overclaiming.

### Mode B — Device-encrypt cryptographic non-custody chain

Under Mode B, the subject's client generates the DEK locally and constructs the full age envelope on the device (§G). Cealis never sees plaintext. The trust chain shrinks to two links:

1. **Trust the subject's own device and SDK** to perform the encryption correctly. This is local to the user — the user can inspect the SDK, audit it, pick the device, or build their own client.

2. **Trust the gate attestations the device fetched and verified pre-encryption** — the Lit assignment record, the G3 committee pubkey, the G4 authority attestation. Same mechanisms Mode A uses, but verified by the subject's own device before encryption happens, not by a Cealis TEE.

Removed from the trust chain vs Mode A: links 1 through 5 of Mode A above. Cealis never had plaintext under Mode B, so there is no "trust we destroyed plaintext after TEE processing" claim — it was never there. Mode B converts the seven-link institutional attestation chain into a two-link cryptographic non-custody structure. The cost is SD incompatibility and the need for a crypto-capable client application (§G).

Mode B changes commit-time custody, not reveal-time custody. The 4-gate Shamir reconstruction at reveal is identical across modes — §D covers it.

### Per-audience framing

The WP is written for us (internal audience). But the trust framing above supports downstream reuse for different audiences, each with a different relationship to the chain.

**For us (internal).** State the chain openly. Name each link. Acknowledge that Mode A requires institutional trust for consumer users even while crypto-literate users can verify mathematically. Acknowledge Mode B converts that to cryptographic non-custody at the cost of SD plus client complexity. Name what Mode B doesn't defend against (subject-device compromise) without dressing it up.

**For crypto-literate reviewers** (grant evaluators, audit reviewers, technical partners). Same explicit-link framing. These readers will verify; overclaiming triggers instant skepticism, and underclaiming wastes the mathematical structure that is actually there. Show the chain; let them verify it.

**For institutional and regulatory partners.** Emphasize that the chain is signed, auditable, and jurisdictionally distributed across operators. Trust is not blind — it is traceable through published records. For regulatory and evidentiary contexts, the Phase 2 G4 attestation chain provides the signed, auditable record that **§286 ZPO free-evaluation** admissibility of electronic documents rests on as default. **§371a ZPO Anscheinsbeweis** (the stronger presumed-authenticity admissibility) requires σ_subject to be a Qualified Electronic Signature under eIDAS Art. 25 — which Cealis's default WebAuthn-platform-authenticator σ_subject does not satisfy. Partners requiring §371a-class admissibility elect the QTSP integration capability per §F (`qes_subject_required = true`, `qtsp_provider_id` from `QTSPRegistry`) and source σ_subject from a registered EU QTSP — D-Trust, Bundesdruckerei, or any other registered QTSP, with a Cealis-published QTSP option as a possible future addition. Without QTSP integration, gate signatures and σ_subject are admitted as §286 free-evaluation evidence. The framing matters legally: §286 is "evaluated alongside other evidence with full judicial discretion"; §371a is "presumed authentic absent successful rebuttal." Both are valid evidentiary postures; the difference is the burden allocation in court.

**For consumer end-users.** Translate without lying. For Mode A: "Cealis encrypts your data in tamper-proof hardware; we destroy the plaintext after encryption completes, inside the hardware boundary; we've made the code public so anyone can verify we do what we say. You don't have to trust us — you can verify." For Mode B (designed, never shipped): "Your device does the encryption; we never see your data — by construction, the plaintext never reaches us."

### Phrasings this WP does not use

The trust framing above excludes a specific set of phrasings that recur in the surrounding industry and that the WP refuses. Seventeen patterns, each paired with the structural replacement:

1. NOT **"V2 is cryptographically secure."** Too vague — trivially true or trivially false depending on what is meant. Replace with specific claims: under threat X, defense Y holds.

2. NOT **"TEE makes it mathematically impossible for Cealis to see your data."** False under Mode A — Cealis TEE processes plaintext briefly inside the boundary. Replace with: Cealis TEE processes plaintext inside a hardware-sealed boundary, then destroys it; the user trusts the TEE attestation chain. Under Mode B, "mathematically impossible" is defensible because the device is the encryption boundary and Cealis is outside it — that phrasing is reserved for the Mode B context only.

3. NOT **"We are GDPR-compliant."** Too vague. Replace with specific claims: crypto-shred blocks future reveals for a given commitment, the vault deletes ciphertext after on-chain shred confirmation, σ_subject stays off-chain and cross-partner-unlinkable by construction.

4. NOT **"Decentralized — no single point of control."** Partially true and partially false. Replace with: no single operator can cause a reveal; Cealis can halt reveals via G4 refusal; Cealis can also stop vault availability because Cealis runs the vault. Neither power alters what a valid reveal contains — both are halt-or-allow axes, not content-control axes.

5. NOT **"Open-source means we're transparent."** Code openness is not the same as transparency about behavior. Replace with: what is open (the `age-plugin-cealis-v3` plugin, the G4 server source, the smart contracts, the stanza format) and what is not open (the vault code, closed by explicit commit — §M covers the threat-model reasoning for that choice).

6. NOT **"Your data is safe forever."** Impossible to guarantee across cryptographic aging. Replace with: we commit to periodic re-keying as cryptographic primitives age, with hybrid post-quantum wrapping at commit and stanza-addition re-key ceremonies without payload re-encryption (§B P21, §M).

7. NOT **"G4 is Cealis's custody role."** G4 is Cealis's attestation-and-refusal role — Cealis holds no decryption-capable key anywhere, σ_G4 authorizes only the G4 share, and that share alone yields no DEK (§B P18). Cealis is a GDPR controller at G4 for the signing-operation processing step (§N G4 refusal scope), but custody in the key-holding sense stays with the composition across gates, not with Cealis.

8. NOT **"Cealis is not a GDPR controller."** Cealis is a controller at G4 for the signing-operation step and at the vault for sealed-ciphertext custody, and is a joint controller with the partner for platform-wide means determined via PDA+ configuration (schema, condition, recipients, retention, shred). Replace with: layered controllership — Issuer (identity attestation), Cealis (G4 + commit-infrastructure + joint-with-partner on PDA+ means), partner (content), recipient (reveal-output + combiner).

9. NOT **"Cealis holds no master key anywhere."** True for the four gates (§B P18 stands), but incomplete once conditional_recipient Mode 1 ships with PasskeyRotationLog. Cealis runs rotation-log infrastructure for Cealis-account passkey rotations. Cealis cannot forge rotations — each rotation requires the prior passkey's WebAuthn assertion (a key Cealis does not custody). Initial-entry integrity depends on the subject's mandatory pre-σ inspection of `initial_passkey_pubkey` via the `age-plugin-cealis-v3` subject-side verifier (§C). Cealis can censor publication (availability degradation), not substitute recipients (custody preservation). Worst-case substitution requires compromising the recipient's current passkey, outside Cealis's control. Replace the blanket phrasing with this nuanced one whenever PASSKEY_ACCOUNT recipients are in scope.

10. NOT **"Cealis has no emergency response capability beyond the 7-day timelock."** Partial truth that understates the real posture. Replace with: Cealis holds a bounded, on-chain-visible, crypto-enforced halt capability via registry deprecation flags. Deprecating a non-canonical entry is instant (2-of-3 CealisSecurityMultisig); deprecating the canonical-in-use entry of any registry adds a 24h expedited TimelockController delay (partner/recipient observation window). Halt is bounded by 72h absent on-chain-verifiable disclosure (`publishDisclosure(bytes)` with keccak-verified content binding). Re-deprecation of the same entry within 30 days of an auto-clear requires TimelockController. Halt is halt-only — cannot grant reveals, cannot alter reveal content — consistent with items 4 and 7. During gate-signing windows, deprecation cannot halt (same architectural discipline as shred — §B P11, §E). **Governance Phase 1 caveat:** at V2 launch, all three CealisSecurityMultisig seats are Cealis-held pending external-advisor seating; the 2-of-3 cross-domain-independence claim is not yet live. EmergencyGovernance circuit breaker similarly reduces to Cealis-alone at Phase 1. Phase 2 (external advisor seated) completes before first paying partner OR within 90 days, whichever is sooner. At Phase 1 the security gains from these primitives are process friction + on-chain visibility, not independent-domain defense — name this explicitly whenever Phase-1-present public copy invokes the multisig story.

11. NOT **"EIP-1271 is cryptographic consent."** Reserved framing for when WALLET_EIP1271 (variant tag `0x03`) ships post-V2. Replace with: EIP-1271 is contract-trust consent — the contract's `isValidSignature` return is the consent gate, not a specific key-holder's signature. Upgradeable recipients' signing requirements can change over the PDA lifetime; subjects have no way to constrain this cryptographically. Use cases where signer integrity must be preserved against possible upgrade (e.g., JOURNALISM_RECIPIENT where signer-composition change mid-PDA is a security event) should prefer Mode 2 k-of-n over multiple EOAs or set `reject_on_bytecode_change = true` on the stanza.

12. NOT **"Reveal delivery is private."** Under WALLET_EOA delivery, ciphertext after DEK derivation is POSTed or IPFS-pulled to the recipient's `delivery_url`; recipients have network-observable delivery. Subjects with strong network-privacy requirements should configure recipient-pull via IPFS/Tor or use Mode 1 (in-app Cealis dashboard delivery).

13. NOT **"§371a ZPO Anscheinsbeweis admissibility as default."** §371a presumed-authenticity admissibility requires σ_subject to be a Qualified Electronic Signature under eIDAS Art. 25 — Cealis's default WebAuthn-platform-authenticator σ_subject is an Advanced Electronic Signature (AES) per eIDAS Art. 26, one tier below QES. Default replacement: §286 ZPO free-evaluation admissibility — gate signatures + σ_subject + PDA configuration + on-chain commitment chain are admitted as documentary evidence whose weight is evaluated alongside other evidence with full judicial discretion. Use the §371a phrasing only when the PDA has elected QTSP integration via `qes_subject_required = true` (§F) and σ_subject is sourced from a registered QTSP. Both §286 and §371a are valid evidentiary postures; the difference is the burden allocation in court.

14. NOT **"the Cealis access client is a secure container / sandbox / DRM."** False under the controlled-use configuration profile (S2-8). The client is a thin SDK helper that makes the cryptography ergonomic — gate-signature collection, ephemeral session keys, no-default-persistence, dual-validation discipline where the client-side schema check is a UX layer and the TEE-side write-validation gate is the only enforcement boundary. The honest analogues are Signal Desktop, 1Password, and MetaMask — applications that make doing-the-secure-thing easy without claiming to fight the authorized user. Replace with: the controlled-use access client is a thin crypto helper that wipes session state by default on close, validates submissions client-side for UX, and routes the security boundary to the G4 Phase 2 TEE write-validation gate; the authorized recipient is not the adversary the spec defends against (item 15).

15. NOT **"Cealis prevents authorized recipients from extracting data once it is displayed on their device."** False, and structurally so. The eligible recipient holding a valid policy-scoped access token is the entitled party; the spec is not designed to defeat them. Replace with: the controlled-use surface defends against ambient copies, uncontrolled persistence, silent onward transfer, scope creep beyond entitlement, write-history rewriting, and malicious-but-authorized over-reach within scope — it does NOT defend against the entitled recipient taking a screenshot, a photograph of the screen, an OS-level keylogger, a post-display memory dump on a rooted device, or any other extraction path that operates from inside the authorization envelope. Future hardening is possible at the device layer; it is not promised here.

16. NOT **"Cealis is a crypto wallet"** / **"Cealis holds your funds"** / **"Cealis-issued wallet."** False under the monetary configuration profile (S2-9, A25). Monetary value escrow applies the same conditional-sealing operation as the data path — the payload class differs (raw 32-byte ECDSA secret instead of partner-defined data bytes), the substrate does not. Cealis is not a wallet provider, does not custody funds, and does not issue wallets in the consumer or institutional sense those phrasings evoke. The destination is a vanilla EOA whose seed is born inside a TEE-genesis ceremony, sealed under the V3 4-gate AND substrate before any extractable plaintext exists, reconstructed only at the recipient's combiner after on-chain condition fire. Replace with: monetary value escrow is one Cealis configuration profile; the destination is a vanilla EOA the recipient operates after reveal; Cealis appears nowhere in the wallet's on-chain signer set; Cealis's system-locked guarantee covers the conditional-sealing operation up to and including reveal, and terminates at the recipient's combiner — post-reveal seed custody is recipient responsibility and the recipient-education clause in `MonetaryEscrowPolicy` UX surface makes this explicit at commit time.

17. NOT **"Cealis is a non-custodial wallet service."** Misleading under the monetary configuration profile (S2-9, A25). The phrasing frames Cealis as a competitor to wallet UIs (MetaMask, Rainbow, Phantom, Argent) — Cealis is not a wallet UI and does not provide ongoing wallet operation. The non-custody property derives from the V3 4-gate AND defense extended from PII data to seed bytes (same architectural pattern, asymmetrically more demanding regulatory regime under MiCA Art. 3(1)(17) "means of access" — see §L for the residual surface, §M for the storage discipline), not from a separate "non-custodial wallet" architecture. Replace with: monetary value escrow is a configuration profile of Cealis's conditional-sealing system; the recipient operates the destination wallet using their own software after the conditionally-sealed seed bytes are reconstructed at the recipient's combiner. The non-custody framing scopes to Cealis's role across the sealing/reveal lifecycle — not to ongoing wallet operation, which is recipient's domain.

Claims about what the system defends against live in §L. Operational discipline around crypto-aging over time lives in §M.

## §L — Threat catalog

The threat catalog states what V2 demonstrably prevents or detects, what V2 explicitly does not fully defend against with the partial mitigations that exist, and what is explicitly out of scope. Honest two-sided treatment — not marketing, not scare-mongering. For each defense, the threat is named, the mechanism is cross-referenced to Part 1, and the residual risk is stated. For each non-defense, the threat is named, the structural reason for non-defense is given, the mitigation (if any) is stated with its cross-reference, and the residual is stated. Out-of-scope items are named with one sentence each. §K states what the user is trusting; §L states what the system defends against — adjacent altitudes, different questions. §M and §N cover operational commitments that turn partial defenses into practical security.

### Defenses

**1. Single-party compromise of any one operator set.** An attacker compromises one of Lit operators, the G3 operator set (dcipher or drand), or Cealis G4 — but only one. Defense: the 4-gate AND-composition reconstructs the DEK only from the threshold Shamir share set (§B P3, §D), so one compromised gate yields at most one share and cannot reconstruct the key. Single-party compromise yields zero decryption capability, crypto-enforced not procedural. Residual risk: none at this level.

**2. Single-organization compromise across gates.** A state actor or adversary attempts to compel one organization's operators across multiple gates. Defense: disjoint-operator composition (§B P19) — Lit operators, the G3 operator set (Randamu Threshold Association or League of Entropy), and Cealis are distinct legal entities under different jurisdictions, so no single organization controls operators across multiple gates. Residual risk: multi-jurisdictional coordinated legal compulsion — Non-defense 1 territory.

**3. Operator discretion errors or policy drift on reveal content.** A human operator makes a wrong decision that improperly grants or denies a reveal's content. Defense: no operator discretion over reveal content or outcome (§B P13). Reveal content is a pure function of chain events, gate signatures, and commit data (§D). Operators can halt (G4 refusal, vault availability) but cannot alter what a reveal contains. Residual risk: operators can still cause a reveal to fail via availability impact, but cannot cause one to complete incorrectly — halt-or-allow axis, not content axis.

**4. Data tampering post-commit.** An adversary modifies stored ciphertext or AAD to alter revealed content. Defense: h_commit anchors the full envelope on-chain (ciphertext digest, AAD, recipient list, composite-identity spec — §C), the ChaCha20-Poly1305 AEAD binds commit_AAD into decryption so any AAD drift fails the tag check, and stanza-level MACs reject combiner bypass at the plugin layer (§C, §B P9). Three detection layers. Any tamper produces a cryptographically verifiable mismatch. Residual risk: tamper is detected, not prevented — availability can be impacted if tampered records are served and rejected, but no tampered plaintext reaches a recipient.

**5. Classical cryptographic aging — asymmetric primitives weakening over time.** Mathematical or engineering advances weaken X25519, Ed25519, or BLS12-381 over the years. Defense: P21 crypto-aging discipline combines hybrid post-quantum wrapping at commit (ML-KEM-768 with X25519) with periodic stanza-addition re-key ceremonies that add new stanzas under fresh primitives without re-encrypting the payload (§B P21, §M). The symmetric payload cipher (ChaCha20-Poly1305) is believed-secure for decades, including against Grover speedup. Residual risk: see Non-defense 2 — fundamental symmetric-cipher break combined with long-retention ciphertext exfiltration is named honestly as a non-defense.

**6. User-initiated erasure (GDPR Art. 17 and general subject privacy).** The subject wants their committed data erased and must be confident no reveal can occur post-erasure. Defense: the on-chain shred triple block (§E). G1 refuses future authorization because `ConditionEngine.isConditionMet` returns false post-shred. G4 reads ShredRegistry pre-attestation and refuses to sign σ_G4, which crypto-halts in-flight reveals because the G4 share cannot be admitted. The vault physically deletes ciphertext after on-chain confirmation. Residual risk: reveals already completed before shred are unrecoverable — shred is forward-looking by design, not retroactive.

**7. Cross-partner linkability across partnerships.** Multiple partners onboarding the same subject could correlate across partnerships via a shared commitment or a shared passkey pubkey. Defense: `subject_commitment_v3` includes a per-partner namespace derived from `partner_id` and `pda_id` (§C), so the same subject produces different commitments under different partners. σ_subject stays off-chain and is AEAD-bound into commit_AAD in the vault only, so passkey public keys never anchor on-chain. Residual risk: off-chain correlation via a shared KYC vendor across partners is a vendor-level concern, not a Cealis-primitive concern.

**8. Quantum attack on a single asymmetric primitive.** A cryptographically-relevant quantum computer running Shor's algorithm breaks classical elliptic curves — X25519, Ed25519, BLS12-381. Defense: hybrid post-quantum wrapping at commit combines ML-KEM-768 (lattice-based, post-quantum) with X25519 (§B P21). Shor breaks X25519 but not ML-KEM-768, and the hybrid construction requires both primitives to fall before the DEK can be extracted from stanzas. Residual risk: a multi-breakthrough scenario where both lattice problems AND elliptic curves fall within the retention window is a structural limit — no mitigation handles arbitrary far-future cryptographic breaks, same logic as Non-defense 2.

**9. Dormant or staggered-key compromise of a single gate.** An attacker exfiltrates one gate's signing key for offline use while the operator remains unaware. Defense: client-side fail-closed on stale published-operator-state. The gate operators' published state (Lit assignment records, G3 committee pubkey, G4 binary hash or DCAP quote) must match current operational state at commit-time and at reveal-time. An attacker with a stolen key but no capability to modify the operator's published attestation stream fails client verification. Residual risk: if an attacker owns both the key and the capability to modify the operator's published state, detection requires external monitoring — not a Cealis-primitive guarantee.

**10. Legal compulsion targeting a single gate operator.** A court orders one operator to produce decryption capability for a specific reveal. Defense: even under compulsion, the compelled operator can only authorize or release its own gate's share. One share does not yield the DEK; the reveal still requires Lit, G3, G4, and any configured conditional-recipient threshold (§B P3, §B P18, §D). Cross-jurisdictional legal processes to compel all required parties simultaneously are an order of magnitude harder. Separately, when legal compulsion targets shred rather than reveal, Cealis can use G4 refusal to halt reveals crypto-enforced. Residual risk: coordinated multi-jurisdictional legal pressure — Non-defense 1 territory.

### Non-defenses

**1. Simultaneous multi-gate operator compromise.** An adversary compromises Lit operators AND the G3 operator set AND Cealis G4 at the same time, or compels all three through a coordinated multi-jurisdictional legal process. Why not defended: this is the defined upper limit of the trust model — if all operators across all gates fall, the DEK is derivable by the attacker. The same mathematical structure that prevents single-party attack enables full-stack attack when all parties cooperate. Mitigation: disjoint-operator selection (§B P19) makes this expensive, slow, and visible across multiple organizations and jurisdictions — but disjointness doesn't eliminate the threat.

**2. Fundamental symmetric-cipher break combined with long-retention ciphertext exfiltration.** An attacker exfiltrates ciphertext now and sits on it for decades. In year X+N, a fundamental break of ChaCha20-Poly1305 (or AES under Grover speedup beyond the √2 reduction) combines with a break of the hybrid post-quantum wrapping to yield retroactive decryption. Why not fully defended: any persistent ciphertext is vulnerable to far-future cryptographic-break. No mitigation is infinite. Mitigation: the stanza-addition re-key ceremony of P21 adds new stanza-layers under fresh primitives before existing primitives weaken (§B P21, §M); the shred-first lifecycle bias of P21 minimizes the time any given ciphertext exists; hybrid post-quantum means multiple independent primitives must fall. Stanza-addition re-key is forward-protecting only — bytes already in an attacker's possession before the re-key ceremony are not retroactively protected. For short-retention PDAs (where ciphertext gets shredded shortly after the enforcement event, typical KYC windows measured in weeks), this threat is practically eliminated because the exfiltration window is bounded. For long-retention PDAs (testament, archival, evidence), the residual remains: the subject is relying on Cealis's governance continuity to coordinate re-key ceremonies before primitives weaken, and shred-first lifecycle bias does not apply. For long-retention PDAs, the mitigation is operational discipline, not architectural guarantee.

**3. Compromised reveal-side combiner.** An attacker compromises the recipient's combiner process — the context that runs `age-plugin-cealis-v3` after receiving verified gate authorizations — and extracts recovered shares, the DEK, or plaintext. Why not fully defended: the combiner is where verified authorizations cause wrapped Shamir shares to be decapsulated or admitted, `Shamir.combine` reconstructs the DEK, and plaintext is produced. If that context is compromised, recovered shares, DEK, or plaintext may leak. Mitigation: share/decap/DEK/plaintext secrecy, authenticated σ handling, and hardened combiner execution — authenticated channels for gate responses, no on-chain publication of share-bearing material, no transit logging, no intermediate caching, execution context appropriate to the use case (TEE or HSM for regulated recipients, audited process memory with explicit risk statement for consumer recipients). Residual risk: recipient-side trust is the recipient's responsibility — Cealis cannot harden a context it does not operate.

**4. TEE compromise at commit-time under Mode A ingestion.** Under Mode A (TEE-ingest), the Cealis TEE or its underlying hardware vendor is compromised before plaintext destruction, exfiltrating plaintext or the DEK. Why not fully defended: if the execution environment that processes plaintext is compromised, plaintext leaks. TEE attestation raises the bar but does not make compromise impossible. Mitigation: cross-vendor TEE enforcement between Lit's serving TEE and G4's Phase 2 TEE (§B P19), reproducible build and on-chain binary hash registry (§K trust chain links 2-3), and Mode B as an option path for use cases where this threat dominates (§G).

**5. Subject-device compromise at commit-time under Mode B ingestion.** Under Mode B (device-encrypt), the subject's device is compromised during DEK generation or envelope construction. Why not defended: client-side encryption shifts commit-time trust from the Cealis TEE to the subject's device. If the device is compromised, plaintext leaks at the source before ciphertext ever exists. Mitigation: subject's responsibility; Cealis provides a verified client SDK and pre-encryption attestation flows but cannot protect against device-level compromise. Residual risk: device security is the subject's axis of trust under Mode B (§K Mode B chain).

**6. Chain-level attack on Base L1.** An attacker breaks Base L1 consensus or the Ethereum L1 security underlying it. Why not defended: V2 inherits Base's security model; attacks on the L1 layer are out of direct V2 control. Mitigation: Base L1 finality (~13 min) is required before any gate fires — zero reorg tolerance in the reveal path (§D). If L1 consensus itself is broken, no L1-anchored protocol can remain sound.

**7. Side-channel and hardware attacks on TEEs.** Cache-timing, power analysis, Spectre-class, or supply-chain attacks on TEE silicon. Why not fully defended: hardware attacks are a vendor-chain concern and evolve continuously. Mitigation: cross-vendor TEE requirement across gates (§B P19) — a single-vendor side-channel does not propagate to all gates simultaneously. Vendor certification (AWS Nitro DCAP, Intel SGX attestation, AMD SEV-SNP) is the base trust layer. Residual risk: a coordinated side-channel that spans multiple TEE vendors at once is outside the mitigation's scope.

**8. Covert staged compromise of operator sets across years.** An adversary gets Lit's key silently, waits six months, gets the G3 key silently, waits another six months, gets the G4 key, then decrypts ciphertext from the window. Why not fully defended: if each compromise is truly silent and uncorrelated in observation, detection is hard. Mitigation: disjoint-jurisdictional operators (§B P19) plus published operator state plus external monitoring (not a Cealis primitive, an ecosystem consideration). The attacker would need silent compromise in three distinct organizations across three jurisdictions without triggering any internal security or key-rotation process. Residual risk: a patient, well-resourced adversary operating silently across years remains a non-defense.

**9. Legal compulsion on an operator to shred a specific record.** A court orders Cealis (or another operator with shred authority under the PDA) to execute a shred on a specific record. Unlike reveal-side compulsion, shred IS within an operator's power to execute unilaterally when the PDA grants that authority — triggering an on-chain shred event that cascades through the triple block (§E). Posture: this is a policy matter, not a cryptographic vulnerability. The PDA-level `shred_authority_id` parameter configures who can trigger shred — Subject, Joint, Operator, Timelock, or Disabled (§E, §F). For use cases where operator-triggered shred is unacceptable, the PDA is configured with Subject-only shred authority, and Cealis cannot shred unilaterally. The choice is made transparently per PDA at deployment.

**10. Vault availability — Cealis shutdown, service withdrawal, or legal compulsion to stop serving the vault.** Cealis operates the vault; if Cealis stops serving, ciphertext becomes inaccessible even if the chain state and the gate operators remain healthy. Why not fully defended: the vault is Cealis-operated by default, and loss of that operator removes ciphertext availability. Mitigation: option path — open-source vault code plus a federated or third-party vault capability, currently deferred by explicit commit (2026-04-21). The protocol's vanish-path property named in §A and §J item 35 holds for protocol composition (chain + gate operators + envelope format + plugin) — vault availability is a separate operational axis where that vanish-path has operational gaps today. §M covers the storage-side reasoning for the current closed-source vault posture.

**11. Oracle compromise at Tier B/C.** An oracle operator's signing key is stolen or the operator is coerced; the oracle signs a false attestation; AttestationGate verifies the signature correctly (the sig IS valid against the registered pubkey) and the Claim passes; the FSM advances on a false premise. Why not defended: Tier B/C conditions verify the oracle's *assertion* of a fact, not the fact itself. Compromise of the asserting authority propagates to the condition. Mitigation: per-PDA oracle pubkey binding (§C `oracle_references_root`) prevents a compromise of one oracle from cascading platform-wide; k-of-n disjoint-oracle attestation mandated-by-default for irreversible use cases (testament, evidence, archival); per-PDA pause (P24) for bug-response; Tier C explicitly marked in the RevealArtifactBundle so recipients know which trust basis applies. Residual risk: single-oracle Tier B or Tier C compromise can fire a single PDA — the mitigation bounds blast radius, it does not eliminate individual wrong-reveals for PDAs whose partners opted into single-oracle.

**12. Tier A is the strong tripwire; Tier B/C are opt-ins into oracle trust.** The universal tripwire — "no release path bypasses the on-chain-verified predefined condition" — is absolute at Tier A (chain-native conditions where the chain verifies the fact itself). At Tier B/C, the chain verifies the oracle's cryptographically legitimate assertion of the fact, not the fact itself. Why not fully defended: physics. No on-chain mechanism can observe an off-chain event without some off-chain entity asserting it. Mitigation: trust tier declared per PDA at commit-time and carried in the RevealArtifactBundle; partners choose tier based on condition type; high-stakes PDAs default to Tier A where possible and Tier B where unavailable; Tier C requires explicit partner acknowledgment plus mandatory k-of-n disjoint-oracle attestation. Residual: partners who explicitly opt into single-oracle Tier C accept the narrower trust basis, named in the bundle so downstream verifiers see it.

**13. Conditional-recipient bricking for long-TTL PDAs.** A PDA names conditional_recipients under a long-fire-time condition (testament, long-heartbeat DeadManSwitch). All named recipients die, lose all Cealis-account passkeys with no synced backup (Cealis accounts have no recovery by design — see `project_no_account_recovery_by_design.md` referenced 2026-04-24), or lose wallet keys. Threshold k becomes unreachable. Why partially defended: the protocol cannot resurrect dead recipients or recover lost passkeys. Mitigation: `conditional_recipients_updatable = true` default for condition modules with `fire_time_ttl_estimate > 5 years` (§F PDA surface) lets the subject (while alive) refresh recipients as reality changes; configurator validation requires `n ≥ 2k` OR explicit `emergency_response_bricking_acknowledgment` for immutable long-TTL PDAs. Bricking produces an observable diagnostic at reveal ("insufficient σ_conditional threshold reached"), not silent data loss — recipients, partners, and subject estates know the commit exists but is unreachable. Residual risk: PDAs whose subjects chose immutability and then outlived their recipient set are unrevealable; data stays sealed, future-crypto-break-risk management per §M still applies.

**14. PasskeyRotationLog censorship.** Cealis hosts the canonical `PasskeyRotationLog` instance; a compromised Cealis UX could refuse to publish a specific recipient's passkey rotation. Why partially defended: Cealis controls its own publication UI. Mitigation: the `PasskeyRotationLog` is an ABI standard, not a singleton — recipients can self-publish their rotation via permissionless contract call on any ABI-compatible deployment (§C). Censorship degrades to "recipient's current passkey is stuck at the current form" — a reveal works if the current passkey is still available to sign σ_conditional. Residual risk: if Cealis censors AND recipient cannot self-publish AND the current passkey dies before the PDA fires, rotation is frozen and that recipient slot becomes unreachable. Composes with #13 bricking above.

**15. Emergency-response multisig compromise (Governance Phase 1).** Attacker compromises the device holding ≥ 2 of 3 `CealisSecurityMultisig` keys at V2 launch (where all three seats are Cealis-held). Attacker deprecates canonical plugin or G4 authority entries, halting all commits using them. Why not fully defended at Phase 1: phase disclosure — the three-seat independence does not yet hold. Mitigation: 72h auto-clear absent on-chain `publishDisclosure` with keccak-verified content binding (§F, §N), 30-day re-deprecation cooldown after auto-clear, 24h expedited TimelockController delay on canonical-in-use deprecations, and `EmergencyGovernance` 3-of-3 circuit breaker that can suspend the Security Multisig for up to 7 days if compromise is suspected. Ransomware leverage caps at `24h delay + 72h halt` per canonical entry with 30-day cooldown per re-attempt; payment is not required to wait out the halt. Phase 2 (external advisor seated, distinct security domain) materially hardens this — at Phase 2 the 2-of-3 property is live. Residual at Phase 1: a compromised Cealis device can ransom the platform for several days per affected canonical entry; Phase-1-present public copy must surface this honestly (§K item 10).

**16. Adversarial halt of specific in-flight reveals via governance collusion.** A well-resourced actor gaining by delaying a specific high-stakes reveal (contested M&A reveal, adverse testament) colludes with the Security Multisig to deprecate the relevant plugin/authority mid-ceremony. Defense: the gate-signing window is a halt-impossibility window by architectural design (§D, §E, §B P11 mandatory shred guardrail). Deprecation flags set AFTER `RevealAuthorized` + Lit assignment do not halt the in-flight commit — verifier reads deprecation state at the authorization block, not current. Residual: risk remains for reveals that have not yet reached `RevealAuthorized`; those can be halted by pre-authorization deprecation, but that halt is visible on-chain with reason code and 24h/72h bounds, not silent.

**17. Cealis class-wide halt as commercial trust surface.** Institutional partners (commercial-lending, regulated-finance) whose enforcement-timing is contractually guaranteed may view Cealis's class-wide deprecation halt as a new trust surface they cannot accept. Why: Cealis gains release-timing authority (halt-only, halt-direction, bounded) that it previously did not hold. Defense: `cealis_class_wide_halt_opt_out` PDA field (§F) — partners contractually requiring no-halt opt their PDAs out entirely. AAD-bound, visible to recipients at reveal. G4 emits reason code `0x0A opt_out_active` on would-be deprecation refusals for opted-out PDAs. Trade-off: partners accepting opt-out accept vulnerability-window risk in exchange for uninterrupted enforcement. Residual: opt-out PDAs inherit the vulnerability for as long as the deprecation stands; Cealis's class-wide halt power is bounded but not zero, and institutional partners must weigh this explicitly at partner-contracting time. **Forbidden on legal-effect PDAs** by the §F Art. 22 safeguard guardrail (conjunct 5): `cealis_class_wide_halt_opt_out = true` is rejected by the configurator when `legal_effect_expected = true`, because the same halt is the Art. 22(3)(a) human-intervention endpoint for Tier B/C legal-effect PDAs and erodes the pre-commit-consent + chain-trigger backstop for Tier A legal-effect PDAs. The trade-off is available only on non-legal-effect PDAs where no Art. 22 surface needs preservation.

**18. Public on-chain disclosure of fundamental-rights exercise.** Without mitigation, G4 refusing a reveal under reason `0x02` (subject Art. 17 erasure received) or `0x03` (subject Art. 18 restriction) and emitting the plaintext reason code on-chain leaks "subject X exercised a fundamental GDPR right at time T for commit Y" to anyone scanning the chain. The reason code itself becomes Art. 4(1) personal data, and the public emission collides with Art. 5(1)(a) transparency-toward-subject and Art. 5(1)(c) data-minimization. Defense: the §F PDA+ "Refusal-reason encryption guardrail" defaults reason codes `0x02` and `0x03` to encrypted-reason mode across all PDAs — G4RefusalRegistry stores `encrypted_reason_blob` rather than plaintext, decryptable only by the partner's resolver flow plus regulators with subpoena authority; the on-chain event emits only `RefusalSignal(authorizationId, "refused")`. Public-reason mode for these codes is opt-in only with explicit subject acknowledgment + partner attestation. Residual: the refusal event itself is on-chain visible (timing leak — anyone observing knows that authorizationId X was refused at time T), but the reason — and therefore the rights-exercise — is opaque to non-partner observers. Reason codes `0x01`, `0x04`, `0x05`, `0x06`–`0x0A` default to public-reason because they describe operational refusals (legal compulsion, integrity, infrastructure deprecation), not subject rights-exercise.

### Out of scope

These are threats §L explicitly does not treat. Each is out of scope for a specific structural reason.

- **Identity verification itself** — delegated to the attestor or KYC provider; the system anchors the attestation but does not verify the identity (§B P14, §I).
- **eIDAS-qualified signature disputes** — σ_subject is evidentiary, not a qualified electronic signature under eIDAS.
- **General partial disclosure of arbitrary predicates** — SD supports per-predicate circuits, and new predicates require new circuits (§B P5, §H).
- **Recovery of lost subject device keys** — passkey recovery is a subject-device vendor concern, acknowledged as known-open work (see §A).
- **Content-level disputes** — Cealis does not arbitrate whether committed data is correct or true; the system anchors what was committed, not what is true.

Operational commitments around crypto-aging and shred lifecycle are in §M; per-phase operational posture is in §N; structural limits of what the system cannot do are in §O.

## §M — Storage + crypto-aging

§M covers where ciphertext lives and how it ages over time. Two levels. Storage architecture: the off-chain vault (Cealis-operated, closed-source by explicit commit, hardened access control) plus the intentionally thin on-chain footprint. Crypto-aging commitment: hybrid post-quantum wrapping at commit, periodic stanza-addition re-key ceremony, shred-first lifecycle bias. Long-horizon safety is an operational commitment, not an architectural guarantee — §M names what the operational commitment is. §L covers what this defends and does not defend against; §M covers the storage mechanism and the aging discipline.

### Vault architecture

Ciphertext (the age envelope, commit_AAD, σ_subject, and metadata) lives off-chain in a Cealis-operated vault. Four architectural properties.

**Append-only audit logs.** The `vault_audit_log` table is append-only — no updates, no deletes, enforced by a database trigger. The append-only property supports chain-of-custody integrity under §286 ZPO free-evaluation by default, and additionally supports §371a ZPO Anscheinsbeweis for PDAs that have elected QTSP integration (`qes_subject_required = true`) where σ_subject is QES-grade.

**Crypto-shred support.** On-chain shred (§E) emits a state change that the vault listens for. After on-chain confirmation the vault physically removes the ciphertext bytes from storage — actual byte removal, not a soft-delete and not a tombstone. The triple block (§E) depends on the vault actually deleting, not just marking deleted.

**Access control.** The partner API uses HMAC-signed requests plus bcrypt-hashed credentials. Subject authentication uses WebAuthn passkeys or EIP-712 wallet signatures with session tokens. The vault runs on hardened infrastructure with rate limits, structured error handling, and request-level audit logs. Access control is the property the vault carries at runtime — the threat model gets this layer specifically because the ciphertext sits behind it.

Vault infrastructure itself has a Phase 1 / Phase 2 posture analogous to §N's G4 treatment. Phase 1 (pilot) runs on a managed cloud platform appropriate to pre-funding operational scale; Phase 2 (production) runs on self-hosted or dedicated cloud infrastructure with tighter operational controls and clearer audit surface. The transition is API-compatible for partners and subjects, same discipline §N applies to G4. Vault-side Phase 2 is separable from G4 Phase 2 — the two transitions are independent, each tied to its own funding and operational readiness.

**Closed-source code by explicit commit (2026-04-21).** The vault code is not open-sourced. This is a deliberate choice, interrogated against the threat model rather than a reflex — the reasoning is in the Considered-and-rejected subsection below, and §K item 5 names the scope of what is open vs closed across the platform.

**Vault migration path.** If Cealis-the-vault-operator stops serving, existing commitments' ciphertext transitions via export-compatible copy. The vault schema — ciphertext blobs, `σ_subject` storage, metadata, and the append-only `vault_audit_log` — is exportable; on-chain `h_commit` continues to anchor the migrated bytes unchanged; no re-commitment needed. Successor vault operator inherits the append-only audit log as historical chain-of-custody record. Migration mechanics sit outside protocol and inside operational-continuity posture (§N).

**Plugin distribution.** Recipients need the `age-plugin-cealis-v3` binary to reconstruct file_key and decrypt. Cealis publishes signed binary releases under reproducible-build discipline; source is open. Recipients either use a Cealis-published binary (verified against PluginHashRegistry state at the commit's block, not current state) or build locally from source and verify the resulting hash against registry state. Either path produces the combiner that verifies σ authorization, decaps wrapped Shamir shares, and reconstructs file_key via Shamir.combine.

### On-chain footprint

The on-chain footprint is intentionally thin. What lives on-chain:

- `h_commit` — the digest anchor for the envelope (ciphertext, AAD, recipients, attestations).
- `ConditionEngine` module state — per-PDA condition logic and per-authorizationId evaluation state.
- `G4AuthorityRegistry` — G4 authority key rotation tuples. 7-day TimelockController on additions; `DeprecationFlag` on individual entries (governed by `CealisSecurityMultisig`, §F, §N).
- `PluginHashRegistry` — canonical `age-plugin-cealis-v3` binary hashes. Same governance shape (7-day on additions, DeprecationFlag on individual entries).
- `DSLVersionRegistry` — Claim DSL interpreter contract versions. Same governance shape.
- `OracleRegistry` — oracle source pubkeys. Same governance shape.
- `QTSPRegistry` — approved EU Qualified Trust Service Providers (D-Trust, Bundesdruckerei, future Cealis-issued QTSP, etc.) whose Qualified Electronic Signatures are accepted as σ_subject when a PDA elects `qes_subject_required = true` (§F). Same governance shape: 7-day TimelockController on additions, per-entry `DeprecationFlag` governed by `CealisSecurityMultisig` (24h expedited delay for canonical-in-use entries, 72h auto-clear absent on-chain disclosure). Recipients verify σ_subject's QTSP signature chain against registry state at the commit's block, not current.
- `PasskeyRotationLog` (ABI-standard contract with Cealis canonical instance) — per-Cealis-account passkey rotation entries, each signed by the prior passkey (§C).
- `CealisSecurityMultisig` and `EmergencyGovernance` — emergency-response governance contracts (§F, §N). Both UUPS-upgradeable via TimelockController.
- `LitV3Assignment` records — per-commit Lit serving-TEE assignment.
- `ShredRegistry` — per-commit shred state (binary, permanent once set).
- `G4RefusalRegistry` — on-chain refusal signals with reason codes 0x01-0x09 and the substantiating `proof` field (§N).
- Event log — reveal lifecycle events (authorizations, challenges, resolutions, deliveries, shreds, deprecations, disclosure publications).

No plaintext, no ciphertext, no identifying data on-chain. Only hashes, state flags, timestamps, and public-key references.

### Cryptographic primitives and their aging horizons

Seven layers carry primitives. Each has a different aging horizon and a different mitigation strategy if the primitive weakens.

- **Payload encryption — ChaCha20-Poly1305 symmetric AEAD.** Multi-decade horizon. Grover's algorithm halves the effective key strength (256 → 128-bit) but the payload cipher remains secure well beyond any foreseeable retention window. No action needed within the foreseeable horizon.

- **AEAD nonce / SD salt derivation — HKDF-SHA256.** Multi-decade horizon. Similar Grover argument. No action needed.

- **Commitment and AAD hashing — Keccak-256.** Multi-decade horizon. Same Grover argument. No action needed.

- **DEK wrapping, asymmetric — X25519 (classical ECDH).** Medium horizon, roughly 10-20 years classically, quantum-broken by Shor on a cryptographically-relevant quantum computer. Mitigation: hybrid with ML-KEM-768 at every commit (see three-part discipline below).

- **DEK wrapping, post-quantum — ML-KEM-768 (lattice-based KEM).** Post-quantum resistant by design, but newer primitive with a shorter cryptanalytic track record. Mitigation: monitor for cryptanalytic advances, add a new stanza under a fresh primitive if weakening signs emerge.

- **Gate signatures — BLS12-381 (Lit and G3) and Ed25519 (G4 Phase 1).** Classical primitives, quantum-broken by Shor on a cryptographically-relevant quantum computer. Mitigation: rotate to post-quantum signatures (Dilithium, Falcon, or equivalent) via gate-operator protocol upgrades as the ecosystem matures.

- **Subject consent — WebAuthn P-256.** Classical, quantum-broken by Shor. Mitigation: subject-device upgrade path through the passkey platform ecosystem — new passkey primitives propagate through vendors, and the system accepts upgraded subject keys without protocol-level change.

Full primitive pins with library versions live in `flows-spec-final.md` §0.12.

### Crypto-aging three-part discipline

The system commits to three operational practices for handling primitive aging. Per P21.

**1. Hybrid post-quantum wrapping at commit.** Every age envelope's DEK-wrapping stanzas use an ML-KEM-768 + X25519 hybrid construction at commit. The wrapping requires an attacker to break both primitives to extract the DEK from any stanza — Shor breaks X25519 but does not break ML-KEM-768, and a lattice-problem break would not help without also breaking the elliptic-curve layer. Hybrid-at-commit is the baseline that every commit carries forward, not a later add-on.

**2. Periodic stanza-addition re-key ceremony.** When a wrapping primitive shows signs of weakening — external cryptanalytic advance, vendor advisory, risk-register threshold crossed — the platform initiates a re-key ceremony. Governance trigger, 7-day timelock on ceremony initiation. New stanzas are added to the existing age envelope, re-wrapping the same indexed Shamir shares under the new primitive where re-wrapping is required. Payload bytes never touched — the ChaCha20-Poly1305-encrypted payload is not re-encrypted, only the share-wrapping layer grows a new stanza generation. The wrap material grows additively at the stanza layer; file_key reconstruction remains stable because Shamir.combine reconstructs the same commit-time DEK from the same share values. Old stanzas continue to verify under their frozen primitives until governance-deprecated, giving a deprecation window for client upgrade and stanza retirement. For conditional_recipients whose delivery mode permits automatic re-signing (Mode 1 PASSKEY_ACCOUNT requires interactive WebAuthn assertion; Mode 2 WALLET_EOA requires wallet interaction), the re-key ceremony becomes a user-coordinated event rather than a fully automated one — acceptable for rare long-horizon events, not for routine operation.

Monitoring for primitive-weakening signals is continuous: NIST post-quantum guidance updates, hardware-vendor cryptanalytic advisories, published research advances on ML-KEM, X25519, BLS12-381, Ed25519, Keccak, or ChaCha20-Poly1305. The governance trigger for a re-key ceremony surfaces when a signal crosses a documented risk-register threshold. §N names Cealis's operational-continuity role for the platform's long-horizon commitments — the subject relies on Cealis's governance continuity to notice the signals and coordinate the ceremony before primitives actually break.

**3. Shred-first lifecycle bias.** For PDAs where the use case permits, shred happens as soon as the retention window closes — not later. Physically-deleted ciphertext has zero future-crypto-break exposure because the bytes do not exist to be attacked. Shred-first turns the retention window itself into a mitigation surface: the shorter the window, the smaller the future-crypto-break attack surface.

These three are mitigations. No architectural silver bullet. For long-retention PDAs the subject is relying on Cealis's governance continuity to coordinate re-key ceremonies when they become necessary.

### Considered and rejected alternatives

Three alternatives were considered and rejected against the threat model. Each is named with the reasoning.

**1. On-chain vault (ciphertext stored on-chain).** Considered for trust-minimization — removes the "Cealis shuts down the vault" threat (§L Non-defense 10). Rejected because on-chain ciphertext is public-by-design. Any future cryptographic break becomes a mass leak simultaneously across all historical records, with no prior breach required. Off-chain vault with access control is strictly better on this axis: an attacker needs both a prior breach and a crypto-break, in sequence, to extract plaintext. On-chain removes the access-control barrier entirely. Additional costs: storage at scale, metadata leakage via access patterns, and permanence that weakens crypto-shred's future-protection property. Decision: off-chain vault stays as default. On-chain vault may return as a per-PDA option for small-data short-retention trust-minimization cases, not as the default.

**2. Open-source vault code as default transparency.** Considered for audit transparency and potential distributed-operator structure. Interrogated against the threat model and found not to address the threats the vault actually faces: code openness does not change who has the ciphertext bytes (openness ≠ data distribution); code openness does not address future-crypto-break plus prior-breach (no code change helps bytes already exfiltrated); code openness does not address reveal-time share/decap/DEK/plaintext secrecy and authenticated sigma handling (those threats live at transport and combiner layers, not storage). What open-sourcing would buy: third-party shred-verification and the option of distributed-or-federated vault operation. Decision: closed-source by explicit commit for now. Revisit if distributed-vault-operator structure or shred-verification audit becomes an active requirement. §K item 5 names the scope of what is open across the platform; §M's closed-source choice for the vault is the threat-model-specific one.

**3. Information-theoretic security — one-time pad or perfect secret sharing.** Considered for true crypto-break immunity. Rejected because it requires key material as long as the data (one-time pad) or N non-colluding parties forever (perfect secret sharing). Operationally painful at any realistic scale. Does not compose with V3 custody's gate-signature model. Decision: not a realistic direction for V2. The answer to long-horizon risk is lifecycle discipline plus stacking re-key plus hybrid PQ plus access control, not information-theoretic primitives.

### Honest closing

V2 stores ciphertext off-chain in a hardened Cealis-operated vault with closed-source code, append-only audit logs, and crypto-shred discipline. Cryptographic primitives age over time. V2 handles aging through three operational commitments: hybrid post-quantum wrapping at every commit, periodic stanza-addition re-key ceremonies that add new wrapping under fresh primitives without touching the payload, and shred-first lifecycle bias where the use case permits. No architectural choice makes stored ciphertext safe forever. V2's long-horizon safety is an operational commitment to periodic re-keying and aggressive shredding — not a silver bullet.

## §N — Operational posture

§N covers the gate-side and company-side operational commitments. Three parts. The Phase 1 → Phase 2 swap discipline for G4 — what the phases are, what changes at swap, and what the phase swap does not retroactively buy for commits made under the earlier phase. The commodity-rental economic argument — why the substrate is composed of rented commodity networks rather than a Cealis-operated staked custody network, and what the per-gate cost profile actually is. And Cealis's identity as a company — commercial operator of the protocol, configurator Cealis-internal, worst-case open-source, vanish-path named as structural property. §M owns the storage-side operational commitment (vault, crypto-aging, re-key ceremony). §N owns the gate-side and company-side. Structural limits of what the system cannot do live in §O. Open-ended compositional possibilities live in §P.

### Phase 1 → Phase 2 G4 swap discipline

Phase 1 is the pre-funding development scaffold. G4 runs as a standard Linux daemon on Cealis-hosted infrastructure. The binary is reproducible-build and the source is open. The binary hash is registered on-chain via the `G4AuthorityRegistry` contract using `(hash, effective_block, tombstone_block)` tuples, so recipients verify against the commit's block rather than current registry state. Hash rotations emit `G4AuthorityUpdate` events and pass through a minimum 7-day governance timelock, so any attempt to swap the running binary is publicly visible at least 7 days in advance. The Phase 1 attestation is an Ed25519 signature over `binary_hash ‖ block_hash ‖ authorizationId ‖ h_commit ‖ timestamp`.

Phase 1 ingestion is plaintext-trust-in-Cealis-during-ingestion. Under Mode A ingestion in Phase 1, the subject's plaintext transits Cealis server memory briefly before the envelope is sealed. The user is trusting the registered binary plus the open-source code plus the on-chain hash registry plus the audit chain — institutional trust, not cryptographic non-custody. Phase 1 is operational-grade attestation and the underlying chain-of-custody surface is below the §286 ZPO free-evaluation strength that Phase 2 carries. Phase 1's role in the system is pre-funding development and internal validation of the swap discipline — it is not the pilot runtime. Partner-facing commits do not land under Phase 1 attestation. Mode B (§G) remains the orthogonal path for use cases that require cryptographic non-custody even at ingestion, independent of the Phase 1/2 axis.

Phase 2 is the post-funding configuration. G4 runs inside a rented TEE (AWS Nitro Enclave or equivalent) at approximately €250/mo rental. The attestation is a DCAP quote whose `user_data` field is bound to `authorizationId ‖ h_commit ‖ block_hash`, verified on-chain via Automata zkDCAP. Cross-vendor is required — if Lit's serving TEE for a given op is Intel SGX, G4's TEE must be AMD SEV-SNP or AWS Nitro, so a single-vendor PKI break does not compromise both gates (§B P19). Under Phase 2 the plaintext enters a hardware-sealed boundary at ingestion rather than plaintext-in-server-memory, which upgrades the legal-admissibility grade — the hardware-attested chain of custody anchors §286 ZPO free-evaluation admissibility as default and additionally satisfies §371a ZPO Anscheinsbeweis for PDAs that have elected QTSP integration via `qes_subject_required = true` (§F). The trust chain stays institutional for consumer users — §K item 4 names it at per-link granularity. An important distinction across phases: Cealis operates the G4 role and signs σ_G4 in both phases, but the TEE infrastructure under Phase 2 is rented commodity, not Cealis-operated silicon. Cealis does not own the hardware.

**Phase anchor at pilot.** Pilot launches on Phase 2 — the HSM TEE configuration. Phase 1 is the pre-funding development scaffold and the API-compatible fallback used to validate swap discipline without blocking pilot readiness. The anchor follows from the economic argument below: the funding that unblocks Phase 2 co-arrives with the first partner signing, so partner-signing ≈ funding-arriving, so pilot-runtime ≈ Phase-2-grade. Partner-facing PDAs are committed under Phase 2 attestation. The §286 ZPO free-evaluation admissibility claims in §K and §M are accurate for pilot because pilot is Phase 2; the additional §371a Anscheinsbeweis claim is accurate for PDAs that have elected QTSP integration. Neither claim transfers to Phase 1 context. A PDA+ guardrail (§F) enforces this at the configurator layer — legal-effect PDA types (KYC-lending, M&A, evidence, medical) cannot be committed under Phase 1 G4.

The swap is an API-compatible drop-in. What changes at swap: the attestation primitive (Ed25519 → DCAP quote), the host environment (daemon → rented TEE), the legal-admissibility grade for the G4 attestation chain (operational → eIDAS-AES-aligned). What does not change: the 4-gate composition, the commit and reveal ceremonies, the age envelope format, the ConditionEngine API, the vault format, the chain contracts, and the Lit V3 + G3 rental integration. Phase 1 dev-scaffold commits remain valid under Phase 1 attestation after the cutover — recipients verify against `G4AuthorityRegistry` state at the commit's block, not current state, and the registry's tombstone tuples keep old attestation paths verifiable indefinitely. A dev-scaffold commit migrated to pilot would require re-commit under Phase 2 with σ_subject re-signed over the new commit — but because pilot is Phase 2 from commit-zero, this migration is not a partner-facing concern. The honest close: the swap discipline is carried to preserve the future-proofing property and to validate the phase mechanism, not because Phase 1 hosts real subjects.

**QTSP backward-compat (where `qes_subject_required = true` is in scope).** σ_subject sourced from a registered QTSP per `qtsp_provider_ref` verifies against `QTSPRegistry` state at the commit's block, not current state — same backward-compat pattern as G4AuthorityRegistry. A QTSP rotating its signing root, being deprecated under the asymmetric registry governance (§F), or being struck from the EU Trusted List leaves prior QES-anchored σ_subject signatures verifiable indefinitely against the original registry entry. Combiners must keep the verification path for prior QTSP entries available; this is part of the live operational discipline P25 commits to (§B P25, §O bounded-extension limit). §371a ZPO admissibility for QES-bound commits is anchored to the σ_subject's QES status at commit time, not at reveal time — German court practice on §371a treats the Anscheinsbeweis as conditioned on the signature being qualified at the time of signing. Rotation of QTSP roots after the commit does not retroactively degrade admissibility.

### G4 refusal scope — bounded reason-code enum

G4 refusal has a closed, on-chain, reason-code-enumerated scope. Refusal is not free-form Cealis veto and not an external-oracle predicate. `G4RefusalRegistry.refuse(authorizationId, reason_code, proof)` emits an on-chain refusal bound to one of ten reason codes:

| Code | Meaning | Origin |
|---|---|---|
| `0x01` | Legal compel | Court order received; Cealis ops sign refusal |
| `0x02` | GDPR Art. 17 | Subject erasure received mid-flight; shred propagation |
| `0x03` | GDPR Art. 18 | Subject restriction / processing-freeze |
| `0x04` | Integrity fail | Per-commit integrity failure in G4's own state |
| `0x05` | Chain mismatch | ConditionEngine state doesn't match G4's independent read |
| `0x06` | Plugin deprecated | Commit's plugin hash is flagged in PluginHashRegistry |
| `0x07` | Authority deprecated | Commit's G4 authority key is flagged in G4AuthorityRegistry |
| `0x08` | DSL deprecated | Commit's DSL version is flagged in DSLVersionRegistry |
| `0x09` | Oracle deprecated | An oracle pinned in the commit's condition is flagged in OracleRegistry |
| `0x0A` | Opt-out active | PDA has `cealis_class_wide_halt_opt_out = true`; deprecation ignored |

The enum is governed by 7-day TimelockController — new reason codes take 7 days to activate and emit `G4ReasonEnumUpdate` events. Each refusal emits publicly; the `proof` field carries the substantiating attestation (court order reference, subject erasure notice, detected integrity failure, chain-state delta, or for `0x06`-`0x09` the `(registry_name, entry_id, deprecation_block, disclosure_cid)` tuple that identifies the specific deprecated entry). Condition authors compose `NOT g4_refusal_standing(authId)` as a Mode P DSL operand (§F "Condition detection" state-read operands) when a PDA's condition layer wants to halt on any live G4 refusal.

Codes `0x01`-`0x05` carry per-commit semantics — the refusal attaches to a specific authorization. Codes `0x06`-`0x09` carry class-wide semantics — the same underlying deprecation affects all pending commits pinned to the deprecated registry entry; G4 emits an individual refusal per authorization but the `proof` field cross-references the shared deprecation event for operational grouping. Code `0x0A` is emitted when a PDA's partner has opted out of Cealis class-wide deprecation halts (§F `cealis_class_wide_halt_opt_out`) — the reveal proceeds under the original (now-deprecated) registry entry, the opt-out status is AAD-bound and visible in the RevealArtifactBundle so downstream verifiers see the trust-basis trade-off.

Under Phase 2, refusal is crypto-enforced — G4 not signing σ_G4 means the G4 share cannot be admitted and the Shamir threshold is not met (§D). Under Phase 1, refusal is operational-grade — the Cealis-operated daemon respects the registry state but the attestation chain is not TEE-bound. Pilot commits land under Phase 2 per the phase anchor above; Phase 1 refusal behavior is scaffold, not pilot runtime.

### Emergency response — asymmetric registry governance

Registry additions (new plugin hashes, G4 authority keys, DSL versions, oracle sources) pass 7-day TimelockController so recipients can observe incoming changes and react. A symmetric 7-day timelock on removals would block fast response to in-the-wild vulnerabilities — the 7-day window IS the exploitation window. The platform resolves this asymmetrically: the 7-day timelock stays on ADDITIONS; DEPRECATIONS travel a bounded fast path via `CealisSecurityMultisig` (§F).

**Deprecation authority.** Each entry across the five Cealis-governed V3 registries (`PluginHashRegistry`, `G4AuthorityRegistry`, `DSLVersionRegistry`, `OracleRegistry`, `QTSPRegistry`) carries a `DeprecationFlag` settable by `CealisSecurityMultisig` (2-of-3). Non-canonical entries (historical, superseded, tombstoned) deprecate instantly. The current canonical-in-use entry in each registry — the most recently added non-tombstoned non-deprecated entry at the deprecation proposal block — adds a 24h expedited TimelockController delay (partner/recipient observation window). During the 24h delay, any address can emit `ChallengeDeprecation(registry, entry_id, reason)` events to register opposition; observation does not block, but creates a public record.

**On-chain-verifiable disclosure.** Every deprecation tx binds `(entry_id, reason_code, disclosure_cid, disclosure_commit_hash)`. Within 72h of the deprecation's block timestamp, any party can call `publishDisclosure(entry_id, bytes summary_content)` which verifies `keccak256(summary_content) == disclosure_commit_hash`; if the verification passes, the contract emits `DisclosurePublished(entry_id, summary_content)` and sets `disclosure_verified_block = current_block`. The summary content lands in event logs (retrievable indefinitely via archive nodes); the full advisory lives on IPFS at `disclosure_cid`. Summary content is capped at 4 KiB to fit within practical Base gas budgets. If no `publishDisclosure` call lands within 72h, the flag auto-clears — any address calls `triggerAutoClear(entry_id)` once the timestamp threshold is reached and the flag is absent of disclosure verification. After auto-clear, re-deprecation of the same entry within 30 days requires 7-day TimelockController, preventing ping-pong halts without accountability.

**DeprecationReason enum** (separate from G4 refusal enum). Closed, TimelockController-extensible. `0x01` active exploit · `0x02` disclosed-but-unexploited vulnerability · `0x03` compromised operator/authority · `0x04` governance-initiated retirement.

**Crypto-enforced halt mechanics.** Three layers.
- The `age-plugin-cealis-v3` plugin reads `DeprecationFlag` state for its own binary hash on load against `PluginHashRegistry` at the `RevealAuthorized` block. Deprecated and not auto-cleared → plugin aborts before Shamir reconstruction.
- G4 reads deprecation state for all registry entries referenced by the commit's AAD at the `RevealAuthorized` block; any deprecated → refuses σ_G4 with the relevant `0x06`-`0x09` reason code (or emits `0x0A` + proceeds if the PDA opted out).
- The combiner independently reads deprecation state for the same entries at the same block; any deprecated → aborts.

All three are share-admission halts, same crypto-enforced path σ_G4 refusal uses for `0x01`-`0x05`. No operational-honesty dependency.

**In-flight reveal protection.** The `RevealAuthorized` block + Lit V3 assignment record together define the "in-flight" boundary. Deprecation flags set AFTER that boundary do not halt the in-flight ceremony — verifiers check deprecation state at the authorization block, not current. This matches the gate-signing halt-impossibility discipline from shred (§B P11, §E mandatory guardrail) and forecloses adversarial halt of specific high-stakes reveals via governance collusion (§L defense #16). Pending commits (pre-`RevealAuthorized`) and new ingestion (2-phase ingestion precheck, §F) do block on deprecation.

**Circuit breaker.** `EmergencyGovernance` is a 3-of-3 threshold contract distinct from `CealisSecurityMultisig` that can suspend the Security Multisig's deprecation authority for up to 7 days. Used only when the Security Multisig is suspected compromised. At Governance Phase 1 (Cealis-all-keys), 3-of-3 collapses to Cealis-alone; at Phase 2 (external advisor seated), real cross-domain independence.

### Governance Phase 1 / Phase 2 — honest posture

Both `CealisSecurityMultisig` and `EmergencyGovernance` exist as contracts from V2 launch, but at launch all three seats on each are Cealis-held pending external-advisor seating. **This is Governance Phase 1.** The 2-of-3 cross-domain-independence story is a Phase 2 property, not a Phase 1 property. Phase 1 posture — surfaced in §K item 10 and §L defense #15 without Phase-2 overclaims — is that the Multisig buys process friction (key separation across devices) and on-chain visibility, not independent-domain defense.

**Phase 2 transition trigger (concrete).** Phase 2 completes before the first paying partner signs a commercial agreement (observable as a `partnerRegistered` event on the PartnerRegistry contract) OR within 90 calendar days of V2 launch, whichever fires first. If neither trigger fires, new partner onboarding halts until Phase 2 is achieved. The trigger rides the same business event as G4 Phase 2 — partner signing ≈ funding arriving — so Governance Phase 2 and G4 Phase 2 transition together rather than on independent clocks.

**Phase 1 disclosure discipline.** Any public copy or partner material that describes the emergency-response story during Phase 1 MUST use outcome-language that names both the current (Cealis-all-keys) and target (external-advisor-seated) forms. §K item 10 carries the required wording; Rule 30 (§K cross-check for public copy) binds every Phase-1-present draft against that discipline.

**Privacy mode — default-encrypted for fundamental-rights-exercise codes.** Reason codes are on-chain and visible by default, but reason `0x02 GDPR Art. 17 erasure` and reason `0x03 GDPR Art. 18 restriction` are themselves personal data — they record that a specific subject (h_commit linkable to subject by partner) exercised a fundamental GDPR right at a specific time. A public emission of `0x02` or `0x03` leaks the exercise of these rights to anyone scanning the chain, which is itself an Art. 5(1)(c) data-minimization concern and an Art. 5(1)(a) transparency concern. Default policy is therefore **encrypted-reason mode for `0x02` and `0x03` across all PDAs**: G4RefusalRegistry stores `encrypted_reason_blob` rather than the plaintext reason code; the encryption key is partner-controlled and reveals only to the partner's resolver flow plus regulators with subpoena authority. The on-chain event emits only `RefusalSignal(authorizationId, "refused")` without the reason. The encrypted-reason path preserves auditability for the designated regulator while closing the public leak. Other reason codes (`0x01` legal compel, `0x04` integrity fail, `0x05` chain mismatch, deprecation codes `0x06`–`0x0A`) default to public-reason mode because they describe operational refusals (legal compulsion, integrity, infrastructure) that do not encode subject-exercise of fundamental rights. PDA+ allows per-PDA opt-out (public-reason mode for `0x02` / `0x03`) only with explicit subject acknowledgment AND partner attestation that public-reason mode does not adversely affect the subject's rights. The configurator surfaces the trade-off at PDA configuration time. Carried through the §F PDA+ "refusal-reason encryption guardrail" below.

**Legal positioning consequences.** Reason `0x01` (legal compel) subsumes what earlier drafts described as a predicate-gated legal-retention-order attestor — legal retention orders route through Cealis ops receiving legal papers and Cealis signing the refusal under `0x01`, no external court_oracle required. Reason `0x03` (Art. 18) is a first-class restriction-right lever and is the substantive infrastructure for Art. 22(3) human-intervention safeguards (§F Challenge window resolution). Reason `0x02` (Art. 17) handles the mid-reveal erasure race — subject shred registered mid-ceremony, G4 refuses in-flight reveals before the G4 share can be admitted. Cealis is the controller at G4 for this processing step (§N Cealis's identity as company and §K item 8 banned-phrasing replacement) — the concession is honest and is the structural reason G4 refusal is a meaningful GDPR-level halt mechanism rather than a theoretical one.

### Commodity-rental economic argument

The alternative architecture would be a Cealis-operated staked custody network. Staking to absorb a $20M partner obligation requires an economic-security floor of roughly $40-80M per partner. Unbootstrappable pre-funding, and not the kind of capital outlay a startup can carry across its first handful of partners. Commodity rental dissolves the constraint. Cealis doesn't stake a network; Cealis rents signing capability from networks that exist for other reasons. Lit's operator pool exists because Lit Protocol runs programmatic signing for many applications. League of Entropy exists because drand produces public-good randomness. Randamu Threshold Association exists as a Swiss non-profit running threshold identity-based encryption. Each of these pre-dates Cealis and runs without Cealis, so Cealis pays per-operation rather than bootstrapping a network.

The customer-relationship structure matters for vanish-path. When Cealis rents signing capability, Cealis is a *customer* of these networks, not a protocol participant in them. Cost is operational, not capital. Commitment is contractual, not cryptographic. If Cealis stops paying a particular commodity network, Cealis's operational ability to initiate *new* commits under that gate stops — but existing-commit reveals continue because gate operators sign against chain state regardless of who authored the commit. The signing payload is a function of `authorizationId`, `h_commit`, and `block_hash`; who paid for the signing request at commit-time doesn't enter the reveal-time function. This is load-bearing for §J item 35.

Per-gate cost profile for the full-engine surface:

- **G1 Chain.** Base L1 gas per transaction — standard DeFi infrastructure cost, per-commit and per-reveal.
- **G2 Lit V3.** Approximately $0.01 per signing operation across roughly 30 permissionless operators. Rental, not staking.
- **G3 dcipher.** Rental; pricing pending direct vendor confirmation.
- **G3 drand.** Public-good access, no per-call fee.
- **G4 Phase 1.** Approximately €250/mo for Cealis-operated server infrastructure. Cealis signs σ_G4 but holds no decryption-capable key — σ_G4 authorizes only the G4 share, and that share alone yields no DEK (§B P18).
- **G4 Phase 2.** Approximately €250/mo for rented TEE capacity. Same "no decryption-capable key" property as Phase 1.

Launch custody posture is all four gates required from commit time, not a three-gate subset. Every partner-ready V2 commitment includes Chain + Lit V3 + G3 + G4. G3 is selected per PDA — dcipher for governed-threshold/legal-resistance cases, drand for time-native/public-availability cases — and frozen into `h_commit`; it is never an automatic fallback and never added at reveal. The `age-plugin-cealis-v3` share policy stays commit-versioned so historical/dev-scaffold 3-gate profiles verify under their original profile, while new partner-ready commits use the full 4-gate profile. G4 Phase 1 → Phase 2 remains real operational phasing; it changes the attestation substrate for G4, not the number of gates.

### Cealis's identity as company

Cealis's protocol. Cealis charges for it. Commercial software, not open-source software. "Platform" in this document means one system serves many use cases through configuration — the PDA+ allowed surfaces plus per-partner PDA parameters (§F). Platform is a configurability claim. Not an open-source claim. Not a decentralization claim.

The configurator is Cealis-internal. Partners do not self-serve new use cases. The onboarding flow for a new partner is: the partner describes the use case, Cealis runs the PDA configurator against the PDA+ allowed surfaces and produces the PDA, Cealis deploys the resulting contracts on-chain, and Cealis provisions the partner dashboard and API credentials. The configurator is the single enforcement point for PDA+ guardrails across every deployment — so the invariants the platform commits to (shred-authority set, G3 choices, ingestion mode availability, condition module whitelist) hold uniformly across partners rather than per-partner discretion. §F covers the two-level configurability model; §N names that the configurator is Cealis-operated and not exposed to partners.

Worst-case open-source is possible. If Cealis-the-company becomes unable to continue operating, or if a distributed-vault-operator structure becomes an active requirement, open-sourcing the protocol stack is a path available to the company. Not a commitment. Not a schedule. A structural option path acknowledged explicitly so readers can reason about continuity under adverse company-state scenarios.

Vanish-path is a structural property of protocol composition. If Cealis-the-company disappears, the substrate does not. The protocol composes rented commodity networks (Lit, dcipher or drand), Base L1, the standard age envelope format, and the `age-plugin-cealis-v3` plugin with an open specification. Existing commits can still be revealed against chain state — gate operators continue independently, the chain runs, the envelope format is standard, the plugin is open-spec, and recipient combiners can be reconstructed from the plugin specification. Data already committed does not depend on Cealis-the-company being present for reveals to complete against existing PDAs (§A names this at altitude; §J item 35 states it as a derivable consequence of §B P18). Vault availability is a separate operational axis where this vanish-path has a gap today — loss of Cealis-the-vault-operator removes ciphertext availability regardless of gate-operator health (§L Non-defense 10).

Structural limits of what the system cannot do live in §O. Open-ended compositional possibilities live in §P.

## §O — Limits

§O is the capability-boundary statement. Each limit below is a structural consequence of the architecture, not a bug. §L and §O are adjacent but distinct. §L catalogs defenses and non-defenses — what the system does or does not block against a named threat. §O catalogs capabilities the system does not have at all. The two overlap at places: a non-defense in §L is often an architectural capability-absence in §O viewed from a different angle. §L says "this threat isn't fully blocked." §O says "this capability doesn't exist." Naming limits explicitly is the opposite of overclaim.

### The limits

- **Cannot operate without the chain.** Chain halt is system halt, because every primitive is coordinated, gated, or verified through Base L1 — commit anchoring, condition evaluation, gate-firing, shred, registry verification (§B P0). If Base halts, the system halts until the chain returns. Mitigation exists at the protocol layer (Base's L1 security model) but is not a Cealis-controlled axis.

- **Universal across attestable-fact domains, not across all possible conditions.** Every condition expressed through ConditionEngine reduces to "a signed attestation from a designated oracle passes a frozen Claim" (§B P4, §F). For a condition to be expressible, an entity must be willing and able to observe the relevant fact and sign an attestation about it. Chain-native facts (time, block state, event emissions from audited contracts) are Tier A — the chain is the oracle and no off-chain trust enters. Facts with established commodity oracles (vital records, court dockets, established data aggregators) are Tier B — the oracle's assertion is verified on-chain but the oracle operator is the trust point. Facts with narrow-domain bespoke oracles are Tier C. Conditions where no oracle exists and none is economic to build — "subject's Twitter account permanently suspended," "academic paper retracted where no retraction registry signs," "breach of fiduciary duty" — fall outside the expressible universe; partners are told at configurator time if their intent falls outside. Universality is a palette-coverage claim across attestable-fact domains, not an all-conditions claim.

- **Cannot guarantee reveal correctness on Tier B/C conditions beyond oracle honesty.** Chain verifies the cryptographic legitimacy of the oracle's assertion; the oracle's assertion is what evaluates the condition. Mitigations — per-PDA oracle pubkey binding (§C), k-of-n disjoint-oracle attestation for irreversible PDAs, per-PDA pause (P24, §B), Tier disclosure in artifact bundle — bound blast radius and distribute trust. They do not make Tier B/C conditions match Tier A's absolute tripwire. High-stakes PDAs should default to Tier A where possible.

- **Cannot verify identity itself.** The system anchors identity attestations but does not perform identity verification. Delegated to an external attestor or KYC provider under P14 Mode A, to the subject under Mode B, to depositor-role-plus-content-hash under Mode C (§B P14, §I). The trust chain for identity extends backwards to the attestor; §L out-of-scope names this explicitly.

- **Cannot issue eIDAS qualified electronic signatures.** σ_subject is a WebAuthn P-256 passkey signature or an EIP-712 wallet signature. Evidentiary, not qualified under eIDAS (§L out-of-scope). The system provides cryptographic subject-assent, not a QES. Partners requiring QES must layer a separate QES provider on top.

- **Cannot generate new proofs about committed data post-commit.** Under Mode A, plaintext is destroyed after TEE processing. Under Mode B, plaintext never enters Cealis. SD outputs are pre-specified per PDA and emitted once at commit-time (§B P5, §H). A predicate not emitted at commit-time cannot be proven later. Generating a new proof requires a fresh commit.

- **Cannot offer fully general partial disclosure.** SD operates per-predicate circuits, each compiled for a specific claim (§H). There is no "any predicate over committed data" capability. Mode B has no SD at all because plaintext never enters the Cealis TEE where the SD pipeline runs (§G).

- **Cannot fully erase if the commitment format itself leaks information.** Shred removes ciphertext and blocks future reveals through the triple block (§E). Shred does not remove the on-chain `h_commit`, the ConditionEngine state, or the ShredRegistry record. If the commit format at a given PDA embeds identifiable structure — for example a schema selector that reveals the data type — that structure persists on-chain after shred. Full erasure is ciphertext plus DEK plus derivable metadata; on-chain metadata is outside the erasure set by construction.

- **Cannot protect against TEE compromise at commit-time under Mode A.** If the Cealis TEE or its hardware vendor is compromised before plaintext destruction, plaintext leaks at ingestion (§L Non-defense 4). TEE attestation raises the bar but does not eliminate the possibility. Mitigation paths include cross-vendor TEE selection and Mode B as an option for use cases where this threat dominates.

- **Cannot protect against subject-device compromise at commit-time under Mode B.** Device-encrypt mode shifts commit-time trust to the subject's device (§L Non-defense 5). If the device is compromised during DEK generation or envelope construction, plaintext leaks at the source before ciphertext ever exists. Subject's axis of responsibility; Cealis cannot mitigate device-level compromise.

- **Cannot protect against simultaneous multi-gate operator compromise.** If Lit operators AND the G3 operator set AND Cealis G4 fall at the same time — or are compelled simultaneously through a coordinated multi-jurisdictional legal process — the DEK is derivable by the attacker (§L Non-defense 1). Structural upper limit of the 4-gate AND-composition. The same mathematical property that prevents single-party release enables full-stack release when all parties cooperate or are compromised.

- **Cannot protect against fundamental symmetric-cipher break combined with long-retention ciphertext exfiltration.** Any persistent ciphertext is vulnerable to far-future cryptographic breaks (§L Non-defense 2, §M). Mitigated by P21 stanza-addition re-key, hybrid post-quantum wrapping at commit, and shred-first lifecycle bias — the attacker needs the break plus long-retention ciphertext plus the specific primitive stack of the commit era. Mitigated, not eliminated. No mitigation is infinite against an infinite time horizon.

- **Cannot protect against compromised reveal-side combiner.** If the recipient's combiner execution context is compromised during reveal, recovered Shamir shares, the DEK, and plaintext can leak. Mitigated by authenticated delivery, no on-chain publication of shares, no transit logging, zeroization, and a hardened combiner context appropriate to the use case. Recipient-side context is outside Cealis's operational boundary.

- **Cannot recover data if the subject loses their device mid-commit under Mode B.** Mode B requires the subject's device to construct the envelope locally (§G). If the device is lost between DEK generation and ciphertext upload, the commit cannot complete and the data does not reach the vault. Reliability limit distinct from security threats — §L out-of-scope names passkey recovery as a vendor concern; §O names the broader reliability bound that applies across the Mode B commit path, not just to the passkey. Mode A has an analogous — but less severe — reliability bound: subject-authentication failure mid-commit (lost or corrupted passkey, wallet unavailable) aborts the commit, but no data is lost because plaintext has not yet been ingested or the ingestion transaction rolls back before chain anchoring. The subject retries with an alternate authenticator or starts a fresh commit.

- **Open-architecture commitment is bounded, not infinite.** P25 commits the system to additive extension within governance for every defined surface, so future features land without breaking past commits. Three honest bounds on that commitment. (1) Share profiles and gate counts are commit-versioned; adding a fifth fixed gate would require an explicit protocol/profile amendment, not silent extension. (2) A change to the Shamir/share-wrapping construction breaks combiners that don't keep the prior interpreter runnable. The `plugin_version_digest` pin on each commit means old commits verify under the original plugin, so the obligation is "keep prior plugin versions runnable in the verifier ecosystem," which is a live operational discipline, not a free property. (3) Cross-PDA composition is mechanically supported by the primitives today, but the configurator and audit tooling for safe composition (acyclicity analysis, cross-PDA dependency surfacing) lands in a later configurator version (§F). Until then, multi-PDA enforcement chains exist as protocol-layer composition, not partner-layer feature. None of these bounds invalidate P25; they are the perimeter inside which P25 holds.

- **Tier A PDAs do not provide a post-commit subject-recourse path beyond crypto-shred.** Chain-native conditions are not disputable — the chain either fired or didn't — so the §F "Challenge-window guardrail" forces zero-window on Tier A PDAs structurally. Subjects accept this at consent-time via σ_subject over PDA_terms_digest, with the §C subject-side verifier presenting the full PDA before signing. The only post-commit lever Tier A PDAs offer the subject is crypto-shred where the PDA's shred authority permits it (§E). This is by design, not a bug — it tightens the system-locked claim where the trust boundary is the chain itself. Tier B/C PDAs have a non-zero challenge window because oracle-honesty is a third-party trust point where dispute is operationally meaningful.

### Closing framing

Every one of these limits is structural. Not a bug to fix, not a roadmap item, not a "coming soon." They are consequences of the architecture's design choices. The architecture chose these bounds deliberately — naming them tells readers what the system is and is not. Listing limits explicitly is the opposite of marketing. Compositional possibilities that extend beyond this document's enumeration live in §P.

## §P — Open-ended depth

The system has more in it than this document articulates. §A named this at altitude — the longer you think about Cealis the more views surface. §P names it at the end. The primitives in §B compose in ways this document doesn't exhaustively enumerate. The features in §J catalogue what falls directly out of Part 1, but the compositional surface extends past that catalogue. Use cases grow without protocol change, because §F is data-agnostic by construction and the ConditionEngine module set is pluggable. Views surface as new reader perspectives and new partner contexts expose aspects of the same primitives — no framing is canonical, and new framings are expected. This section names a handful of compositional directions the primitives already support, states what is closed in this document and what is open, and closes by stating that this document is a snapshot, not a closed specification.

### Compositional possibilities the primitives support

Named non-exhaustively — compositional directions the primitives mechanically support. Each is one sentence: the direction plus the mechanism connection.

- **Time-locked reveals** — a reveal scheduled for a specific date or duration, because the ConditionEngine module set includes a TimeLock module that evaluates block timestamp against a pre-set trigger (§B P4, §F).

- **Subject-initiated reveals** — the subject (data originator) authorizes release to a named recipient under pre-specified conditions, because the condition module set supports a SubjectInitiated trigger evaluating subject consent at reveal-time (§B P4, §F).

- **Compositional enforcement chains** — the reveal artifact of one PDA becomes an input to another PDA's condition, because the RevealArtifactBundle is structured verifiable output and the ConditionEngine accepts attested data as signed oracle input (§B P4, §D). The primitives mechanically support this today; the configurator + audit tooling for safe cross-PDA composition (acyclicity analysis, cross-PDA dependency surface) is a later-configurator-version deliverable per §F, not a protocol-level gap.

- **Threat-activated reveals** — reveal triggered by an external signal (death certificate, court order, regulator demand) rather than a default event, because the condition module set supports external-signal modules that evaluate signed attestations from designated oracles (§B P4, §F, §I).

- **Dead-man's-switch at the primitive level** — the subject re-locks on a cadence, and missing a re-lock releases the data, because the ConditionEngine module set supports a HeartbeatMissed module that fires on expiry of a rolling subject-signed heartbeat (§B P4, §F).

- **Progressive multi-stage reveals** — different fields of the same commitment release under different conditions, because the age envelope supports per-recipient stanzas and the commit_AAD binds per-recipient schema selectors (§B P8, §C, §D); time-staggered releases to the same recipient compose via a second PDA's condition reading the first PDA's reveal artifact (§B P4 via the compositional enforcement chain above).

- **Configuration transparency** — surfacing as a first-class partner-facing attestation that a PDA's rules cannot change post-deployment without leaving an on-chain audit trail, because PDA configuration, gate-operator rotations, and condition module assignments all happen on-chain with timelocked updates (§B P9, §M). A partner attempting to alter the rules after deployment leaves an audit trail independent of the data the rules govern.

Each of these directions lands through one of §F's three extensibility vectors — template composition, oracle onboarding, or DSL extension — none of which require protocol rework. Novel conditions absorb into the palette without forking the system; data-agnostic schema polymorphism (§B P7) absorbs new schemas without platform-level change; the composition space is larger than this document enumerates by design.

### What's closed, what's open

Closed in this document: the primitives (§B), the ceremonies (§C commit, §D reveal, §E shred), and the threat model (§L). These are stable. The system commits to them. Future revisions may refine or extend, but the current commitments do not shift silently.

Open in this document: use cases, views, and compositional expressions. Use cases land by configuration (§F is data-agnostic, the schema space is not enumerated). Compositional expressions arise from composing the primitives in directions this document doesn't enumerate.

### Closing statement

This document is a snapshot, not a closed specification. It is expected to grow. The primitives composing the system are stable; what the system can do with those primitives is open.

### Glossary

Brief reader reference for load-bearing terms used throughout. Not exhaustive.

- **age envelope.** The ciphertext format — header with recipient stanzas plus a ChaCha20-Poly1305 payload. Produced at commit; decrypted at reveal via the custom `age-plugin-cealis-v3` combiner. §C, §D.
- **authorizationId.** Per-commit identifier binding the subject commitment, PDA identifier, PDA version, and a client-generated nonce. Threads through every ceremony event for a given commit. §C.
- **commit_AAD.** SCALE-encoded binding container for every field the AEAD check depends on at reveal — authorization identifiers, PDA references, binding digests, configuration choices. §C.
- **Ceremony resolver.** PDA-declared on-chain address with halt-capability during challenge windows on both reveal and shred axes. Bound in `pda_root`; cannot rotate post-commit. Can invoke G4 refusal, confirm no intervention, or extend the window within PDA+-capped limits. Operationally relevant only for PDAs with non-zero challenge windows — under the §F "Challenge-window guardrail" that means PDAs with at least one Tier B/C condition module on the relevant axis. Serves as the Art. 22(3)(a) human-intervention endpoint for Tier B/C legal-effect PDAs; remains available but not load-bearing on Tier A legal-effect PDAs (where Art. 22(3) is satisfied via pre-commit consent + chain-native trigger determinism + crypto-shred). §F.
- **Tier A / Tier B / Tier C.** Trust tiers per condition module, declared per PDA and carried in the RevealArtifactBundle (§F "Trust tiers"). Tier A is chain-native — the chain itself is the oracle (TimeLock, SubjectInitiated, OnchainState reads against audited partner contracts). No off-chain trust. Tier B is commodity oracle (Chainlink feeds, established data aggregators). Tier C is bespoke or partner-operated oracle. The §F "Challenge-window guardrail" forces `reveal_challenge_window` and `shred_challenge_window` to zero when all of the PDA's relevant-axis condition modules are Tier A; forces ≥ archetype floor when any is Tier B/C.
- **ConditionEngine.** On-chain contract that evaluates whether a commit's predefined condition has fired on either reveal or shred axis. Authored per PDA in Mode P (stateless predicate) or Mode F (FSM); module set is pluggable; PDA+ controls the allowed set. §B P4, §F.
- **DEK.** Data Encryption Key. Generated randomly at commit, used to encrypt the payload once, Shamir-split into gate/conditional-recipient shares, reconstructed at reveal only after enough authorized shares are recovered, and destroyed after one-shot decryption. §C, §D.
- **G1 / G2 / G3 / G4.** The four gates. Chain (Base L1 ConditionEngine event), Lit V3 Chipotle, dcipher or drand, and the Cealis verification component. §B P3, §D.
- **G4AuthorityRegistry, PluginHashRegistry, DSLVersionRegistry, OracleRegistry, QTSPRegistry, ShredRegistry.** On-chain registries. The first five carry 7-day TimelockController on ADDITIONS plus per-entry `DeprecationFlag` governed by `CealisSecurityMultisig` (§F, §N — asymmetric registry governance). ShredRegistry stores per-commit shred state (binary, permanent once set). §M.
- **QTSPRegistry.** Optional on-chain registry of approved EU Qualified Trust Service Providers (D-Trust, Bundesdruckerei, future Cealis-issued QTSP, etc.) whose Qualified Electronic Signatures are accepted as σ_subject when a PDA elects `qes_subject_required = true`. Same governance shape as OracleRegistry. Used only by PDAs requiring §371a ZPO Anscheinsbeweis admissibility; default PDAs use platform-authenticator WebAuthn σ_subject and admit at §286 free-evaluation. §F, §M.
- **`qes_subject_required` and `qtsp_provider_ref`.** PDA-level capability + binding. When `qes_subject_required = true`, σ_subject must be a Qualified Electronic Signature issued under the QTSP referenced by `qtsp_provider_ref` from `QTSPRegistry`. Frozen at commit via `subject_authenticator_class = qtsp_qes` in `pda_root`. Required by partners targeting §371a ZPO Anscheinsbeweis admissibility. §F.
- **`subject_authenticator_class`.** PDA-level enum `{platform_authenticator, qtsp_qes, synced_passkey}`. Frozen at commit in `pda_root`. The §F PDA+ "σ_subject authenticator class guardrail" rejects synced_passkey for legal-effect PDAs. §F, §C.
- **`art_9_scoped` and `art_9_basis_id`.** PDA-level metadata for processing of Art. 9(1) GDPR special-category data (health, biometric for unique identification, genetic, racial / ethnic origin, religious / philosophical beliefs, political opinions, trade-union, sex life / sexual orientation). Required by the §F PDA+ "Art. 9 special-category guardrail." `art_9_basis_id` is a closed enum of the ten Art. 9(2) bases. When the basis is `(2)(a) explicit_consent`, the §C subject-side verifier surfaces a separate plain-language consent flow distinct from the standard PDA-terms confirmation. Frozen at commit in `pda_root`. §F.
- **encrypted-reason mode.** G4RefusalRegistry emission mode that stores an `encrypted_reason_blob` rather than the plaintext reason code, with the on-chain event reduced to `RefusalSignal(authorizationId, "refused")`. Decryptable only to the partner's resolver flow plus regulators with subpoena authority. Default for reason codes `0x02` (Art. 17 erasure) and `0x03` (Art. 18 restriction) across all PDAs per the §F "Refusal-reason encryption guardrail." Closes Art. 5(1)(a) and Art. 5(1)(c) collisions on public-by-default rights-exercise leakage. §N "Privacy mode," §F.
- **`refusal_reason_encrypted_default`.** PDA-level set of reason codes that default to encrypted-reason mode. Default `{0x02, 0x03}` for all PDAs by the §F "Refusal-reason encryption guardrail." Per-PDA opt-out (public-reason for these codes) requires explicit subject acknowledgment + partner attestation; configurator surfaces the trade-off at PDA configuration time. §F.
- **CealisSecurityMultisig.** 2-of-3 on-chain contract with authority to set `DeprecationFlag` on registry entries — instant for non-canonical entries, 24h expedited TimelockController delay for canonical-in-use. Each deprecation binds `disclosure_commit_hash`; absent `publishDisclosure(bytes)` with keccak-verified content within 72h, the flag auto-clears. 30-day cooldown on re-deprecation of the same entry. Member rotation through 7-day TimelockController. §F, §N.
- **EmergencyGovernance.** 3-of-3 on-chain contract distinct from `CealisSecurityMultisig` with authority to suspend the Security Multisig's deprecation power for up to 7 days. Circuit breaker for Multisig compromise. §F, §N.
- **Governance Phase 1 / Phase 2.** `CealisSecurityMultisig` and `EmergencyGovernance` exist from V2 launch but all seats are Cealis-held at Phase 1 pending external-advisor seating. Phase 2 transition completes before first paying partner OR within 90 days of V2 launch. §F, §K item 10, §N.
- **PasskeyRotationLog.** ABI-standard on-chain contract carrying per-Cealis-account passkey rotation entries. Each entry is signed by the prior passkey's WebAuthn assertion; Cealis provides a canonical instance on Base L1, recipients MAY use ABI-compatible alternatives. Cealis cannot forge rotations (no prior-passkey custody) but can censor publication; recipients can self-publish via the permissionless contract. §C, §K item 9.
- **conditional_recipient.** Non-partner recipient whose σ authorizes a conditional-recipient Shamir share AND who receives plaintext at reveal. Polymorphic by delivery mode: PASSKEY_ACCOUNT (variant 0x01, shipping V2), WALLET_EOA (variant 0x02, shipping V2), WALLET_EIP1271 (variant 0x03, reserved post-V2). role_tag carries semantic metadata: HEIR / BENEFICIARY / ACQUIRER_COUNSEL / MEDICAL_PROXY / SUBJECT_ALTERNATE / JOURNALISM_RECIPIENT / SUBJECT_SELF. Generalizes the testament-specific heir stanza from earlier V3-custody drafts. §C, §D, §F.
- **conditional_recipients_policy.** PDA-level k-of-n configuration over the conditional_recipient set. `{n, k, recipients: [{delivery_mode, binding, role_tag, delivery_hint?}, …], recipient_stanza_merkle_root}`. Bound into commit_AAD via `conditional_recipients_policy_digest`. §F.
- **`pda_updatable`, `conditional_recipients_updatable`.** PDA-level booleans. When true, subject (while alive) can issue a fresh σ_subject update replacing parts of the PDA (including the conditional_recipients policy). Default true for long-TTL PDAs (`fire_time_ttl_estimate > 5 years`) to mitigate conditional-recipient bricking and emergency-response halt risk. §F.
- **Open-architecture commitment.** P25's discipline that every protocol surface has a defined forward-compat extension path — schema configuration, condition extensibility vectors, versioned Shamir gate/share profiles, Mode A/B ingestion, registry-mediated version updates with timelock and per-entry deprecation, conditional_recipient variant-tag reservation, additive PDA+ guardrails. Each commit pins its full version surface so old commits verify under their original references regardless of platform evolution. Bounded by three honest perimeters named in §O: share-profile versioning, plugin-version backward-compat as live operational obligation, cross-PDA composition tooling deferred to a later configurator version. §A, §B P25, §J item 37, §O.
- **`cealis_class_wide_halt_opt_out`.** PDA-level boolean. When true, commits under this PDA are exempt from Cealis class-wide deprecation halts. AAD-bound and visible to recipients at reveal. G4 emits reason code `0x0A opt_out_active` on would-be deprecation refusals. Escape valve for institutional partners whose commercial model requires uninterrupted enforcement. **Forbidden on legal-effect PDAs** (`legal_effect_expected = true`) by the §F Art. 22 safeguard guardrail conjunct 5 — available only on non-legal-effect PDAs. §F, §L defense #17.
- **Shamir share.** One threshold share of the commit-time DEK. A single share is information-theoretically insufficient to recover the DEK; the combiner needs the threshold set configured in commit_AAD. §C, §D.
- **h_commit.** On-chain anchor hash committing the full envelope and configuration. Any drift in any input produces a different h_commit and fails the AEAD check at reveal. §C.
- **Mode A / Mode B.** Ingestion modes. Mode A (TEE-ingest) is the shipping default — plaintext transits the Cealis TEE boundary and is destroyed after processing. Mode B (device-encrypt) is architected as a PDA+ capability for later enable — the subject's client constructs the envelope locally and Cealis never sees plaintext. §G.
- **Mode P / Mode F.** ConditionEngine authoring modes, per §B P4. Mode P is a stateless Claim-DSL predicate evaluated at ceremony-attempt time; default for shred conditions because destruction predicates reduce to state-reads for most archetypes. Mode F is a finite state machine advanced by oracle attestations; default for reveal conditions because release conditions genuinely traverse stages. Each PDA declares (mode, spec) independently for reveal and shred. §B P4, §F.
- **PDA / PDA+.** Partner Deployment Agreement. PDA is the per-partner parameter set; PDA+ is the platform-level configurability Cealis sets (allowed surfaces, module whitelists, ingestion-mode availability). §F.
- **Phase 1 / Phase 2.** G4 operational phases. Phase 1 is a Cealis-hosted server with sealed-code attestation (Ed25519 over the binary hash). Phase 2 swaps to a rented TEE with DCAP quote verification. Commits made in Phase 1 stay valid under Phase 1 attestation post-cutover. §N.
- **σ_subject.** Subject's consent signature — WebAuthn P-256 passkey, EIP-712 wallet, or eIDAS QES from a registered QTSP — bound into commit_AAD via `keccak256(σ_subject)`, with the signature itself stored off-chain in the vault. The authenticator class is enforced by the §F PDA+ "σ_subject authenticator class guardrail." For legal-effect PDAs (KYC-lending, M&A, evidence, medical) the configurator requires either (a) WebAuthn assertion from a **platform authenticator** with attestation statement (not synced passkey), or (b) QES from a registered QTSP per `qes_subject_required = true`. Non-legal-effect PDAs (consumer, journalism, archival, testament) accept synced passkeys. The platform-authenticator and QES paths are designed to satisfy eIDAS AES "unique linkage and sole control" requirements; the QES path additionally satisfies §371a ZPO Anscheinsbeweis. §C, §F.
- **σ_Lit, σ_G3, σ_G4, σ_conditional.** Gate signatures that authorize corresponding Shamir share release or admission at reveal. σ_Lit, σ_G3, σ_G4 are the three fixed gate signatures; σ_conditional is a variable-length vector from `conditional_recipients_policy` (empty when n = 0). They are authorization evidence, not DEK material; share secrecy carries the key boundary. §B P22, §D.
- **proof_shred.** Public verification signature produced when a shred ceremony clears both authority and condition gates. Binds `(authorizationId, h_commit, block#, ts, shred_reason_code)`. Shred proves the condition fired, does not derive a key. Uses `proof_` prefix to avoid overloading σ-naming. §E.
- **post_challenge_reveal_in_progress.** Derived DSL predicate — `reveal_progress_state(authId) IN {GatesSigning, Finalized}`. AND-composed into every shred condition as a PDA+ mandatory guardrail, so shred cannot race gate-signing. Closes the destruction-axis tripwire mirror. §B P11, §E, §F.
- **subject_commitment_v3.** Per-partner-namespaced subject identifier. Same subject across different partners produces different commitments, preventing cross-partner correlation at the commitment layer. §C.
- **TEE, DCAP.** Trusted Execution Environment and its attestation quote format. AWS Nitro, Intel SGX, and AMD SEV-SNP are the current vendor families. DCAP quotes verify on-chain via Automata zkDCAP under Phase 2. §G, §K.
- **Vault.** Off-chain, Cealis-operated, closed-source ciphertext store with append-only audit logs (§286 ZPO free-evaluation integrity by default; §371a ZPO Anscheinsbeweis when the PDA has elected QTSP integration) and crypto-shred support. §M.
