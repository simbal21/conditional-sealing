# Conditional Sealing: Threshold-Gated Data Escrow with an On-Chain Release Trigger — Design and Evaluation Note

**Simon Baltes**

*Written July 2026, after the project's retirement; revised for publication September 2026. The project was developed under the working name Cealis.*

> **Status of this document: an unreviewed design and evaluation note.** It has never been submitted to, reviewed by, or published in any venue, and it is structured as a note because that is the clearest structure for the material — not as a claim of peer review or of research-paper standing. Most of its references are to documents inside this repository rather than to external literature. Corrections found before publication are in [`ERRATA.md`](../ERRATA.md), which materially qualifies Section 4.2; read it alongside Section 6.

## Abstract

I present the design and reference implementation of *conditional sealing*: a primitive in which data is encrypted once and can be reopened only when a pre-agreed, machine-checkable condition is confirmed by a public blockchain, with no master key held by any single party. The construction splits a data-encryption key 3-of-3 via Shamir secret sharing over three organizationally distinct signing gates — a rented threshold/TEE network (Lit Protocol), a rented randomness/attestation network (drand or dcipher), and a refusal-only operator verifier — all of which withhold their signatures until an on-chain condition engine confirms the trigger, yielding a strict four-gate AND in which the chain is the mandatory objective trigger but holds no key material. The cryptographic core is tested against locked golden fixtures, and the on-chain implementation contracts are Sourcify-verified on a public testnet (Base Sepolia; the UUPS proxies in front of them are not verified; entry-point proxy `0xb09a8300423CA3BD0E028bAB6A6245A248520D02` — testnet-only; see the drift disclaimer in the repository README). The evaluation contributes two results. The technical result is positive with stated limits: the cryptographic core is real and adversarially tested, while the operational layer — live gate transports, production runtime, independent verifier — was never completed, and internal audits found multiple CRITICAL and HIGH issues (four distinct CRITICAL findings over time; see `docs/audits/FINDING-RECONCILIATION.md`). The market result is negative and, I argue, the more useful contribution: a pre-committed, falsifiable six-condition demand instrument (the Fundability Fingerprint), applied adversarially to 157 candidate companies and use cases, found zero clean fits, exposing a structural negative correlation between trigger objectivity and ability to pay. The project was retired on that evidence. This note documents both the construction and the reason no one should rebuild it without first rerunning the demand test.

**Keywords:** conditional sealing; threshold cryptography; witness encryption; timelock encryption; secret sharing; negative result; demand study.

## 1 Introduction

Every deployed data-custody system shares one background assumption: somebody can always see the data. A vault has an administrator; a database has a DBA; an escrow account has an escrow agent. The moment sensitive data exists in a system, some party is positioned to read it — and can therefore be subpoenaed, bribed, breached, or simply curious. This assumption is so uniform that it is rarely stated, and it forecloses a class of arrangements whose common blocker is the sentence *someone can open it too early*: a security researcher will not hand over a working exploit before payment; a lender holding borrower identity becomes a honeypot and a standing liability; a counterparty will not pre-load data meant to be released only if something goes wrong, because whoever holds it in the interim can be pressured.

Conditional sealing is the primitive that removes the early-peek possibility: data encrypted once, reopenable only when an agreed condition — a date passing, an on-chain event, an oracle-attested fact, a holder falling silent — is confirmed true by a public blockchain rather than by a human, and constructed so that no single party, including the operator, holds a working key. The theoretical ideal here is witness encryption [2], which would make the condition itself the decryption key with no committee at all; since witness encryption does not exist at usable cost, this work takes the committee route: rented threshold networks stand in for the missing mathematics, and the engineering problem becomes how to compose them so that no single network is trusted.

Cealis is a reference implementation of that composition, built over roughly three months in 2026 (2026-03-13 to 2026-06-10; the published repository carries a fresh single-commit history because the original contains credentials and personal data) and deliberately retired. This note is its design record. One statement of scope governs everything that follows, made once here and pointed to rather than repeated: **the system was never externally audited, never ran in production, and never held real user data; its on-chain components exist on a public testnet only, whose deployed bytecode has drifted behind later source-level security fixes; the project was retired on 2026-06-10 and the repository is an archive, not a maintained system.** The repository `README.md` ("Status" and "What this is not") is the canonical statement of these limits.

The contributions are:

1. **A construction** for condition-gated decryption that AND-composes multiple independent threshold networks behind a mandatory on-chain trigger, including an authenticated envelope format with per-stanza MACs and an explicit refusal-only compliance gate (Section 2).
2. **A tested reference implementation**, with an honest accounting of which components are real and which were stubs at retirement (Section 3).
3. **A technical verification record**: locked golden fixtures, a reproduced contract test suite, a database-dump integration check with a positive control (environment-gated, not in CI), and a published internal audit trail including a withdrawn self-grade (Section 4.1).
4. **A negative market result as a first-class finding**: a pre-committed, falsifiable six-condition demand instrument applied adversarially to 157 candidates, yielding zero clean fits and a structural explanation — the objectivity-versus-ability-to-pay scissor (Section 4.2).

The fourth contribution is the one I most want other builders to take. Negative results are chronically under-published in systems work; this one was cheap to obtain (about a day of paper analysis, run too late), is fully specified for replication, and identifies a market-structure property rather than an execution failure.

## 2 Design

### 2.1 The primitive

A *seal* is a commitment of the form: plaintext *m*, sealed at time *t₀* under condition *C*, such that (i) before *C* is confirmed true, no party or sub-threshold coalition — holder, recipient, operator, or any single gate network — can recover *m* from any material the system stores; (ii) once *C* is confirmed true on-chain, release proceeds mechanically to the entitled recipients with a chain-of-custody record; and (iii) release cannot be forged: no party can cause a release while *C* is false. The condition *C* must be machine-checkable; the design deliberately refuses subjective triggers, because the only honest justification for involving a blockchain is that on-chain evaluation makes the trigger objective by construction — there is no adjudicator to bribe.

At commit time, a fresh data-encryption key (DEK) is generated and the plaintext is encrypted under ChaCha20-Poly1305 [10], with the nonce derived from the DEK and the commit's context digest and the commit's binding metadata carried as associated data. Only a hash of the sealed data is recorded on-chain; the payload never touches the blockchain. An adversary who fully controls the smart contracts has therefore stolen a hash.

### 2.2 The four-gate composition

The DEK is split 3-of-3 by Shamir secret sharing [1] over GF(2⁸) across three *signing gates*; the chain is a fourth gate of a different kind — the mandatory trigger they all require, holding no share:

- **G1 — the chain (trigger, not a shareholder).** A `ConditionEngine` contract evaluates the configured condition. G1 contributes no key material; its role is that no signing gate acts until it fires.
- **G2 — Lit Protocol** [4], a rented threshold/TEE network, signs once its release evidence is present.
- **G3 — drand or dcipher**, fixed per deployment at commit time. The scope is deliberately precise: drand attests the passage of time, tlock-style [3], not arbitrary events; dcipher (Randamu) is the path to richer condition attestation.
- **G4 — a refusal-only Cealis verifier.** It may refuse to sign on narrow legal, GDPR, or integrity grounds; it cannot open anything, and its share alone sits below the reconstruction threshold.

Because the split is 3-of-3 over the signing gates and every signing gate waits on G1, the composition is a strict four-gate AND: miss any signing gate and `Shamir.combine` yields nothing usable (fail-closed); without the chain's condition, no gate signs at all. Internally this was called the *universal tripwire* — no module or registry can move the system into a release-authorized state on its own — and it is checked as a contract-level invariant (Section 4.1). When a deployment adds conditional recipients, share count and threshold grow together, so the AND remains an AND. The field arithmetic in the Shamir implementation is constant-time by construction, with the qualifier stated wherever the claim appears: under a JIT-compiled, garbage-collected JavaScript runtime, any constant-time property is best-effort.

Each share is wrapped to its gate under a hybrid X25519 + ML-KEM-768 [11] construction, a hedge against harvest-now-decrypt-later adversaries — relevant for a system whose premise is that sealed data may sit for years.

### 2.3 The envelope

A seal travels as a custom plugin envelope in the `age` format discipline [9]: a header of gate-recipient stanzas plus the encrypted payload. Every stanza carries its own MAC over its index, binding tag, and plugin version; conditional-recipient stanzas carry an additional binding MAC over their full length-prefixed payload. Verifiers must validate a stanza's MAC before parsing any of its fields, which closes cross-variant substitution attacks — one stanza type cannot be reinterpreted as another through byte manipulation — and the plugin aborts hard on any MAC failure. The format is locked by golden fixtures checked into the repository, so drift between specification and implementation fails the build rather than accumulating silently.

### 2.4 σ as authorization, and the refusal gate

Gates never see data. A gate's signature σ is an authorization to decapsulate exactly one share — nothing more. The reveal path verifies the gate signatures, decapsulates the corresponding stanzas, reconstructs the DEK, and delivers plaintext to entitled recipients with an on-chain custody record of every step. This separation is deliberate: only wrapped key shares ever route through gate networks, so no gate network ever holds the payload or material sufficient to decrypt it.

The refusal-only G4 gate is the design's explicit compliance seam. A lawful-erasure order or a detected integrity failure needs a place to land, and hiding that place would have made it an unstated backdoor. Making it explicit also forces honesty about its cost: a component that *can* refuse is a component that can be *compelled* to refuse. The project therefore maintained a banned-phrasings list — no unqualified "non-custodial," no flat "decentralized," no "a subpoena can't open it," no "no one can block it" — which this note inherits. The defensible claims are narrower: non-custody by design for the fixed gates, releases unforgeable from outside, and refusal scoped, logged, and below the threshold needed to open anything. A system whose operator can halt releases is not censorship-proof.

## 3 Implementation

The implementation is a pnpm monorepo of TypeScript packages plus a Foundry contract suite: `v3-crypto` (sealing primitives, Shamir split, hybrid wrap, envelope), `v3-custody` (the four-gate AND combiner), `contracts` (the `ConditionEngine`, 9 condition modules, registries, and governance), `v3-configurator` (per-partner policy validation), `v3-sd` (selective disclosure via Poseidon and PLONK), `v3-api` (Fastify ingestion/delivery server), `v3-ops` (key-ceremony procedures), `v3-demo` (end-to-end harness), and `verify-sdk` (an offline independent verifier). Contracts are live on Base Sepolia behind UUPS proxies (entry point `0xb09a8300423CA3BD0E028bAB6A6245A248520D02`); the implementation contracts are Sourcify-verified, the proxies are not (`deployments/base-sepolia-verification.json`) — a testnet-only historical proof-of-deployment whose caveats Section 1's status statement covers.

What is real and what was a stub matters more than the package list. The honest state at retirement, condensed from the repository's per-subsystem assessment (states: real & tested / partial / simulated (stubbed) / not built):

| Subsystem | State | Reality at retirement |
|---|---|---|
| `v3-crypto` | real & tested | Real: golden-fixture tested; constant-time-by-construction field math (best-effort under the JS runtime) |
| `v3-custody` | partial | Combiner real and adversarially tested; **external gate signing transports stubbed** |
| `contracts` | partial | Strong test discipline; live testnet deploy predates the security fixes |
| `v3-configurator` | partial | Logic present; a barrel export shipped a no-op validator |
| `v3-sd` | partial | Real cryptography, not wired into the API |
| `v3-api` / runtime | partial | Boots once, on in-memory stores with unwired auth |
| apps / UI | not built | No browser UI; nothing calls the API over HTTP |
| `verify-sdk` | not built | Independence property asserted, not delivered |

The single most consequential row is `v3-custody`: the AND combiner — the component that enforces "no master key" — is real, but the live network calls to Lit and to drand/dcipher were stubs, so the independent parties whose separateness is the entire point ran simulated inside one process on one machine. The architecture's central property was designed and locally enforced, never operationally demonstrated. Three further single-key operational edges were known and open at retirement: contract upgrade authority sat behind a mandatory time delay but on a single key; the key-publish step was not yet bound to verified party identities, so a substitution there would not have failed shut; and privileged roles configured each seal's parameters and delivery destination. None of these breaks the cryptography; each is a place where one operational key still mattered.

## 4 Evaluation

The evaluation has two halves of different kinds: a technical verification of what was built (4.1), and an empirical study of whether anyone would pay for it (4.2). The second produced the project-ending result.

### 4.1 Technical verification

**Reproduced test record.** At retirement the contract suite passed 330 forge tests — of which 56 are fuzz tests and 3 are invariant tests in a single suite (inclusive subsets, not additive); I re-verified the forge suite at 330/330 on 2026-07-03 (forge 1.7.1), after retirement, during release preparation. The invariant suite includes the universal-tripwire property: under randomized sequences of module and registry interactions, no module or registry can move the system into a release-authorized state on its own. The TypeScript suites cover the crypto suites (including locked negative vectors and randomized share-subset cases for the Shamir threshold), envelope MAC and substitution defenses, and the combiner. A checked-in spec-compliance guard makes drift between the specifications and the code fail the test suite.

**Golden fixtures.** The envelope format and the sealing primitives are pinned by locked golden fixtures: byte-exact reference vectors that the implementation must reproduce. This converts "the implementation matches the spec" from an assertion into a build gate, and it is the reason I describe the cryptographic core as spec-conformant rather than merely tested.

**Database-dump check.** The claim "the system's own store cannot reconstruct a key" was checked directly rather than only argued. An integration test (`v3-demo/tests/integration/real-stack-e2e.test.ts`; environment-gated, needs a real Postgres, and not part of CI) dumps the server's durable state — the sealed envelope and every stored share record — and confirms the key cannot be rebuilt from it: the stored shares exist only in wrapped form, unwrapping them with any key other than the gates' fails, and combining zero shares fails. A positive control runs the same records with the real gate keys, which are held outside the database, and does reconstruct the key, so the negative result reflects missing keys rather than a broken harness. The scope is deliberately narrow: this demonstrates that the gate keys are not in the database, not that the wrapping resists cryptanalysis.

**Internal audit record.** Internal security review was substantive and is published in full in `docs/audits/`. Two adversarial self-audit passes (2026-05-14 and 2026-06-02), a 2026-05-19 synthesis, and an honest-audit rewrite (2026-06-03) found multiple CRITICAL and HIGH findings across the live testnet contracts and the off-chain pipeline; the corpus names four distinct CRITICAL findings over time (C1, C2, C3, F-1 — see `docs/audits/FINDING-RECONCILIATION.md`). The instructive ones: C1, an off-chain commit-AAD round-trip integrity check silently skipped for historical and re-keyed commits (fixed in source); C2, a deployed `ChallengeRegistry` that stores a challenger allowlist root, documents merkle enforcement in its NatSpec, and never verifies membership — permissionless challenge-open on the live contract (fixed in source only; the deployed contract remains challenge-open); and F-1, a Mode-F FSM tripwire defeat found by the June pass (fixed in source on 2026-06-02, never redeployed — the live testnet contract still has it).

**A withdrawn self-grade.** An early self-assessment scored the contracts 5.00/5 on the Trail of Bits nine-category code-maturity rubric. A later rewrite withdrew that grade to approximately 3.5/5, recording explicitly that the original had counted self-authored documentation as audit maturity, and instructed that the 5.00/5 never be cited (`docs/audits/MATURITY-SCORECARD.md`). I report the withdrawal here as evaluation data: it is the measured size of self-assessment inflation in this project — about 1.5 points on a 5-point scale — and it is why every "tested" claim in this section names its evidence. Consistent with Section 1's status statement, none of this internal review substitutes for the external review that never occurred.

### 4.2 The demand study

**Motivation and instrument.** Most privacy infrastructure dies on demand, not technology, and "is the cryptography real?" is a question a builder can answer alone while "will anyone buy this?" is not. To make the second question falsifiable, I constructed the *Fundability Fingerprint* (`docs/research/fundability-fingerprint.md`): six binary conditions that a sealed-data use case must all satisfy to be a fundable head-on business — C1, the data is dark (sealed until trigger, not read live); C2, the release trigger is objective and machine-verifiable; C3, the holder carries no standing legal duty to produce the data early; C4, non-custody is an actual hard requirement of the deal; C5, a paying, motivated check-writer exists; C6, no trustless or near-free incumbent already owns the slot. The test is a strict AND, not a weighted score: each condition is individually necessary (a subjective trigger collapses the product into an audit log regardless of everything else; a standing production duty makes adoption non-compliance regardless of budget), and weighted scoring would dilute a fatal failure across five passes. The output is a verdict — *survived*, *wounded* (a narrow honest slice remains), or *dead* — plus the identity of the first failing condition.

**Procedure.** The instrument was applied to a population of **157 candidate companies and use cases**: 100 in fields the project already knew or bordered (lending, inheritance, whistleblowing, escrow, bug bounty, and others) and 57 in field clusters never previously examined (clinical trials, biometrics, defense technical data, energy markets, and others). Each candidate received a devil's-advocate pass whose explicit job was to kill it against all six conditions and record the first hard failure — an inversion adopted because an advocate evaluating their own thesis will find the one slice that passes and over-generalize it. **Disclosure of method:** these passes were *agent-run desk evaluations over public information*, executed by AI agents under my direction and adjudicated by me; **no company was contacted, and no primary research was conducted.** The entire population was processed on a single date (2026-06-06), which is only possible at that rate with an agent fleet. "Devil's-advocate" describes the adversarial role each pass was assigned — it does not denote rater independence, and Section 6 restates the resulting threat correctly. A single-case pilot preceded the population run: the project's own flagship thesis (sealing borrower identity for undercollateralized on-chain lending, released on default) failed on a near-napkin argument — recovery fails on insolvency, not anonymity, and the institutional borrowers were already identity-verified — collapsing C4 and C5. That clean kill motivated the full run.

**Result.** Zero of 157 candidates cleared all six conditions. The zero is the hard number: it is identical in every internal file that recorded the run. The wounded/dead split is soft and I disclose it wherever a split appears: the component boards report 0/18/139 (survived/wounded/dead), the master summary 0/~26/~131, and row-level counting across both boards 0/25/132; the disagreement is entirely about where to draw the wounded/dead line on marginal cases and does not touch the zero. Per-segment aggregates, verdict counts, and the killing condition for each segment are published in `docs/research/kill-test-results.md`; the per-company sheets are not published because they name private companies and founders, and no part of the finding depends on the names.

**The scissor.** The failure distribution, not the verdict count, is the empirical contribution. Deaths clustered: C2 (no objective trigger) was the leading killer by a wide margin, followed by C1 (data not dark), C6 (trustless incumbent), C5 (no payer), and C3 (standing duty). And the clusters sorted the market into two nearly disjoint blades. Blade A — crypto-native segments (on-chain credit, DAO succession, prediction markets, agent payment rails): triggers genuinely machine-verifiable, but the rows die on C6 and C5 — trustless incumbents of the Safe/Zodiac [5] and Sablier [6] genre already own the slot, and the would-be buyers are thin-budget teams that build in-house. Blade B — enterprise segments (genomics, healthcare, KYC, defense, clinical, forensics): real budgets, but the rows die on C2, C1, and C3 — the release event is a human, legal, or governance judgment; the data is read live; and a standing duty to produce makes self-disablement non-compliance. **Across the surveyed population, objectivity of the trigger and ability to pay are negatively correlated.** Where the trigger is clean, the money is not; where the money is, the trigger is not. This is a structural property of who holds machine-verifiable triggers versus who holds budgets, not a gap that engineering or funding closes — which is why I treat the zero as a finding about the market rather than bad luck, and why the project was retired on it four days after the population run.

The ~25–26 wounded entries (split soft as disclosed above) corroborate the scissor from the other side: every one sits where an objective trigger *already exists in the customer's world* — a database-lock date, a deed-recorded event, an embargo lift, an already-signed royalty split, a liveness lapse, a pre-funded payment — and every one is a narrow partner-fit layer rather than a head-on product. During the same period, the far better-funded confidential-compute category shipped the commodity version of the adjacent primitive (Zama's FHE stack with a threshold key-management service reached mainnet in December 2025 [7]), sharpening C6 for exactly the Blade-A slot.

I present this negative result as a first-class contribution for three reasons. It is falsifiable and pre-committed: the six conditions and the strict-AND logic were fixed before the population run, so the instrument could not be softened until something passed. It is replicable: the method — broad candidate population including one's favorite ideas, adversarial per-candidate evaluation, first-failure recording, death-distribution analysis — is fully specified, and at agent-assisted throughput the population run costs about a day. And it carries the study's transferable lesson in a single asymmetry: the build consumed three months; the test that killed it took a day of agent-assisted work and should have run first.

## 5 Related work

**Witness encryption.** The theoretical ideal of this design space is witness encryption (Garg, Gentry, Sahai, Waters [2]): encrypt to an NP statement so that any witness-holder can decrypt, with no committee and no trust. At usable cost it does not exist. Conditional sealing is best read as a committee-based practical approximation: threshold networks stand in for the missing mathematics, and the trade — deployability today for trust in committees — is explicit and unflattering; every honest claim in this note is downstream of it.

**Timelock encryption.** drand's tlock construction [3] delivers exactly one condition — the passage of time — with strictly less trust: encrypt to a future beacon round, and the beacon's own operation performs the release. Where the condition is purely temporal, tlock is simpler than this design, and Cealis's G3 gate uses drand in precisely that time-attestation role. Conditional sealing generalizes the condition language and pays for the generality with committee trust and operational apparatus.

**Lit Protocol alone.** The sharpest competitive question — "why not just Lit?" — begins by conceding the premise: Lit [4] already gates decryption on programmable on-chain conditions with a live threshold/TEE network, and for many cases it is the simpler right answer. The differences matter only when their threat models matter: AND-composition across organizationally disjoint networks, so no single threshold network — Lit included — can release a key alone; a refusal-only sub-threshold compliance gate with a defined legal surface instead of ambient operator power; and payload/key-split separation, so no gate network ever holds data or material sufficient to decrypt it.

**Smart-contract escrow and custody.** Safe with Zodiac modules [5] provides programmable asset custody; Sablier [6] streams value on schedule; hashed-timelock contracts [8] release funds against a revealed preimage. These are the incumbents Section 4.2 credits with holding the trustless slot, and the distinction is categorical: they govern who may *move value* and when; conditional sealing governs who may *read data* and when. The market adjacency was real; the primitive is different.

**Fully homomorphic encryption.** Zama's FHE stack [7] computes on encrypted data — a stronger and genuinely different primitive. Conditional sealing opens data when a condition becomes true; FHE lets data be used without ever opening it, and its threshold key-management service overlaps the custody role the gates play here. Its mainnet arrival reshaped the market this system would have sold into.

**Novelty accounting.** The cryptographic pieces are not new: Shamir sharing [1], the hybrid X25519 + ML-KEM-768 wrap [11], ChaCha20-Poly1305 [10], and the `age` envelope discipline [9] are careful but standard composition; the per-stanza MACs and substitution defenses are format engineering, not new cryptography. Two things would have been genuinely novel if completed, and neither was: an operationally realized AND-composition across organizationally, jurisdictionally, and TEE-vendor-disjoint threshold networks demonstrated live end-to-end, and the refusal-only gate operated as a first-class protocol role rather than a documented intent. Both are exactly the unfinished operational work of Section 3. What stands completed is the composition, its test record, and the negative demand result.

## 6 Limitations

The limitations below are the note's hedging, stated once and in full.

**The operational layer was never demonstrated.** The central architectural property — that independent, organizationally disjoint parties jointly and exclusively control release — was enforced by a real, adversarially tested combiner but exercised only in simulation: the live signing transports to Lit and to drand/dcipher were stubs, and the "independent" parties ran inside one process on one machine. The adversary model in `SECURITY-MODEL.md` describes the architecture as designed; the system as actually run collapsed its operator-separation rows onto a single machine. Every claim in Section 2 about multi-party custody should be read as *designed and locally enforced*, not *deployed and demonstrated*. Relatedly, the constant-time property of the field arithmetic is by construction only and best-effort under a JIT-compiled, garbage-collected JavaScript runtime; no hardware-level timing evaluation was performed.

**No external review.** All verification in Section 4.1 is self-verification: internal audits, self-authored tests, a self-run reproduction. The withdrawn 5.00/5 self-grade is direct evidence of how far self-assessment drifted in this very project before correction, and there is no principled reason to assume the corrected assessment is free of the same bias in smaller measure. The audit findings that were caught (including all four CRITICALs) were caught by the same author-directed, AI-assisted process that wrote the code, which bounds the class of defects the record can speak to.

**The demand study is a single-market, single-period observation.** The 157-candidate population was assembled in May–June 2026 and reflects that market moment — including the recent mainnet arrival of a heavily funded FHE incumbent, which sharpened C6 in a way that may not persist or generalize. The six conditions are tuned to the conditional-release category; the strict-AND method transfers, the specific conditions may not.

**Solo-rater validity threats.** The study's most serious methodological weakness is that one person built the instrument, assembled the population, and adjudicated every verdict. The devil's-advocate passes were adversarial in role but **not independent in the statistical sense**: they were agent passes issued from one instrument, by one operator, sharing correlated priors, with every verdict adjudicated by me. The false-kill rate was never measured, and the instrument was never given a positive control — it was never shown capable of emitting *survived* for a business known to work, so its discriminating power is unquantified. There is no inter-rater reliability to report, no blinding, and a live conflict of interest in both directions: sunk cost pushed toward finding survivors; by June, fatigue and a mounting negative prior may have pushed toward kills. Three facts partially mitigate but do not remove the threat: the conditions were fixed before the population run; the zero is invariant across all three internal tallies while only the wounded/dead line moves (0/18/139 vs. 0/25/132 vs. 0/~26/~131); and the per-segment failure attributions are published for adversarial re-scoring. A hostile reader can rerun the instrument on the published *segments* and dispute segment-level verdicts; note the published unit is the segment, not the candidate, so per-company re-scoring is not possible from this release. That check has not been performed by anyone but me.

**Selection and construct validity.** The population was hunted broadly and deliberately included the project's own favored theses, but it was still one person's map of the addressable fields; entire fundable segments may simply not have been surveyed. And the instrument screens *demand shape*, not market size, pricing, timing, or reachability — a clean fit, had one existed, would still not have been a validated business.

## 7 Conclusion

Cealis set out to remove the assumption that somebody can always see the data, and ended as two results of unequal value. The technical result is a competent composition: a genuinely tested cryptographic core — real secret sharing, a fixture-locked envelope, an invariant-checked on-chain trigger, a contract suite reproduced green offline — wrapped in an operational layer that was never finished, with the gap between the two documented rather than blurred. The market result is the one I would defend hardest: a pre-committed, falsifiable demand instrument, run adversarially across 157 candidates, returned zero clean fits and a structural explanation — the customers with objective triggers cannot pay, and the customers who can pay have subjective triggers and standing duties to read their own data. The mathematics held; the market did not; and the test that established this cost about a day against a build that cost three months. The project was retired on that evidence, and the retirement is the finding. For anyone drawn to this primitive — and the primitive remains attractive — the reusable artifacts are the cryptographic core, the specification corpus, and above all the instrument: run the kill test before the build.
