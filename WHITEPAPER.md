# Conditional Sealing — A Public Whitepaper Edition

**Simon Baltes, 2026 (written at the project's retirement and open-source release)**

> **What this document is.** This is the readable edition of the project's specification corpus — a full technical whitepaper and eight Stage-2 specifications, condensed to something a person can read in one sitting. It describes a system that was built between March and June 2026 and deliberately retired on 2026-06-10. The system was designed and built under the working name **Cealis** and is released as **conditional-sealing**; the working name appears unchanged in the frozen specifications, audit records, and on-chain artifacts this document draws on. The honest one-line status, taken verbatim from the project's own state-at-retirement assessment, is: **cryptographically real, operationally unfinished.** The cryptographic core is implemented, spec-conformant, and tested against locked golden fixtures. The operational layer around it — the live wiring to external gate operators, the production runtime, the user-facing surfaces — was never finished. The code was **never externally audited**, never ran in production, and never held real user data. Read this as a design record and a reference, not as a description of a running service.

---

## Contributions and limitations

This document doubles as the project's research record, so I will state its contributions the way a paper would, and the limitations with the same precision.

**Contributions.**

1. **A tested reference implementation of AND-composed, multi-network threshold custody for condition-gated decryption** — the operation this document calls *conditional sealing*. The combiner enforces that a Shamir threshold spans several organizationally distinct gate networks, so that no single threshold network, including the operator's own, can release a key alone.
2. **An `age`-plugin envelope format with per-stanza MACs and cross-variant substitution defenses**, locked by golden fixtures so that drift between specification and implementation fails the build rather than accumulating silently.
3. **A refusal-only verifier role** — a gate that can veto a release but cannot open anything — as an explicit, scoped compliance seam rather than an unstated backdoor.
4. **A falsifiable demand-test methodology** (the Fundability Fingerprint), pre-committed before the market work was run, with a documented negative result: 0 clean fits out of 157 surveyed companies (Section 6).
5. **A per-subsystem maturity record** (Section 5), which grades each component by what it demonstrably does rather than by what it was intended to do.

**Limitations.** Each contribution has a mirror. The operational layer was never demonstrated live: the external gate signing transports were stubs, and the independent parties whose separateness is the point ran simulated inside one process. The testnet deployment is a single run whose bytecode has since drifted from the fixed source. No external review of any kind took place. And the field arithmetic is constant-time by construction, but a JIT'd, garbage-collected JavaScript runtime makes any constant-time claim best-effort. The status box above is this document's canonical statement of these limits; later sections point back to it rather than restating it.

## 1. What the system does

Conditional Sealing seals data so that it can be opened for exactly one reason: a condition that both sides agreed to in advance, written so a machine can check it, becomes true. Until then it does not open. By design there is no login that reveals it, no support team that can be leaned on, no human in the loop to bribe or coerce.

The short way to say it: **escrow with no escrow agent.** The role a trusted middleman normally plays — holding something valuable and releasing it when the moment is right — is performed instead by cryptography and a public blockchain. The design goal is that no single party can open the data early: not the counterparty, not an administrator, not the operator, not an attacker who has broken into one part of the system.

One sentence before anything else: that design goal is held today *by the cryptography*, which is real, implemented, and tested, and was never demonstrated *by the operations* — the seam is stated once in the status box above, and Section 4 maps exactly where it runs.

That one capability — seal under a condition no single party can override, release automatically when the condition is met — is the whole system. I called the operation *conditional sealing*. It does not change from use case to use case; what changes is the condition and the configuration around it. Everything else in this document is what that one primitive turns out to be worth, how it was built, why the math held and the market did not, and what a reader can take from the wreckage.

## 2. The problem it removes

Every digital system in use today shares one hidden assumption: **somebody can always see the data.** A vault has an administrator. A "secure" database has a database admin. An escrow account has an escrow agent. The instant data exists somewhere, a person or a company is in a position to read it — and therefore can be subpoenaed, bribed, breached, or can simply decide to look.

That assumption is so universal it is invisible, and it quietly blocks a whole class of valuable arrangements. The blocker in each case is the same sentence: *someone can open it too early.*

- A security researcher won't hand you a working exploit before you pay — once you've seen it, the incentive to pay evaporates.
- A lender can't safely hold a borrower's real-world identity — the moment they hold it, they are a honeypot and a standing liability.
- A counterparty in a sensitive deal won't pre-load the data the other side needs *only if something goes wrong* — because whoever holds it in the meantime can be pressured into handing it over.

In each of these, the deal does not merely become riskier because someone can peek early. It does not happen at all, or it happens only at a punitive price. Remove the early-peek possibility and the arrangement becomes possible. The system was not designed as a safer version of an existing product. It was designed as the thing that lets a class of arrangements exist that currently can't.

The same primitive reads differently through different eyes, and that turned out to be a feature of the design rather than a confusion. To a platform that must hold identity data but never wants the ability to read it, a seal means *non-existence*: "to me, this data does not exist until the agreed event happens." To someone protecting evidence or intellectual property, it means *tamper-evidence*: "this is provably the original, sealed and untouched since the moment it was created." To parties in a settlement or contingent disclosure, it means *conditional reveal*: "this opens on a defined trigger and on nothing else." One core, configured per deployment, rather than three products.

## 3. How it works

The architecture is a stack of layers, each one closing a class of attack. I'll walk it from the payload outward.

**The payload is encrypted once, off-chain.** At commit time a fresh data-encryption key (DEK) is generated, and the plaintext is encrypted under ChaCha20-Poly1305, an authenticated cipher, with the nonce derived from the DEK and the commit's context digest, and the commit's binding metadata carried as associated data. Only a cryptographic fingerprint of the sealed data — a hash — is recorded on-chain. The data itself never touches the blockchain. The consequence is sharp: an attacker who completely owns the smart contract has stolen a hash, not the data. There is nothing decryptable on the chain to take.

**The key is split, and no single share is enough.** The DEK is divided using Shamir secret sharing over GF(2^8), implemented with field arithmetic that is constant-time by construction (best-effort under the JavaScript runtime — see Contributions and limitations) and verified against locked test vectors. This is genuine secret sharing — a true cryptographic AND, where every required share is necessary and any missing share leaves you with nothing usable — not the weak imitation where each "share" secretly equals the whole key. The implementation was adversarially tested to confirm it does the real thing, including an integration check (environment-gated, not in CI) that dumps the server's stored state, confirms the key cannot be rebuilt from it without the gate keys, and includes a positive control showing the same records do reconstruct it when the gate keys are present.

**The key shares go to three signing gates; the fourth gate — the chain — is the trigger they all require.** Each share is wrapped to the signing party meant to hold it (G2, G3, G4 below). None of them signs until the chain's condition fires, so the composition is a strict four-gate AND even though the chain itself holds no share:

- **G1 — the chain (trigger, not a shareholder).** A `ConditionEngine` smart contract (deployed only to the Base Sepolia testnet; see the deployment disclaimer in Section 5) evaluates the configured condition: a date passing, an on-chain event firing, an oracle attesting a fact, a holder going silent. The chain, not a human, decides whether the condition is true.
- **G2 — Lit Protocol.** A rented threshold/TEE network that signs once its gate's release evidence is present.
- **G3 — drand or dcipher (Randamu).** A rented threshold network, chosen per deployment and frozen at commit. The scope is narrower than the bullet's position suggests: drand attests the passage of *time* (tlock-style timelock release), not arbitrary events; dcipher is the path toward richer condition attestation. Whichever network a deployment chooses, the choice is fixed at commit.
- **G4 — a refusal-only operator verifier.** It can *refuse* to sign on narrow legal, GDPR, or integrity grounds. It cannot open anything on its own; its signature alone is far below the reconstruction threshold.

Miss any signing gate and the Shamir threshold is not met; without the chain's condition, none of them signs at all. There is no decryption path that routes around the chain — internally I called this the *universal tripwire*, and it is the design's load-bearing property: the release trigger is objective by construction, because it is evaluated on-chain where there is no adjudicator to bribe. When a deployment adds conditional recipients (an heir, a beneficiary, an acquirer's counsel), the split widens: the share count and threshold grow together, so the AND stays an AND.

**The share wrap is hybrid post-quantum.** Each share is wrapped under X25519 combined with ML-KEM-768, so a future adversary who breaks elliptic-curve cryptography alone still cannot unwrap recorded shares. This is a hedge against harvest-now-decrypt-later, which matters for a system whose whole point is that sealed data may sit for years.

**Everything is carried in an authenticated envelope.** The seal travels as a custom `age`-plugin envelope: a header of gate-recipient stanzas plus the encrypted payload. Every stanza carries its own MAC over its index, binding tag, and plugin version, and conditional-recipient stanzas carry an additional binding MAC over their full length-prefixed payload. Verifiers must validate the MAC before parsing any stanza field, which closes cross-variant substitution attacks — a stanza of one type cannot be reinterpreted as another by byte games — and the plugin aborts hard if any MAC fails.

**The gates only ever sign; they never see data.** A gate's signature is an authorization to decap one share, nothing more. The reveal verifies signatures, decaps the corresponding stanzas, reconstructs the DEK from shares, and delivers the plaintext to the entitled recipients along with an on-chain chain-of-custody record of every step. Below threshold, `Shamir.combine` yields nothing and the reveal halts, fail-closed.

Read together: there is nothing to steal on the chain, the one release path cannot be forged from outside, no single party's share is enough, and the trigger is a fact rather than a judgment. Those are the designed properties of the part that was built, adversarially tested rather than externally proven. The next section is the accounting of the part that wasn't built.

## 4. The trust model

The gap between what the mathematics holds and what the operations ever demonstrated is the most important fact about this system. The status box at the top states it once; this section maps where the seam runs.

**What the math holds.** The AND-composition combiner — the component that enforces "no master key" — is real and adversarially tested. The Shamir implementation is genuine threshold cryptography, golden-vector verified. A database-dump integration check shows that the system's own stored state does not contain the gate keys and cannot, by itself, reconstruct a key. The envelope format, the per-stanza MACs, and the signature verifiers conform to their specifications, and a checked-in spec-compliance guard makes drift between spec and implementation fail the test suite rather than accumulate silently. These are demonstrated properties of code you can read in this repository.

**What operations never demonstrated.** The live signing transports to the external gate operators — the actual network calls to Lit, to drand or dcipher — were stubs at retirement. The independent parties whose separateness is the entire point were, in practice, simulated inside one process on one machine, so "all of them at once" collapsed to "that one process." The off-chain runtime ran on in-memory mocks: no real database, no real queue, authentication unwired. The offline independent verifier (`verify-sdk`), whose job was to let anyone check a seal without trusting the operator, is a stub — the independence property is asserted in the design, not delivered in code. Operational decentralization — organizationally, jurisdictionally, and TEE-vendor-disjoint operators actually running their gates — was architected and never realized. By construction the architecture intends that no single operator can open a seal; no deployment ever put that intention to an end-to-end operational test.

**G4 means compellability, and I say so.** The refusal-only gate exists for good reasons — a lawful-erasure order, a detected integrity failure — but a component that *can* refuse is a component that can be *compelled* to refuse. That is why the project maintained a standing list of banned phrasings, which this document inherits: never "non-custodial" without qualification, never "decentralized" as a flat claim, never "a subpoena can't open it," never "no one can block it." The honest claims are narrower: the architecture is non-custody *by design* for the fixed gates, releases cannot be *forged* from outside, and refusal is scoped, logged, and below the threshold needed to open anything. A system whose operator can halt releases is not censorship-proof, and pretending otherwise would have been marketing, not engineering.

**Where single-key edges remained.** Three operational surfaces were known, named, and open at retirement. Contract upgrade authority sat behind a mandatory time delay but on a single key rather than genuinely independent control — the honest claim was always "upgrades are delayed," never "no single party can change the contracts." The key-publish step — the moment each Shamir share is wrapped to the party meant to hold it — was not yet bound to verified party identities, so a substitution at that moment would not have failed shut. And privileged roles configured each seal's parameters and delivery destination. None of these is a crack in the cryptography; all of them are places where, at retirement, a single operational key still mattered.

**The security record.** The external-review status is in the status box at the top and does not improve below it. Internal security review was substantive — repeated adversarial self-audit passes in May and June 2026 — and it found real problems: multiple CRITICAL and HIGH findings across the live testnet contracts and the off-chain pipeline, published in this repository (the corpus names four distinct CRITICAL findings over time; see the [finding reconciliation](docs/audits/FINDING-RECONCILIATION.md)). An early self-assessment against the Trail of Bits nine-category code-maturity rubric scored the contracts a perfect 5.00/5; a later rewrite withdrew that grade to roughly **3.5/5**, noting explicitly that the original had counted self-authored documentation as audit maturity. The withdrawn grade, the audit findings, and the full scorecard are in `docs/audits/`.

## 5. What was built and verified

The state below was assessed against the source tree at retirement; where earlier internal documents carried stale figures, this corrected assessment supersedes them.

The build ran for roughly three git-tracked months, 2026-03-13 to 2026-06-10. At retirement the codebase held the `ConditionEngine` plus 9 condition modules; the contract suite's invariants include the universal-tripwire property that no module or registry can move the system into a release-authorized state on its own. The cryptographic core is tested against locked golden fixtures, and a spec-compliance guard is checked into the repository so that drift between the specs and the code fails the build rather than accumulating silently.

The specification corpus — a full technical whitepaper plus eight Stage-2 specifications covering the cryptography, the contracts, custody integration, the per-partner configurator, ingestion and delivery, operational key ceremonies, the selective-disclosure pipeline, and controlled use — is the complete worked design behind this system. The system was designed before and while it was built, not improvised and documented after.

The contracts are live on the Base Sepolia testnet, fronted by the `ConditionEngine` proxy `0xb09a8300423CA3BD0E028bAB6A6245A248520D02`; the implementation contracts behind the proxies are Sourcify-verified (the proxies themselves are not — see `deployments/base-sepolia-verification.json`), and a read-only live smoke script is in `contracts/script/live-smoke.sh`. The deployment's caveats — testnet-only, bytecode drifted behind the June 2026 source-level security fixes, administrative keys not under secure management — are stated canonically in `deployments/README.md`; read that disclaimer before touching anything on-chain, and never send anything of value to the deployment.

Per-subsystem, the honest state at retirement:

| Subsystem | State | Reality at retirement |
|---|---|---|
| `v3-crypto` (sealing primitives, envelope, Shamir + PQ wrap) | real & tested | The strongest part: real, golden-vector tested, best-effort constant-time field math (see §3), spec-compliance guard |
| `v3-custody` (4-gate AND combiner) | partial | Combiner real and adversarially tested; external gate signing transports were stubs |
| `contracts` (ConditionEngine + modules + governance) | partial | Strong test discipline in source; live testnet deploy predates the security fixes |

One more thing deserves a line: the build methodology itself. A solo founder drove AI agent fleets through a structured pipeline — Work-Package missions early on, then a Stage/Rail/Wave roadmap, then autonomous "build-loop fires" that ran inventory-fix-verify-close cycles. The retirement itself was run as a deliberate close-out of that pipeline, not an abandonment.

## 6. Why it was retired

Cealis died on a demand-side scissor, not on technology.

The design's load-bearing insight was that a public chain is the one place a release trigger can be objective by construction. What the market work of May and June 2026 showed is that the same insight cuts the customer base in half, and the halves don't overlap. Where the trigger is genuinely objective — an on-chain event, a chain-verifiable fact — the customers are crypto-native, small, and unpaying, and the trustless slot is already held by incumbents like Safe/Zodiac and Sablier. Where the customers can pay — regulated enterprises with real data liabilities — the triggers they care about are subjective, and worse, they carry a standing legal duty to access their own data live, which is precisely the capability conditional sealing removes. Objectivity of the trigger and ability to pay turned out to be negatively correlated across the surveyed market. During the same months, a far better-funded category shipped the commodity version of the underlying capability: Zama took FHE with a threshold key-management service to mainnet in December 2025. The cryptography solved a real problem; it was not the binding constraint.

The decision itself was made falsifiable before it was made. The project built a strict paper-only demand filter — the Fundability Fingerprint, a six-condition AND test that a target segment had to pass cleanly — and ran it, then ran a follow-on kill test over 157 concrete companies. The result was **0 clean fits out of 157**. Faced with that, the options were to soften the test until something passed, or to believe the evidence. The project was killed on 2026-06-10.

I count that as a corrected instinct rather than a failure of nerve. The original instinct — build the primitive first, because the primitive is the hard part — produced real cryptography and a real specification corpus. The corrected instinct is the one the kill test enforced: the hard part of this business was never the mathematics, it was finding a buyer whose trigger is objective *and* whose budget is real, and no amount of additional engineering would have manufactured that buyer. Killing a technically healthy project on demand evidence, with the test results published, is the decision I would defend hardest from the whole run.

## Related work and positioning

This design did not invent the ambition of condition-gated secrets. It sits in a lineage, and placing it there precisely is the fastest way to see what is new, what is borrowed, and what is merely assembled.

**Witness encryption.** The theoretical ideal of this entire design space is witness encryption (Garg, Gentry, Sahai, and Waters, 2013): encrypt a message to an NP statement, so that anyone holding a witness for the statement can decrypt, with no committee, no key holders, and no trust in anyone. If practical witness encryption existed at usable cost, most of this architecture would be unnecessary — the condition itself would be the key. It does not exist at usable cost. Conditional sealing is best read as a committee-based practical approximation of witness encryption: threshold networks stand in for the missing mathematics, checking the condition and releasing key shares when it holds. The trade is explicit and unflattering — deployability today in exchange for trust in committees — and every honest claim in this document is downstream of that trade.

**Timelock encryption.** drand's tlock construction delivers exactly one condition — the passage of time — with elegant economy: encrypt to a future round of a public randomness beacon, and the beacon's own operation performs the release. Where the condition is purely "after time T," tlock is simpler than this design and strictly less trusting, and the G3 gate here uses drand in precisely this time-attestation role (Section 3). Conditional sealing generalizes the condition language — on-chain events, oracle-attested facts, the silence of a holder — but pays for the generality with committee trust and with the operational apparatus Section 4 describes.

**Lit Protocol alone.** The sharpest competitive question the design ever faced was "why not just Lit?" — and the honest answer starts by conceding the premise. Lit Protocol already gates decryption on programmable on-chain conditions, holds keys in a live threshold/TEE network, and requires none of this system's surrounding machinery. For many use cases, Lit alone is the simpler right answer, and this document says so plainly. The design here differs in three ways, and the differences matter only when their threat models matter. First, AND-composition across organizationally disjoint networks: Lit is one gate among four, so no single threshold network — Lit included — can release a key by itself; a compromise or compulsion of one network is below the Shamir threshold. Second, the refusal-only G4 gate gives compliance a scoped, sub-threshold veto with a defined legal surface, instead of an ambient operator power. Third, the deliberate payload/key-split separation: the payload is encrypted once, off-chain, and only wrapped key shares ever route through gate networks, so no gate network ever holds the data or material sufficient to decrypt it.

**Smart-contract escrow and custody.** Safe with Zodiac modules gives programmable custody of assets; Sablier streams value on a schedule; the hashed-timelock contract genre releases funds against a revealed preimage. These are the incumbents Section 6 credits with holding the trustless slot, and the distinction is categorical: they control *funds*, not *data confidentiality*. They answer "who may move this value, and when"; conditional sealing answers "who may read this data, and when." The market adjacency was real; the primitive is different.

**Fully homomorphic encryption.** Zama's FHE stack computes on encrypted data — a stronger and genuinely different primitive. Conditional sealing opens data when a condition becomes true; FHE lets you *use* data without ever opening it, and its threshold key-management service overlaps the custody role the gates play here. Zama's mainnet arrival in December 2025 reshaped the market this system would have sold into; Section 6 covers the commercial consequence.

**The dead-man's-switch genre.** The category this design most resembles in the popular imagination is the dead-man's switch: check-in timers on somebody's server, a trusted party instructed to send an email. The genre's defining weakness is that its trust assumptions are ad hoc and undocumented, and usually reduce to one operator who can be subpoenaed, bribed, or simply fail. This design is best understood as an attempt to systematize that genre: write the trust model down, split it across parties, make the trigger machine-checkable, and give refusal a defined shape.

**What would have been novel, and what is composition.** Precision matters here. The cryptographic pieces are not new: Shamir secret sharing (1979), a hybrid X25519 + ML-KEM-768 share wrap (ML-KEM per FIPS 203), ChaCha20-Poly1305 (RFC 8439), and the `age` envelope discipline are engineering composition — careful, but standard. The per-stanza MACs and cross-variant substitution defenses are good format engineering, not new cryptography. Two things would have been genuinely novel if completed, and neither was: an *operationally realized* AND-composition across organizationally, jurisdictionally, and TEE-vendor-disjoint threshold networks, demonstrated live end-to-end — a custody trust model I have not seen deployed elsewhere; and the refusal-only compliance gate operated as a first-class, sub-threshold protocol role rather than a documentation promise. Both are exactly the operational work the status box says was never finished. What stands completed instead is the composition itself, its test record, and the negative demand result of Section 6.

## 7. What a reader can take from it

The project is archived and unmaintained, and contributions are not solicited. But an archive can still be useful, and four things in this repository are worth taking.

**The cryptography.** The `v3-crypto` package is the strongest code here: a GF(2^8) Shamir implementation with golden vectors and constant-time-by-construction field math (best-effort under a JavaScript runtime; see §3), a hybrid X25519 + ML-KEM-768 share wrap, a complete `age`-plugin envelope format with per-stanza MACs and cross-variant substitution defenses, and the signature verifiers around them. It is Apache-2.0 licensed with an explicit patent grant, spec-conformant, and adversarially tested. Its review status is the one in the status box, so anything you lift from it should be independently reviewed before real use — but as a reference implementation of threshold-gated sealing, it is genuinely reusable.

**The specifications.** The corpus in `docs/specs/` is a complete worked design for condition-gated data escrow: the commit, reveal, and shred ceremonies, the four-gate custody composition, the per-partner policy layer, the oracle discipline, the selective-disclosure pipeline. Whether or not anyone builds this exact system again, the design questions it answers — how do you bind a key-split to attested identities, how do you make refusal scoped and provable, how do you keep a shred from racing a reveal — will recur in any serious attempt at the same primitive.

**The methodology.** The agent-orchestrated build process — missions, roadmap rails, autonomous verify-and-close loops — produced a fully specified contract suite and tested TypeScript packages in about three months with one person steering. The internal process documents are not part of this archive, and neither is the commit history: this repository is published with a fresh single-commit history because the original contains credentials and personal data. The evidence available to a reader is therefore the source tree and the test record — not the build log.

**The audit discipline.** The practice itself is transferable: a banned-phrasings list that forbade the claims the marketing wanted to make; adversarial self-audits whose CRITICAL findings were published; a maturity self-grade that was withdrawn and rewritten downward when it didn't survive scrutiny; and a retirement decision made by a pre-committed falsifiable test. None of it required funding or permission.
